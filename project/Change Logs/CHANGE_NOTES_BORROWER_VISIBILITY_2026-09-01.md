## Status

**Implemented and configuration-verified in production OLTP at version `2.200099`; awaiting the user's record-level manual acceptance test.**

- No borrower was marked hidden during implementation.

## Design decision

The visibility rule is implemented through one physical flag and one OLTP slice, not through a security filter or calculation condition:

```appsheet
NOT([Hidden Flag])
```

This design preserves the complete base-table population for every business rule. Only the primary `Borrowers` view reads the filtered slice. A hidden borrower therefore still:

- exists in the authoritative `Borrowers` table;
- remains referenced by `Loans[Ref Borrowers]` and all existing reverse references;
- appears in the Loans view and through loan-to-borrower navigation;
- contributes to Statistics, portfolio totals, collection logic, and all other calculations; and
- remains available to OLAP and downstream reporting through the existing base tables.

This is intentionally not a deletion, archival state, default resolution, security control, or reporting exclusion.

## Implemented production changes

### 1. AppSheet Database source column

Added the following physical column to `Money database` / `Borrowers`:

| Property | Configuration |
| --- | --- |
| Name | `Hidden Flag` |
| Source type | `Yes/No` |
| Existing rows | Created unchecked/false; no row was switched to true during implementation |

The source column was added directly in the production AppSheet Database. The OLTP `Borrowers` schema was then regenerated from 30 to 31 columns.

### 2. OLTP column configuration

Configured `Borrowers[Hidden Flag]` as follows:

| Property | Configuration |
| --- | --- |
| AppSheet type | `Yes/No` |
| Show? | `TRUE` |
| Editable? | `TRUE` |
| Required? | `FALSE` |
| Initial value | `FALSE` |
| Display name | `ซ่อนจากรายชื่อผู้กู้ / Hide from Borrowers List` |
| Description | Explains that the flag hides only the Borrowers view and that loans/calculations still include the borrower |
| Searchable | Retained as generated by AppSheet; it does not control the filter behavior |

No virtual column or aggregate helper was added.

### 3. Editable `Visible Borrowers` slice

Created OLTP slice `Visible Borrowers`:

| Property | Configuration |
| --- | --- |
| Source table | `Borrowers` |
| Row filter | `NOT([Hidden Flag])` |
| Update mode | Adds, updates, and deletes allowed, preserving the operational behavior of the original base-table view |
| Included columns | All 31 production OLTP Borrowers columns, including `Hidden Flag` |
| Descriptive comment | Records that only the primary borrower list is filtered and that base-table relationships, loans, collections, and calculations remain unchanged |

The 31-column order is recorded in `Documents/AppSheet_Data_Dictionary.xlsx` / `Slice Columns`.

### 4. Primary Borrowers view

Changed only the primary `Borrowers` deck view:

- Before: source `Borrowers`.
- After: source `Visible Borrowers`.
- Preserved the existing Creation Date sort, card fields, position, and actions.

The following view sources were re-read after the change and remain unchanged:

- `Collection` -> `Todays Collection Board`.
- `Loans` -> `Loans`.

### 5. Borrowers form

`Borrowers_Form` uses manual column order. Added `Hidden Flag` after `Creation Date` so the operator can set or clear the flag from the normal borrower edit form. The embedded production form preview displayed the field as a Yes/No choice and showed the bilingual explanation.

No separate management view was added. A hidden borrower can be restored by opening the borrower through an associated loan/reference and setting `Hidden Flag` back to `FALSE`, or by updating the source field with appropriate access.

## Manual testing required

Use a controlled borrower with a known active or historical loan:

1. Sync the production app to version `2.200099`.
2. Record the current Borrowers list result and relevant totals.
3. Edit the borrower and set `ซ่อนจากรายชื่อผู้กู้ / Hide from Borrowers List` to Yes.
4. Save and sync; confirm the borrower disappears from only the primary Borrowers view.
5. Open Loans; confirm the borrower's loans still appear normally.
6. Open a loan and follow its borrower reference; confirm the borrower record remains accessible.
7. If the borrower has a current collection item, confirm Collection behavior is unchanged because it still uses `Todays Collection Board`.
8. Confirm dashboard/Statistics totals and relevant loan balances are unchanged.
9. Restore the borrower through the loan/reference edit path by setting `Hidden Flag` to No.
10. Sync and confirm the borrower returns to the primary Borrowers view.
11. Test creation of a new borrower; confirm the initial flag is No and the borrower appears normally.
12. Verify the same user roles that could edit borrowers before the change retain equivalent add/update behavior through the editable slice.

Do not treat the change as accepted until the hide, unaffected-loan/calculation, and unhide paths have all passed.

## Downstream considerations

- The physical column exists in the shared Money database, but the OLAP app schema was intentionally not regenerated. This causes no current OLAP filter or calculation change.
- If OLAP later needs to display or manage the flag, regenerate and review the OLAP Borrowers schema under a separate change. Do not use `Hidden Flag` to exclude borrowers from reporting metrics unless the user explicitly changes the business rule.
- Looker Studio must continue to include the complete borrower and loan populations.

## Rollback instructions

1. In production OLTP, open Manage > Versions.
2. Restore version `2.200095`.
3. Sync a client and confirm the primary Borrowers view again uses the base `Borrowers` table and the form no longer references `Hidden Flag`.
4. Leave the nullable/false source-database `Hidden Flag` column in place. It is harmless when unused and preserves any flag values created during manual testing.
5. If source-column removal is later requested, first confirm no app, slice, view, form, automation, OLAP object, or external consumer references it, then perform that destructive schema change under a new approved change log.
