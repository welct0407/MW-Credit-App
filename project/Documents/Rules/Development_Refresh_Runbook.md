# Owner-requested DEV refresh

Owner revision: **21 October 2026, Asia/Bangkok**. A refresh replaces the contents of `loan_manager_dev` with a snapshot of `loan_manager_prod`. It is exceptional, not part of development or promotion, and it is the only PROD-to-DEV copy this project has (no other environment is refreshed). The current PWA/API configuration and the canonical MW-Credit-App database tools are used; no AppSheet copies, regeneration or application-mode changes.

## Scope and authority

An owner instruction "refresh DEV from PROD" approves: one read-only PROD snapshot, a restore-tested DEV backup, the destructive replacement of `loan_manager_dev`, the owner and privilege repair that follows, the temporary owner window, the required private records and the Environment inventory update. It does not approve a PROD write of any kind, a notification send, copying receipt objects between buckets, schema changes, service activation or a deployed code or configuration refresh (separate, [below](#code-and-configuration-refresh-and-closure)). Confirm the scope (data only, or data plus code and configuration) and a quiet window in which nobody uses the DEV PWA.

## Executor and route

Run it from a Claude Code cloud session in Accept edits mode (Auto mode denies the sanctioned PROD read and the Secret Manager reads), signed in as `codex-cloud`, through the IAP tunnel to the Debian host's Cloud SQL Auth Proxy ([database/README.md](../../../database/README.md#linux-cloud-sessions)). Reads and snapshots use the read identity (`Get-DbEnvironment development`); writes use `postgres` (`Get-DbEnvironment development -Admin`). Use the PostgreSQL 18 client binaries under `/workspace/.setup/postgresql-18.6/bin`; the system `pg_dump` is version 16. Evidence goes to `$MW_PRIVATE_ROOT/AppSheet-Loan-Project/flyway/dev-refresh-<date>/` (mode 0600) and the private operator bucket (`dev-backups/`), because the session is ephemeral; nothing private enters Git.

## Facts that shape the procedure

- DEV and PROD are two databases on one instance, so roles are shared. PROD objects are owned by `_prod` closed roles (`mw_notify_owner_prod`, `mw_jobs_owner_prod`, `mw_ledger_owner_prod`, `mw_changes_owner_prod`, `mw_app_prod_journal_owner`), DEV objects by the `_dev` ones. A restore that carries owners or privileges would silently give DEV objects to PROD roles. Restore with `--no-owner --no-privileges` and repair owners and privileges to the DEV snapshot with `scripts/database/Refresh-DevCatalog.py reconcile`.
- On Cloud SQL `postgres` is not a superuser and holds the DEV owner roles with `inherit false, set false`. Dropping, re-owning or granting on their objects needs the owner window (`owner-authority-cli.mjs prepare` for the five DEV owners) open before the restore and closed (`restore`) after the Flyway check. The window also grants each owner `CREATE ON SCHEMA public`; the reconcile must leave those grants in place (`--window-owner` once per prepared owner), or `restore` refuses with "Owned authority changed concurrently" and the grants have to be re-granted by hand first. A new owner needs `CREATE` on the object's schema, so the reconcile restores schema owners before their objects (first live run, 21 October 2026).
- A schema plus data restore creates triggers after the data load, so no calculation, ledger or change-log trigger fires. A data-only restore would re-run the ledger projection and is not allowed; disabling triggers is forbidden by the hard rules. Use `pg_restore --clean --if-exists --no-owner --no-privileges --exit-on-error -1`: one transaction, so a failure leaves DEV untouched.
- `pwa_push_subscriptions` holds PROD device credentials and `pwa_notification_deliveries` pending sends; the DEV dispatcher would push to the PROD-installed app. Delete both before any DEV worker runs; keep events, preferences and job runs.
- `flyway_schema_history` arrives from PROD. DEV may end at the same or a higher version; reapply unreleased migrations with the guarded runner inside the owner window, never `baseline`, `repair` or checksum edits.
- DEV writers are the three Cloud Scheduler jobs `mw-credit-app-dev-{notifications,daily-charges,recent-analytics}` (region `asia-southeast1`) and the DEV command service under a signed-in person. The integration agent writes to PROD only. Read the schedulers' state first; pause only the enabled ones with `gcloud scheduler jobs pause`, and let a Terraform plan of the `dev` stack confirm the end state (it must show no other change).
- Restored receipt rows point at PROD objects; the DEV command service stays on the DEV bucket, so those images do not render in DEV. Never point DEV at the PROD bucket.
- DEV PWA clients re-walk their offline dataset once after the refresh (the change-log sequence restarts); nothing to repair.

## Procedure

1. **Preflight, read-only.** Tunnel up, read identity works, `MW_PRIVATE_ROOT` set, no ambient `PG*` variables, PostgreSQL 18 client on the path. Read DEV and PROD Flyway history (head, row count, one md5 over version:checksum); the newest file in `database/migrations/`; DEV `pg_stat_activity`; scheduler states. A checksum difference between DEV and PROD, or a PROD version ahead of DEV, stops the refresh.
2. **Baselines and DEV backup.** `Refresh-DevCatalog.py snapshot --identity read --fingerprints --out <private>/dev-catalog-before.json` (any `_prod` owner or grantee in DEV is a defect: stop). `application-role-cli.mjs --action plan` (after `Get-DbEnvironment development -Admin`) must report 0 violations; it always prints its full idempotent statement set (501 on 21 October 2026), and the same set must come back after the refresh. `configure-dev-read-role.py` must report no statements, and so must it after the refresh. `Backup-ProductionPromotion.py --environment development --expected-version <inventory DEV version> --approval-reference '<owner instruction>'` dumps DEV as the read identity, restore-tests it and copies the folder to `dev-backups/`; that dump is the rollback.
3. **PROD snapshot.** `Backup-ProductionPromotion.py --expected-version <inventory PROD version> --approval-reference '<owner instruction>'` (read-only on PROD; the dump, `baseline-private.json` fingerprints and `recovery.json` land in `prod-backups/`). `pg_restore --list` the dump and keep the listing.
4. **Rehearsal, required.** Disposable PostgreSQL 18 cluster under `$MW_LAB_DIR`, an empty database `loan_manager_dev`, then `Refresh-DevCatalog.py lab-prepare --lab-port <port> --before dev-catalog-before.json` (NOLOGIN placeholders for every role the live snapshot names, their memberships and the database owner; no CI prerequisite scripts). Restore the PROD dump with the exact options of step 6, run as root over TCP (the `postgres` OS user cannot read the private folder), delete the two notification tables' rows, `reconcile --lab-port <port> --before dev-catalog-before.json --apply`, `compare --prod-baseline baseline-private.json --expect-empty public.pwa_notification_deliveries,public.pwa_push_subscriptions`, then `Test-TriggerOrder.sql` and `Test-RowChanges.sql` (`Test-AccessMatrix.sql` and `Test-LedgerAccess.sql` encode the CI role set and fail on real DEV grants; they prove nothing here). Repeat the restore with the DEV dump, with `--clean --if-exists` (rollback rehearsal). Record the statement counts; they are the expected counts for step 6. The rehearsal `postgres` is a superuser, so Cloud SQL permission failures only show in the step 6 dry run. Destroy the cluster.
5. **Quiesce DEV.** Pause enabled DEV schedulers; the owner closes the DEV PWA; terminate the remaining DEV sessions (`pg_terminate_backend`) and confirm none return; write the preflight record.
6. **Replace DEV** in one admin session: `Get-DbEnvironment development -Admin`; `owner-authority-cli.mjs prepare --environment development --owner mw_notify_owner_dev --owner mw_jobs_owner_dev --owner mw_ledger_owner_dev --owner mw_changes_owner_dev --owner mw_app_dev_journal_owner --apply`; `pg_restore -h 127.0.0.1 -p 15432 -U postgres -d loan_manager_dev --clean --if-exists --no-owner --no-privileges --exit-on-error -1 <dump>` (password from the 0600 file for that command only, `PGSSLMODE=disable` on the proxy hop); `DELETE FROM public.pwa_notification_deliveries; DELETE FROM public.pwa_push_subscriptions;`; `Refresh-DevCatalog.py reconcile --identity admin --before dev-catalog-before.json --window-owner <each prepared owner>` as a dry run (it executes and rolls back), then `--apply` (commits only with an empty residual difference); `Invoke-Flyway.ps1 -Environment development -Command validate` (`migrate` first only for an approved pending set, followed by `application-role-cli.mjs --action post-migrate --apply`); `owner-authority-cli.mjs restore --state <prepare record> --apply`. Expect the restore to take about 13 minutes through the IAP tunnel for a 17 MB database (21 October 2026), not seconds; the lab numbers measure the database, not the tunnel.
7. **Verify before anything resumes.** `Refresh-DevCatalog.py compare --identity read --before dev-catalog-before.json --prod-baseline baseline-private.json --expect-empty public.pwa_notification_deliveries,public.pwa_push_subscriptions` reports an equal catalog and equal fingerprints; `application-role-cli.mjs --action plan` and `configure-dev-read-role.py` report nothing; zero enabled push subscriptions; DEV reader and command `/health` 200 and unauthenticated `/api/session` 401; one owner sign-in shows the refreshed data. A synthetic write test only when the owner asks.
7a. **Restore the DEV test Partner (R095).** A refresh replaces DEV data, so the Claude Code test account's Partner row is gone: run `psql -X -v ON_ERROR_STOP=1 -v login_email=welct0407@gmail.com -d loan_manager_dev -f scripts/database/Ensure-DevTestPartner.sql` as `postgres` (idempotent; DEV only; the notice says written or unchanged). Never run it against PROD and never add that account to PROD. One-time owner steps before the account works at all (not repeated per refresh; the Partner row above and DEV capability policy version 2 must exist first): no account is created (the account is the owner's existing Google account `welct0407@gmail.com`); sign in once at https://dev-lm.mw-credit.com with it; copy the refresh token from the browser DevTools and store it as a secret version without printing it: `read -rs TOKEN; printf '%s' "$TOKEN" | gcloud secrets versions add mw-credit-app-dev-claude-test-session --data-file=- --project clever-oasis-508610-n7`. The stored value is a Firebase refresh token for this app's project only: it grants no access to the Google account's mail or other Google services. PROD's identity check accepts it but PROD refuses it (no PROD policy member or Partner row); never add that email to PROD Partners or the PROD policy. The Identity Platform user pool is shared with PROD, so the test user can sign in to PROD but has no PROD policy member and no PROD Partner row, which is what keeps PROD closed; keep it that way.
8. **Resume, records, cleanup.** Terraform plan of the `dev` stack shows only the scheduler attributes you paused (apply) or no change; watch the first dispatcher tick (zero deliveries) and the first hourly job. The owner re-enables notifications in the DEV PWA on each DEV device. Update the DEV row of the [Environment inventory](../Environment_Inventory.md) (refresh date, PROD snapshot timestamp and dump sha256, DEV backup sha256 and object, owner-window and reconcile record ids) and write one change note; delete local dumps, restore directories and the admin credential file; close the tunnel by its ssh process (`kill $(pgrep -f 'ExitOnForwardFailure=ye[s]')`; a plain `pkill -f` pattern naming the host matches the shell that runs it). Report DEV ready, incomplete or rolled back, with what the owner still has to do.

## Rollback

Run step 6 again with the DEV dump from step 2 (skip the notification deletes; the DEV dump holds the DEV subscriptions), then step 7 against `dev-catalog-before.json` and its own fingerprints. Schedulers stay paused until that verifies. Never touch PROD as a workaround.

## Code and configuration refresh and closure

Only when the owner asked for it: deploy the intended pinned DEV artifact and configuration while preserving DEV URLs, theme and environment indicators, authentication, secrets and storage isolation; reapply retained work deliberately and rerun only the evidence the refresh invalidated. Refresh approves neither an unreleased feature nor promotion.
