# MW Credit solution design

A two-user financial operations PWA using the existing PostgreSQL financial engine. AppSheet is not a runtime, scheduler or API dependency.

## Current state

- Firebase Hosting serves the PWA from two sites (DEV `mw-credit-app-dev-737787224638`, PROD `mw-credit-prod-737787224638`) at `dev-lm.mw-credit.com` and `lm.mw-credit.com`.
- Cloud Run runs the reader, command, notify and jobs services per environment in `asia-southeast1` from one image per environment; reader and command run `services/production/business-server.mjs`, notify and jobs run `services/workers/server.mjs`.
- R090 (Released 23 October 2026): a fifth Cloud Run service per environment, `mw-credit-app-chat-{dev,prod}`, runs `services/chat/server.mjs` from the same image and serves the in-app chat (see In-app chat below).
- One shared Cloud SQL instance holds `loan_manager_dev` and `loan_manager_prod`. DEV schedulers stay paused; PROD has one scheduler owner per job.
- Deployed versions (Hosting versions, Cloud Run revisions and image digests, Flyway, Debian commit) are stated only in the [Environment inventory](Environment_Inventory.md#latest-verified-deployments).
- Read next for a PWA or API change: [PWA orchestration](Rules/PWA_Orchestration.md); for a promotion: [Release workflow](Rules/Release_Workflow.md).

## Data and financial behavior

PWA and agent payments converge on native API/SQL command handling. Do not duplicate allocation logic in clients. Preserve source identity, idempotency, audit and reconciliation; resolve uncertain outcomes before retrying.

Use [data model](PWA_Data_Model_Overview.md) and [dictionary](Data%20Dictionary/README.md). Heavy reusable computation belongs in SQL. Preserve grain, unknown/null values, signed corrections, date rules and provenance. Operational reads can display owner-scoped cached responses immediately while revalidating through live providers; completed-day analytics use governed snapshots. DEV and the PROD prepare complete owner-scoped read bundles and authorized receipt media in background, prioritizing foreground reads so unvisited views can query prepared data offline. Persistent bundles are separate from the evictable response cache. Bounded resumable chunks replace an existing complete bundle only after traversal finishes, using actor/day-scoped cursors and local mutation revision guards; traversal is not one global database snapshot. After initial completion, recurring content-hash manifests reuse unchanged DTO content and detect other-user changes; main-domain source fingerprints avoid unchanged provider evaluation, while protected recipient notifications scan manifests. Dataset/checkpoint commit guards preserve local mutations and pending edits. The header shows refresh/failure and active online cycle progress; polling coalesces with in-flight preparation to preserve cursor continuity; applied writes invalidate read revisions. Financial command validation and action previews remain network-authoritative. Historical corrections require rebuilding affected dates.

Principal, interest, capital, expenses and settlements remain distinct. Do not silently change reporting formulas in UI work. Partner identity/roles control access; delivery addresses are not authentication. Reviewed R062 settings let Delivery Email vary independently of Login Email, retaining role/capability checks; defaults never rewrite existing nullable flags. Cash-view changes are temporary until explicitly saved, distinct from immediately persisted language. R062 source verification and DEV/PROD settings delivery are complete; V92, command API and Hosting are verified. DEV delivery stays isolated. Unfinished forms restore in their original context and require Save/Confirm before synchronization. The DEV and PROD saved-change coordinator reconciles durable queued requests by request ID before posting on startup/reconnect/foreground wake or manual Sync now, serializes tabs and retains rejected/conflicting changes for review. Submitted actions require no second sync approval; known failures expose stable specific reasons and retained details. Direct Loan Delete submits online immediately without a confirm/pending-queue stage and uses owner/environment/loan-scoped UUID/version session recovery; reopen checks status, and only explicit unresolved retry can repost the same request. Backend constraints remain unchanged. Manual and automatic synchronization share the same engine; short retries back off while durable requests remain, and abandoned-tab locks recover without changing request identity. Released R059 enables owner-authorized one-time note-draft migration and automatic synchronization in PROD.

## Receipts, push and jobs

Receipt originals/manual uploads remain private in the existing GCS bucket. Preserve exact paths, generations and access checks; never guess filenames or revive AppSheet for compatibility. The PWA downscales photos to about 1600 px JPEG under 1 MiB before upload (server limit unchanged at 5 MiB); API storage I/O runs outside database transactions.

Receipt recognition (R075, enabled in DEV and PROD since R075; owner design in the [Claude Doc](https://claude.ai/artifact/KP7KKQnNy1QDnXqEiRsgRx)): after a manual slip upload the PWA calls the command service route `POST /api/payment-commands/{requestId}/receipts/{receiptId}/recognition`, which sends the stored image over the private VPC to the Debian recognizer `mw-receipt-recognition` (integration agent, `10.148.0.2:8790`, Google ID-token caller identity, DEV and PROD separated by caller). The provider is Codex by default, Gemini on Vertex AI, or (R142) Claude Opus 5.5 through keyless workload identity federation with Gemini as automatic fallback; per caller route keys choose the provider and may let a CRC-valid slip QR reference replace the printed reference for allowlisted banks, and the result contract is unchanged. The result only pre-fills the form with warnings (amount, bank reference, slip date and time); the person saves the payment, and manual command v7 carries `bankReference` and `transferTime` into Payments "Bank Reference" and "Created At". Recognition never posts a payment. The model lists every account or PromptPay number printed on the slip (`account_numbers`; R087); the host matches them against the active cash accounts: exactly one account matches, two of ours are ambiguous, none is unmatched. A slip of our own outgoing transfer therefore matches our account, and the form submission is the human check. The slip amount is read as a decimal string: a correctly grouped thousands comma (`1,480.00`) is accepted like the agent's rule (R079), whole baht fills the form, a fraction warns `amount_fractional`, and anything else (`5,00`, `1,2345`) warns `amount_unreadable` and fills nothing. Payer names (R095, source): the recognizer also returns `payer_name`, the sender name printed on the slip. The borrower's stored payer names (`Borrowers."Communication Name"`, one per line, shown as "Payer names on slips") are compared by the parity modules `payer_name.py` and `payer-name.mjs` (`match`, `near`, `mismatch` or `unknown`; titles, case and masked characters ignored; `?` one unknown letter; different scripts are `unknown`). The name never blocks or holds a payment in a strong context: the manual path shows `Payer on slip` and, when the name is new, an info line, and the agent decides the borrower by conversation as before. A posted receipt learns a new readable name (command `schemaVersion` 8, `payerLines` `{before, after}`, applied only if the column still equals `before`; V111). Only a partner-forwarded slip in a 4+ person group or a partner direct message is resolved by stored name (narrowed by group participants, the forwarder's same-batch nickname hint, charges due and an exact amount fit); otherwise it holds as `PAYER_UNRESOLVED` or `PAYER_NAME_UNREADABLE`.

Successful PWA/agent commits wake the notification worker centrally, after the response, within about 1.5 s; the minute worker recovers a missed wake. Persisted event/delivery records allow minute recovery without re-posting payments. Push text (R080, Released; R081 name rule in source): the dispatcher reads the event through `pwa_notify_content_v1` between prepare and start and sends a banner in the recipient's language (Partners "Language Preference": Thai for 'ไทย', otherwise English), title = activity + amount (for example `Payment received ฿5,000`), body = the borrower name only (no actor); R081 name rule: a Thai recipient sees Borrowers "Borrower Name", an English recipient only the English name (Borrowers "Description", the form's "English name"), and the body is empty (title only) when there is none; only the borrower name is truncated (grapheme budgets 30 title, 80 body; payload title 1 to 60, body 0 to 200 characters), and a failed read sends the generic "New activity". R089 (Released 22 October 2026): each Notifications history row shows the same title and body, rendered by the notification API through `pwa_notify_history_content_v1` (V103) from current facts with the caller as recipient, so it can differ from a past generic push, plus a "time · state" line with the translated state (Sent, Sending, Not confirmed, Failed, Not sent); a row without text, such as an old cached item, shows "MW Credit / New activity", and tapping a row opens the detail as before. The Web Push payload is v2 (`v`, `eventId`, `title`, `body`, `url`, `tag`); the service worker renders it and falls back for v1 or malformed payloads. The owner accepted borrower name and amount on the lock screen (20 October 2026). Subscriptions are per device with account preferences; iPhone enrollment uses the installed Home Screen app. No always-on database listener. R090 batch 2 (Released): every notification is dispatched immediately: the command service, the chat service and the jobs worker wake the notify worker after COMMIT (the 1.5 s post-commit cap that made command wakes no-ops is removed), a busy notify worker answers 202 queued and makes one more pass instead of 409, and the scheduler stays the recovery. A chat reply is pushed to the asking Partner's own devices only when the app has left the chat (V105 event `chat.reply`; "Reply ready" or "Reply failed" with the thread title); the PWA aborts the stream when the page is hidden, polls on return, and a notification tap opens the thread (`GET /api/chat/threads/:id` loads a thread outside the first page; the composer stays disabled until it is loaded). Whether the app left the chat is reported by the client, not inferred from the connection (Cloud Run does not propagate a client abort on the HTTP/1.1 SSE path): on hidden or `pagehide` the PWA sends a keepalive request (or `sendBeacon`, a `text/plain` body carrying the token and state, no preflight) to `POST /api/chat/threads/:id/messages/:messageId/presence`, which sets `pwa_chat_messages.detached_at` (V106, batch 2c); on visible it clears it and polls. Completion reads the flag and records the `chat.reply` event only when it is set; the service logs `chat_turn_attachment` and `chat_turn_presence`. Each answer shows the answering model at its end (appended to the sources line, for example "Checked: … · Gemini 4 Argon"; its own line under a failed reply; "checking figures · <model>" while provisional; the raw id for a retired model). Producer wakes (command, chat, jobs) get 30 s; a queued extra notify pass runs only with more than 11 s left, otherwise it is logged as dropped and the scheduler recovers.

Reads verify the token without a revocation check; writes and unknown routes check revocation (owner decision 19 October 2026, "check on writes only"). APIs return 401 `session_invalid` only for definite token errors; verifier outages return 503 `session_check_unavailable`, and a stalled request body returns 503 `body_timeout`. Both are retryable and never sign the owner out. Saved (pending) changes survive an involuntary sign-out; voluntary Sign out stays disabled until they sync.

Startup (R132, Released 6 November 2026): a device with a persisted Firebase identity and an owner offline lease verified within 24 hours shows the saved workspace at once from a provisional session (uid and email only, no token fields); network reads and writes wait until Firebase confirms the same uid, and a missing, different or failed identity takes the sign-out path that keeps pending saves. Offline datasets and media are deleted after 7 days without a successful online check; pending (unsynced) changes are never deleted. The About screen (available signed out) can produce an encrypted troubleshooting file (RSA-OAEP/AES-GCM, public key embedded in the build, private key in Secret Manager, owners only); saved-change content is included only when signed in, with no raw uid, email or tokens. Schema 2 (R133, Released 7 November 2026) adds each domain's last request (status, code, duration, attempts, failures), one `dataset-failed` event per distinct background failure, up to 10 recent check cycles with their triggers, preparation activity, receipt counts and a 3-receipt sample (unreadable blobs marked), session and sync-outcome events, startup timing marks (localStorage `mw-credit-startup-timing`, numbers only), latest build and device hints, with up to 40 events. The header's last-update cell shows the running activity (Connecting…, Signing in…, Signing out…, Saving…, Reading receipt…, Loading…) only while the refresh icon spins.

Offline sync (R078, Released to DEV and PROD on 19 October 2026). Polling: an unchanged poll is 2 requests; a changed records domain downloads a key-level delta from the V97 change log instead of re-walking, with the per-domain fingerprint as the authority, and a Bangkok day change keeps date-independent keys and re-reads the rest. Own write: a posted payment (or the result read once after a queued payment syncs) is applied to the stored records and collection bundles at once, rows show "Confirming…" (Correct, Move interest and Delete stay disabled) until the touched domains (records, collection, cash) confirm; the own receipt is seeded into the offline media store under the server receipt time (`seedOwnReceipt`: the local file when its SHA-256, size and type match the upload descriptor, otherwise one shared verified download; on the online post, a queued sync, a correction and a loan close), so it is not downloaded again. After a write, collection and cash also take key-level row deltas (per borrower, per account-day) and walk only on the listed conditions. Full sync: a last section of the Saved changes page (opened by All synced or Waiting to sync, also when nothing is waiting) sends the saved changes first, then walks every domain from the start after one confirmation; offline it is disabled; queue and drafts are never discarded. Reconciliation: at the first idle, visible, online moment after 06:00 and 18:00 Bangkok (or 12 hours after the last pass) the PWA asks the server to compare per-key digests of each stored domain; a pass the server cannot answer waits 30 minutes and does not repeat finished domains; a mismatch heals once per slot (the change cursor is dropped and the bundle is marked `needsWalk`, so a reload still walks). Data-check warning (UX-RECON-01..07): a mismatch that persists after its heal is shown per area above Full sync on the Saved changes page, as an indicator beside the header refresh icon, as a dot on the side-menu All synced button and as one toast per new occurrence; a later match, a Full sync followed by a check of the flagged areas, or sign-out clears it. Offline media: receipts are checked locally against their receipt time and re-queued when missing or older.

One native scheduler owns each job/environment. Daily charges run at 00:05 and recent analytics hourly, Asia/Bangkok. SQL job keys/locking prevent duplicate work.

## In-app chat (R090)

Status: Released to DEV and PROD on 23 October 2026 (PR #131, batches 1, 2 and 2c; the PROD service exists because `chat_authorized` was set under the owner's production instruction; tag `R090` pending). Design and owner decisions: [R090 design](../outputs/r090-pwa-chatbot/DESIGN.md); change note: [R090 chat](https://github.com/welct0407/MW-Credit-App/blob/4c80ffde/Change%20Logs/CHANGE_NOTES_R090_PWA_CHATBOT_2026-10-23.md).

The Partner conversation moves from Instagram into the PWA: a fifth bottom-menu item "Chat" with chat history, a New chat button, a model picker (set by the service's `CHAT_MODELS_JSON`; `gemini-4-argon`, `gemini-3.8-flash` and `gemini-3.5-flash` until R108 (Released 31 October 2026), which made it Claude-only: `claude-opus-5-5`, with an old Gemini thread continuing on the default Claude model) and streamed answers (SSE). The service verifies the Firebase token and that the Partner holds the `read` capability (the PROD service exists only after `chat_authorized`), then runs a turn of at most a bounded number of model rounds: the model may call `data_catalogue`, `read_records` (the existing agent read provider, with the signed-in Partner as actor) and `sql_query` (a guarded read-only statement run under `SET LOCAL ROLE mw_chat_read_<env>`). A reply passes the number-grounding check before it is committed; a reply that cites numbers no tool returned is retried and, if still ungrounded, the turn fails with `GROUNDING_EXCEEDED`. The chat had no write tools in this release; R106 adds them (below). Batch 2 adds a read-only job status view for the SQL tool (`pwa_job_status_v1`, V105) so the chat can say whether the daily charge job ran, a query-discipline rule in the prompt (plan the turn, at most two fetch rounds, one query per relation) with `maxRounds` 16, and the reply push above. R092 (chat service only, no SQL or UI) makes `sql_query` return small results (at most 100 rows and 32 KB; the model aggregates totals in SQL and lists only the charges the reply shows) and has the reply name each borrower in the reply language (English `Description`, Thai `Borrower Name`, each falling back to the other). Claude is not a chat provider (no Vertex quota; the owner dropped it).

R122 (Released to DEV and PROD on 4 November 2026; PROD acceptance pending; owner scope of 4 November 2026; no SQL) adds a Translate button beside the English name on the New borrower form. `POST /api/chat/transliterate {text}` (Thai name, 1 to 120 characters) checks the same token and `read` capability, sends one tool-less request through the VM chat relay to Claude Sonnet 5.5 (`claude-sonnet-5-5`) at medium effort with thinking off (`thinking:{type:'between_tools'}`, `max_tokens` 512, RTGS romanization; owner choice for speed). The relay (`chat_relay_api.py`) accepts an optional, strictly validated `thinking` key (absent, `{type:adaptive}` or `{type:between_tools}`); the chat itself is unchanged and keeps adaptive thinking and returns `{english}` only when the JSON reply matches `^[A-Za-z][A-Za-z .'-]{0,119}$`; otherwise 502 `transliteration_invalid` or 503 `model_unavailable`. Nothing is stored and the name is not logged. The relay uses keyless federation, so no Anthropic key is added; the relay change is on the Debian VM `vm-mw-credit-agent`, shared by DEV and PROD, and is backward compatible. Also R122: the Borrower page shows outstanding principal under open loans and the Cash page From/To shows the borrower name in the viewer's language ([change note](https://github.com/welct0407/MW-Credit-App/blob/2d4dd30/Change%20Logs/CHANGE_NOTES_R122_BORROWER_DISPLAY_TRANSLATE_2026-11-04.md)).

R102 (Released 28 October 2026) adds the Collection status Long overdue (`long_overdue`, colour `#37474f`): a borrower with at least one unpaid past-due charge and 8 or more days since the borrower's last payment on the Bangkok business date (R137, owner decision of 9 November 2026, V140; R102 first counted 8 or more days past the charge date). A borrower who never paid counts from the first charge date. A payment is a posted repayment of more than 0 per borrower across all loans, not a Referral Rebate Offset or Net-off at Disbursement. Overdue is an unpaid past-due charge with a payment in the last 7 days. Long overdue rows are ordered fewest days since last payment first, and the tile reads "No payment for N days" or "Never paid · N days" (English and Thai) instead of "Long overdue · N days". Group order is not paid, partially paid, overdue, long overdue, fully paid; rows carry `overdueDays`. The same read serves online and offline, the Dashboard shows a "Long Overdue" count between Overdue and Fully Paid, and Metabase has a matching lane. R102 also adds the chat model Claude Opus 5.5 (Medium effort): the chat service sends to the VM relay `mw-chat-relay` (port 8791, Google ID token, caller allowlist per environment), which holds no key and reaches the Anthropic API through workload identity federation from the VM identity, one workspace and rule per environment. It is behind the `chat_relay.enabled` switch (off); Gemini stays the default until the DEV proof, and a relay failure reads "model unavailable" with no silent fallback.

R106 (Released to DEV and PROD on 30 October 2026; owner acceptance pending) lets the chat change data through a confirm card. For a Partner who holds `command` and is flagged `Partners."AI Reviewer"`, the chat service registers `propose_action` (and `action_catalogue`) over a static catalogue of 45 existing command operations (`services/chat/assets/command-catalogue.json`); `partner.*`, `cash-openings.initialize`, receipt-image payment corrections and loan closes, and a Full analytics refresh are excluded, and every delete, `settlement.reverse/cancel` and `loan.default` stay in with a destructive warning. The model never executes anything: the host fills the request id, target, expected version and predecessor from the command service's own record routes, validates the command, stores it as a proposal (V118 `pwa_chat_proposals`, 15 minutes) and streams a `proposal` event; the PWA shows a card built only from server fields (before and after values, rule-based consequences). A turn may propose a group of 1 to 100 changes on one card (D12, V119; the limit was 20 until R138, V141): the model sends them to `propose_action` in calls of at most 25 changes with `more:true` on every call but the last, because the Debian relay cuts one model request at 110 s; the service holds the planned lines in memory for the turn and creates the one group, and its one card, on the call without `more`, and a failed final call holds nothing, so the model sends every change again. Confirm is enabled as soon as the card is pending, the device is online and the remainder choice (if any) is made; the R106 visibility gate (CWR-01, Confirm disabled until the whole card had been seen) was removed in R138 because it never armed on a card taller than the pane, and Confirm all runs at most 270 s (lines not claimed by then stay pending). Each line is its own proposal with its own request id and outcome, and one Confirm runs the lines in order through the command service; a group is refused when it has more than 100 lines, two lines for the same record, a line that depends on a record created in the same group, or a payment or loan close together with other lines for the same borrower. A loan's version covers its charges and repayments, so a line pinned when the card was proposed would fail `source_conflict` after an earlier line of the same group changed that loan (R139). Confirm therefore carries versions forward: at its start it reads each affected line's version (it must equal the pinned one), and around each earlier line it reads again and carries the new version only if the before-read matched the carried one, so only the group's own writes are absorbed. A loan line (update, delete, undo default) is carried after earlier charge lines on its loan, a charge update or delete only after a loan update on its loan, a charge create is unversioned, and a card without `card.target.loanId`, an unknown outcome or a failed read is never carried; the line then posts its pinned version and the database refuses it. The carried line is posted once with the Partner's token under its own request id; loan closes, projected-charge bookings, defaults and charge generation are not carried. Nothing happens until the Partner taps Confirm; a typed "yes" never confirms. Confirm claims the proposal exactly once and the chat service calls the command service over HTTPS with the Partner's own Firebase token, so authorization, idempotency, audit and the busy and reconcile protocol are the command service's own; an unknown outcome is reconciled by status read and never retried under a new id. A payment takes the Partner's amount and the host obtains the per-charge split from the Payments screen's own draft routes (Auto-assign, review, the next projected charge as schema version 9). The tool is behind the `chat_commands` Terraform switch (`CHAT_COMMAND_URL`, default off); without it the tool is absent and the routes answer 404. Design and decisions: [R106 change note](https://github.com/welct0407/MW-Credit-App/blob/8ced324/Change%20Logs/CHANGE_NOTES_R106_CHAT_WRITES_2026-10-30.md); the prompt digest changes, so every thread opens a new history epoch on its first turn after the deploy.

PWA: on the Collection detail, directly under the amounts block and above the borrower note, a read-only card shows a headline, up to four points tagged by speaker (Borrower, Partner, Referrer, Other borrower, MW Credit, Other), a freshness line (`Updated 14:32 · last 3 days`: the time when generated today in Bangkok, otherwise the date) and a last-message line (speaker and time) with a Show more / Show less expander when there are more than two points (expanded state is kept per borrower while the page stays open).
