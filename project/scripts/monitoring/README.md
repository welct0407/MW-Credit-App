## Current dashboards (R089)

The five dashboards `mw-now`, `mw-pwa`, `mw-agent`, `mw-infra` and `mw-cost` are generated by `node project/scripts/monitoring/build-dashboards.cjs` (no dependencies) from one module per dashboard under `dashboards/` (`now.cjs`, `pwa.cjs`, `agent.cjs`, `infra.cjs`, `cost.cjs`) and the shared `lib.cjs` (grid, Cloud Monitoring URL template, state mappings, freshness fragments). `lift(dashboardFile, panelId)` copies a proven panel from the retired dashboards' last JSON (`dashboards/retired/`) byte for byte (exception, R090: Infrastructure 14 and 15, Metabase CPU and RAM, send one combined Railway call each instead of the four lifted calls, which Railway's API rate limit failed now and then); the builder only renumbers, repositions and retitles. Output goes to `infrastructure/grafana/dashboards/mw-{now,pwa,agent,infra,cost}.json`, which Terraform applies through the [Grafana runner](../../../infrastructure/grafana/README.md). `node project/scripts/monitoring/build-dashboards.cjs --check` verifies the committed JSON without writing. New selectors: `state-timeline.jq`, `scheduler-attempts.jq`, `ops-health.jq`, `gcp-status.jq`, `backup-age.jq`, `freshness.jq`, `sum-by-label.jq`, `sum-points.jq`, `cost-prior-azure.jq`, `gcp-by-service.jq` and `cloudrun-by-service.jq` (`turn-points.jq`, the conversation turn chart's selector, was removed with the Instagram conversation in R091). Tests: `node project/scripts/monitoring/test_build_dashboards.cjs` (unique IDs, titles, datasource UIDs, no grid overlap, link bar and tag, Asia/Bangkok), `python3 -B project/scripts/monitoring/test_dashboard_queries.py` (jq fixture tests of the new selectors against the generated JSON) and `test_debian_health.py` for the collector additions. `test_availability_queries.py` still reads only the old classic Performance JSON (known, unchanged until retirement). Update the [visual guide](../../Documents/Resource_Monitoring_Dashboard_Guide.md) in the same batch.

## Availability collectors

`debian-health.py` is installed independently at `/opt/mw-resource-monitoring/debian-health.py`; `mw-resource-health.service` uses the existing integration-agent Python virtual environment and mwagent identity. The matching systemd timer runs every two minutes. It reads existing private configuration in place and sends only numeric health states through the existing VM identity to GCP Monitoring. No credential copies or new public ports are needed. Installation consists of copying these three files to their respective `/opt/mw-resource-monitoring` and `/etc/systemd/system` paths, `systemctl daemon-reload`, then enabling the dedicated timer. Capture any existing copies before updates. Do not restart or invoke business jobs as part of installation.

`test_debian_health.py` checks timer semantics; `test_sql_uptime.py` and `test_hosting_health.py` check the SQL uptime and Hosting fields. The external webhook uptime check is owned by Google Cloud Monitoring, not either VM. No Azure scheduled probe is retained: VM-01 is not 24x7.

Rollback: disable/stop only `mw-resource-health.timer` and its service, remove only its dedicated files/units after preserving evidence. Existing provider metrics/data sources, workload jobs and historical monitoring samples are unaffected. GCP custom metric history may be retained after collector removal.

## Initial provisioning (already completed)

`Initialize-Azure.ps1` checks the signed-in tenant/subscription/account, creates a dedicated one-year service-principal secret and group-scoped read permissions. It refuses existing principals/credentials.

`Initialize-AzureVmControl.ps1` separately provisions the owner-approved single-VM control identity with only read, instanceView, start and deallocate permissions. It never runs a power operation and must not be replayed against the existing identity. `VmControl.Helpers.ps1` is retained as inactive preparation only; no dashboard calls it. Do not re-enable it without a new request and supported Grafana authenticated actions. Power-cycle testing is disruptive because VM-01 hosts the desktop/Codex session; do not use deallocation as an automated smoke test.

`Initialize-Gcp.ps1 -ApprovedKeyCreationException` is a security-sensitive, one-time procedure requiring owner authorization. It creates the dedicated monitoring identity/dataset, temporarily makes project-level exceptions for both key-creation constraints, creates one key outside Git, and restores inherited enforcement in `finally`. It refuses an existing key or local policy. Do not rerun for routine dashboard changes. If interrupted, inspect/restore project policies immediately and reconcile the existing identity/key; never automatically create another key.

Detailed GCP billing export and the Railway workspace token were configured in their authenticated web consoles. `Install-DataSources.ps1` installs only the three named Infinity sources and refuses existing UIDs. It never writes plaintext credentials into generated dashboards. `Monitoring.Common.ps1` (used by these helpers) reads the private path documented in the operating reference. No workload deployment, business database write or AppSheet change is part of these tools.

`worker-timing.jq` formats same-sample numeric worker timing values, rejects pagination and returns Unknown after six minutes.

### Metabase health group

`metabase_probes.py` uses liveness/readiness, a fixed saved SELECT 1 canary, the public chart shell/protected API guard, and the read-only Railway PITR status probe in `metabase_pitr.py`. It is deployed next to `debian-health.py`; the latter requires the module. Key storage is external and restricted; see the operating reference for IDs and rollback. `Initialize-MetabaseProbe.ps1` is a guarded one-time helper, not a deployment step. Run `test_metabase_probes.py` plus collector tests; `metabase-probe.jq`, `metabase-backup.jq` and `metabase-pitr.jq` are the Infrastructure 17 selectors.

The four Live tiles and PITR share rule `MW | Metabase component unhealthy` (`ffzb4act1o0zka`), whose canonical selector is `metabase-alert.jq`: one stable `component` label and binary `value` per tile; only fresh Down (0) or Degraded (2) yields 1; Unknown, Paused, missing or older-than-six-minute telemetry yields 0. The Daily and Weekly backups share `MW | Metabase scheduled backup unhealthy` (`mw-metabase-backup-health`), using `metabase-backup-alert.jq` against Railway's scheduled-backup list. Both rules use Last reduction, threshold above 0, 2-minute evaluation, 4-minute pending period, KeepLast on no-data/error, and direct `MW Performance IRM` contact. The rules are Terraform-owned in `infrastructure/grafana/owned-services.tf.json`; change them there, then update the guide and operating reference.
