# Official API conversation intake

Owner authorized scheduled API reads on 21 September 2026. Browser automation is prohibited, following the owner's prior account restriction. No browser is used. Group sending remains untested and is not enabled.

Live read evidence: the conversation-list endpoint returned 15 conversations, 12 with three participants, and messages for 13 conversations. Individual group-object/history endpoints returned HTTP 400; the working route is account conversations with expanded message fields. This is observed account behavior, not a claim of general vendor support.

`conversation-poll` runs every five minutes after the previous run finishes, under `mw-conversation-poll.timer`. Every scan discovers current conversations and selects those containing a currently AI-enabled borrower, including groups created that day. It requests 100 messages per page and follows both outer conversation pagination and nested message cursors. Borrower images and authorized Lisa-forwarded images are eligible; other participants and non-image content are ignored. Images feed the existing receipt job table and worker; receipt validation, current borrower identity, bank aliases, duplicate checks and Partner IG-first/email-fallback notices remain shared.

The first activation establishes a timezone-aware cutoff. Each successful conversation check stores a watermark with a five-minute overlap; message IDs make repeat scans harmless. Message and image reservations commit with that watermark. The same message/attachment job key is used by webhook intake. Polled events have their own provenance table and never become signed webhook evidence or refresh the IG delivery window.

New conversations start at the existing activation cutoff; existing ones start at their saved watermark minus the overlap. Read until reaching that boundary or exhausting accessible history. The working continuation is `messages.limit(100).after(cursor){...}` on the account conversation-list endpoint, selecting only the original conversation from the result. Returned group `/messages` URLs still fail on this account and are not followed. Live probes on 25 September confirmed that a populated continuation returns older messages, while an exhausted expansion can omit `messages` entirely even though the preceding page had a `next` link. A present conversation with an omitted expansion is empty; a disappeared conversation, malformed page, invalid/repeated cursor or changed ordering is held.

At most ten message pages are read per conversation per scan. If history cannot be completed within that bound, or participants/attachments are incomplete, that conversation's transaction and cursor stay unchanged. Other conversations continue. The command reports aggregate counts plus at most twenty hashed conversation keys/fixed error reasons and exits with status 2 if any conversation failed, so systemd records partial failure. The next scheduled run retries from the preserved cursor. No additional alert delivery is implemented. A manual API backfill needs explicit historical scope; existing deduplication prevents reprocessing captured images. The poller does not write payments; the downstream receipt policy controls automatic ordinary posting and reviewer/manual cases.

Deploy with the reviewed runtime updater, then `scripts/activate-conversation-poll.sh`. Inspect `systemctl status mw-conversation-poll.timer` and `journalctl -u mw-conversation-poll.service`; successful output contains aggregate counts only. Roll back by stopping/disabling this timer and restoring the recorded config/package backup without replacing current journals. The webhook remains active independently.

For an explicitly owner-requested same-day group backfill, use `conversation-poll --date YYYY-MM-DD` with the usual config/catalogue arguments. This mode reads from Bangkok midnight, restricts to group conversations, preserves normal polling watermarks/cutoffs, and queues only unseen images through the same receipt workflow. It does not reopen terminal receipt jobs or replay existing reviews. Earlier dates are rejected. A history gap holds only the affected group rather than skipping its messages.
