# Partner receipt review

Owner authority: 21 September 2026. Use the same queue for group API polling and signed webhook receipts. Do not replay historical receipts when enabling review. Valid new receipts are checked against manually recorded Payments, then proposed with borrower, amount, receipt date/time to the minute, receiving account and proposed action. Proposals retain current loan/charge facts; changed facts invalidate approval.

Each Partner receives the request in their current preferred language, Instagram first. A signed inbound message must directly reply to that exact accepted outbound message ID, from its recorded recipient, with fresh unique Partner identity and IG integration enabled. `yes`, `approve`, `approved`, `อนุมัติ` approve after trimming and case folding. Any other direct reply rejects. Unlinked messages cannot decide anything. First valid decision from either Partner wins; repeated replies cannot execute twice. No reply remains pending for up to 24 hours, then expires. Email fallback informs only; email replies are not an approval channel.

All potential loan closures and amounts above the current latest unpaid charge are manual handling, as explicitly requested. Approval of those requests records MANUAL_REQUIRED and informs Partners; it never invokes Loan Close or records an overpayment. No database migration was requested or performed. If multiple loans/charges make a proposal uncertain, hold for manual review.

For an ordinary payment, approval triggers fresh borrower/account/Partner validation, a current manual-payment check, and an exact proposal/fact comparison. Only then commit POSTING and call the existing PROD OLTP Payments API once using Lump Sum, the receipt amount/date/time, receiving account and approving Partner Login Email. Existing DB processing owns allocations/repayments. Verify Posted status, amount, borrower, bank reference, account, minute and summed repayments. An uncertain Add is never retried; subsequent runs only read back the deterministic payment key. Success notices go to Partners, never the group.

This is not atomic exclusion against concurrent manual entry between the final read and API call. Existing DB validation applies, and unknown outcomes stop for reconciliation. The owner declined a database change. Group sending and browser automation remain disabled. General data writes remain disabled; `partner_review_execution_enabled` gates only the scoped review executor.

Deployment: reviewed updater backs up package/config and consistent journals. Confirm a successful Cloud SQL backup before `scripts/activate-partner-review.sh BACKUP_ID`; it preserves a new review cutoff and restarts the webhook to capture reply links. Roll back by setting partner_review_enabled and partner_review_execution_enabled false, restoring prior package/config if needed, and retaining all journals. Never restore old journals over accepted messages or posted payments. No synthetic financial test is sent to production.
