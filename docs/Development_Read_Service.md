# Native read service

Current read implementation serves authenticated Borrowers, related loans and Collection/charge data. Other business reads, writes and receipt access are composed through the command/business runtime.

## Source ownership

- services/api/read-handler.mjs: route validation and request handling.
- services/api/borrower-read-store.mjs: bounded SQL reads.
- services/api/read-access.mjs and services/lib/firebase-claims.mjs: identity/access policy.
- services/production/business-server.mjs and business-runtime.mjs: composition for DEV and PROD, selected by APP_ENV.
- services/production/business-config.mjs and services/lib/connection-guard.mjs: fixed environment/target guards.
- services/payment-command/handler.mjs: additional operational/management route families.
- apps/pwa/src/live-main.tsx: live application entry.

DEV and PROD run the same business server; APP_ENV selects the database, identities, origins and capability policy. The DEV capability policy lists the owner only. Exact runtime configuration comes from the owning infrastructure stack and service loader; do not copy old checkpoint settings.

## Data and access

Validate Firebase identity and current Partner membership/capabilities. Use explicit environment origins/database identities and restricted database roles. Shared Google sign-in does not make DEV/PROD routes interchangeable.

Borrower visibility excludes only Hidden Flag=true; false/null remain eligible under the source contract. SQL supplies governed balances and financial calculations. Paging/search are bounded and cursor-bound; one page is not a complete portfolio.

Borrower detail Upcoming Charges reuses Collection's five-date forecast, date detail and paging for the selected visible borrower, including borrowers with only future charges. Borrower-scoped upcoming reads use the visible-borrower boundary; Collection-scoped reads retain their existing Collection membership check. Both use the existing forecast SQL, cursor binding and freshness checks. Viewing upcoming rows is read-only and does not submit borrower changes.

Collection preserves status grouping and orders borrower names ascending within each group with stable id ties. Loan-related charges/payments order by business date descending, null dates last, then id ascending. Both use matching scoped/versioned cursor boundaries; existing eligibility, balances and authorization remain unchanged.

DEV and released R059 PROD bulk reads use `GET /api/offline-dataset?domain=records|collection|cash|management` and recipient-scoped `GET /api/notifications/offline-dataset`. They retain authenticated membership/capabilities, existing read DTOs and SQL calculations in read-only repeatable-read transactions. One shared bulk connection slot preserves foreground SQL capacity; cancellation stops abandoned preparation. Cash coverage follows the existing recent-statement provider. Released R059 enables main-domain routes in production composition and recipient datasets when existing notifications are enabled. Deployment/artifact and recovery facts are recorded in the PM environment inventory and existing R059 promotion record.

Protocol 2 uses `protocol=2` with an optional `cursor` on both dataset routes and splits preparation into bounded chunks. Protocol 1 is retired; both dataset routes require protocol=2 or 3. Traversal cursors bind actor, domain and business day; startedAt identifies traversal start, and asOf is read metadata; the traversal is not one global MVCC snapshot across requests. The PWA persists partial stages and resumes their cursor using local read-revision/cursor compare-and-swap. Focus/reconnect resumes work; a local applied mutation restarts that revision. Prior complete bundles remain available until every new page commits atomically.

After initial protocol-2 completion, protocol 3 uses read-only POSTs on the same routes with cursor/need/sourceVersion bodies. Deterministic per-domain logical-page caps keep manifest/need replays identical, with a between-page byte boundary and no elapsed-time cutoff in protocol 3. Bounded content-hash manifests transfer values only for missing hashes; canonical hashing ignores asOf metadata and can index an existing complete bundle. Main domains use actor/day-scoped source fingerprints to skip unchanged providers (R078: per domain, `count(*)` plus `sum(hashtextextended(primary key || ':' || xmin))` with no ORDER BY, one scan shared by the domains of a poll), validating traversal source at start/end. Notifications always scan protected recipient manifests with sourceVersion=null; they have no cheap source gate or universal snapshot claim.

R078 (offline sync efficiency; released to DEV and PROD on 19 October 2026, with V97 and the V98 read grant) keeps protocol 3 as the transport and adds, version tag `business-offline-v5` (R078 introduced `v4`; R097 moved it to `v5` for the Collection prepaid fields; every installed client walks once after each such deploy):

- **Pages and headers.** Deterministic page caps are records 32, collection 2, cash 16, management 8. The preflight answers `Access-Control-Max-Age: 7200`. Each domain's fingerprint covers its own tables (cash also includes Borrowers; records hash Daily Analytics by content without "Generated At" over Snapshot Date from the Bangkok date minus 31 days, and Statistics as ("Row ID","Statistics ID")), so the hourly analytics job no longer re-walks records or collection.
- **Poll.** A body flag `versions:true` returns the domain versions in one request: an unchanged poll is 2 requests (was 5).
- **Change cursor (`since`, v4 delta).** Every response that starts a bundle carries `changes` {seq, xmin, businessDate}, read in the same repeatable-read snapshot as the providers. It comes from `public.pwa_row_changes` (V97, see [database README](../database/README.md)); when the table is missing or unreadable the field is absent and the domain walks. A records request carrying `since` and rows changed since it gets a `schemaVersion` 4 delta: upsert/remove patches for the affected borrowers' rows (details, lists, loan-related, drafts, history, months), with `loanList` and the dashboard re-read whole, `paymentMonths` replaced whole, and the same-snapshot fingerprint. The fan-out follows the dependency audit on `readRecordsTargeted` (referrers, allocation loan labels, loan-related of re-read payments). The fingerprint stays the authority: unchanged needs an equal fingerprint; log rows absent with a different fingerprint, a missing row, a `*` TRUNCATE marker, a cursor gap, a moved row (owner, target or charge set changed; the log has no old values), the limits (loans, charges, payments, referees, 4 x 2048 values, a 5 s budget) or any error walk as protocol 3. Upserts name the walk's order (id, "Row ID" COLLATE "C") and the client re-sorts. A 400 steps `since` down per path.
- **Day change (request level 4, `dates`).** A records, cash or management check whose cursor is from an earlier Bangkok date (1 to 14 days) is answered with `dayChange`: date-independent keys (`offlineDayKeys`) stay on the client with their business date moved; a resumable day plan re-reads the others (`records@day:<from>`). Records combines row changes since the cursor; cash walks on any change; management accepts only changes to tables that feed re-read keys. With an empty log the sources must hash to the client's version at its own date. Any error, gap, marker, moved row, unlisted key or kept key with another date walks. At level 4 a `businessDate` equal to the envelope's is left out of content hashes and hydrated by the client; cash and management bundles send their cursor too. A test-only `pinOfflineBusinessDate` lets lab tests cross a month end and is refused on Cloud Run (`K_SERVICE`).
- **Row deltas for collection and cash (request level 5, `rowDeltas`).** Collection and cash answer from the change log as patches, with a new `replaceWhere` patch mode that replaces the rows of a scope. Collection scope is per borrower, including borrowers of allocated or repaid charges; it walks on a Cash Accounts change, an unmapped table, a borrower hidden now, more than 8 borrowers or a missing row. Cash scope is per account-day from max(date, window start); Borrowers and Partners map to their statement days; it walks on Cash Accounts, Cash Holders, Cash Statement Context, r008, a missing ledger row, more than 30 account-days (`CASH_ACCOUNT_DAY_LIMIT`) or `TARGETED_LIMITS`. A rename or hide/unhide may be a delta when it stays byte-equal to a walk and the reconciliation matches; the client walks on `deltaMovesRows` or `deltaScopeMoves`. A 400 steps the request level down 5, 4, 3. The fingerprint stays the authority.
- **Inline values (request level 6, `inlineValues`).** Every schemaVersion 4 response carries its referenced values inline, so a delta answers in one request without the manifest-and-need round trip; the later day-change chunks keep the old path. Above `INLINE_VALUE_BYTES` (512 KB) or `INLINE_VALUE_COUNT` (2048) the response falls back to manifest plus need; the manifest is identical either way. The client hash-checks each inline value and sends a bad one to need. A 400 steps the level down 6, 5, 4, 3 (records at level 5 goes straight to 3).
- **Full sync.** `full` forces a protocol 3 walk of every domain (no source version, cursor or versions shortcut) and restarts a walk in flight.
- **Reconcile.** `POST offline-dataset {reconcile, sourceVersion, digests}`: a version that differs answers `stale`; otherwise the server walks the domain in-process in one snapshot, patches it like a client and compares per-key SHA-256 digests (shared module `services/lib/offline-dataset-digest.mjs`, used by server and PWA). Result `match` or `mismatch` (the differing key names); a version that moved answers `changed`, never a mismatch. Cached per actor, day and version for 12 h (64 entries), 40 s budget, one log line `offline_reconcile {domain, result, keys, ms}`.
- **Payment draft plan (R110).** `POST /api/payment-drafts/:borrower/plan` with `{amountReceived, purpose}` returns the pay-forward plan (V121 `pwa_pay_forward_plan_v1`): allocation lines, charges to book or raise and the paid-through date per loan. Auto-assign returns a `remainder` object (amount left after due charges, with the plan for the chosen purpose); with no purpose chosen Review is blocked. Review answers 409 `plan_changed` when the forecast or a balance moved. The Collection read adds `prepaidPaymentDate` and the loan read adds `paidThrough`.
- **Auth floor.** Reads verify the token without a revocation check; writes and unknown routes are checked (owner decision 19 October 2026). The command pool idles 10 minutes with keepalive.

Visible polling every 60 seconds and reconnect/focus check for changes from other users. Complete data and checkpoints commit together under original local mutation revision, expected cursor and prior-base guards; response-cache epoch is separate. Existing complete data remains visible while updating or failed. An unavailable initial cache epoch disables caching/fallback for that read while allowing a valid online response to succeed. Without a valid fallback, preserve the actual429/5xx response, body and request reference; warm fallback and authorization/abort/revision guards remain intact. Downloads never replace pending requests/drafts, and mounted view refresh preserves dirty edits.

The PWA prepares complete owner-scoped bundles and authorized receipt images separately from the response-cache LRU, enabling local search/paging and unvisited offline views. Foreground reads take priority; atomic replacement preserves prior complete data on storage failure. The header shows actual preparation progress and page-scoped refresh failures. Financial close/correction/auto-assignment/review and command-status reads remain online. Read-only Collection Note baseline can refresh from prepared data when not editing, busy, blocked or carrying a pending request; dirty text remains protected. Note autosave behavior is unchanged, and the reported note concern is not claimed fixed.

Authentication state uses the Firebase SDK. Do not copy tokens into custom storage/logs/URLs. Clear or reject stale-session results and preserve denied access rather than granting permissions automatically. Offline viewed snapshots follow the current bounded cache policy; they do not authorize posting.
