# Environment-bound notification and canonical job workers

Shared by DEV and PROD (renamed from `modules/dev-workers`; module addresses are unchanged). R053 uses two private Cloud Run services and separate IAM/SQL identities. DEV and PROD roots call this module from `workers.tf` with explicit environment binding (default DEV). Each root owns only its separate worker resources; neither alters the shared SQL instance. The existing DEV state alone owns shared Scheduler API enablement. `enabled=false` creates nothing. Enrollment (`enabled=true`, no image) creates fourteen prerequisites only. Runtime requires a reviewed immutable image from the matching environment repository and explicit numeric notification-policy/VAPID versions. Worker activation and schedule activation are independent flags, all false by default.

| Worker | Identity prefix | Fixed POST route | Bangkok schedule |
| --- | --- | --- | --- |
| Notification dispatcher | `mw-credit-app-notify-dev` | `/internal/dispatch` | Every minute |
| Canonical jobs | `mw-credit-app-jobs-dev` | `/internal/jobs/daily-charges` | 00:05 daily |
| Canonical jobs | Same jobs identity | `/internal/jobs/recent-analytics` | Hourly at minute 0 |

The caller `mw-credit-app-scheduler-dev` receives only service-scoped `run.invoker` on these workers. Optional `command_dispatch_enabled` adds only `mw-credit-app-command-dev` as an invoker of the notification service, never jobs. Optional `chat_dispatch_enabled` (R090 batch 2, default off) does the same for the chat identity `mw-credit-app-chat-<env>`: `run.invoker` on notify only, and its email and unique id pinned in `WORKER_CALLER_SUBJECTS_JSON` through `chat_caller`, which the owning stack passes from its chat service account; the chat service then gets the three `NOTIFICATION_DISPATCH_*` keys. Optional `jobs_dispatch_enabled` (default off, requires the enabled notify and jobs workers) does the same for the module's own jobs identity and gives the jobs worker the three wake keys. The notify worker code must list the chat and jobs identities among its accepted callers before either flag is turned on. Notify accepts network ingress with Cloud Run IAM enforced, allowing direct command calls without a new VPC; jobs retains internal-only ingress. Neither has anonymous invocation. Application code additionally verifies Google's OIDC token against the exact caller, its pinned service-account unique id (`WORKER_CALLER_SUBJECTS_JSON`: the scheduler for both workers, plus the command identity on notify when direct dispatch is enabled) and the audience. No integration-agent identity or grant is configured in this DEV module; the verified existing PROD VM identity must not gain DEV access merely for implementation. The documented deterministic default URL `https://SERVICE_NAME-PROJECT_NUMBER.REGION.run.app` supplies the audience without a Terraform self-reference ([Cloud Run HTTPS invocation](https://docs.cloud.google.com/run/docs/triggering/https-request)). Same-project Scheduler calls to default URLs are accepted as internal ([ingress documentation](https://docs.cloud.google.com/run/docs/securing/ingress)).

Both workers always use minimum zero and request-based CPU, including when notification dispatch is enabled. There is no LISTEN connection or continuously running dispatcher. Authorized backend callers request bounded dispatch after commit; the minute Scheduler tick recovers missed calls and pending retries. The dispatcher pool remains bounded to two connections per instance. Region is `asia-southeast1`; both services retain maximum one configured instance/concurrent HTTP request, 1 CPU/512MiB and a 120-second request timeout. Durable leases remain authoritative during transient revision overlap. Scheduler deadline is 150 seconds. Jobs have five retries bounded to ten minutes, with database boundary checks/idempotency authoritative; a previous day is never silently replayed. No queue, anonymous invoker, database-wide setting, bucket grant or VAPID access for jobs is added.

Dispatcher receives the existing Firebase user-read custom role and access only to the existing DEV VAPID container and new DEV notification-policy container. Payloads never enter Terraform. Reuse VAPID version 1 only after validating its P-256 pair privately; do not rotate it to fill missing local files. The approved subject is `mailto:welct0407@mw-credit.com`. Command enrollment optionally receives the policy and public key, never VAPID private access. Jobs receives neither notification secret.
