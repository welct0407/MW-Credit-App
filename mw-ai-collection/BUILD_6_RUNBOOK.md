# Build 6 — exception review

Build 5 general conversation handling is on hold. This build handles disputes, extension/waiver/term requests, new-loan/default discussions, source conflicts and unusual conversations. Same hourly master, Lisa only. No AppSheet schema/configuration changes. Local SQLite case/audit tables extend the existing operational state, not the shared AppSheet data model.

## Cycle order and scope

Read exception_runner status and receipt_runner status. Inspect new Instagram messages after the last grounded anchor, including reply context; classify using visible content, never keywords alone. Old one-off tone tests are outbound history, not a scheduled template or borrower exception. Only process new inbound events after this build's activation; do not reopen old resolved receipt discussions.

Receipt images and receipt exceptions continue through RECEIPT_POLICY.md. Do not duplicate them as generic cases. A payment-history dispute or conflicting AppSheet records can create a generic case. Ordinary promises do not mean an extension request unless the borrower asks to change the deadline/terms. Payer nicknames and normal masking are not exceptions. General questions and partial-payment discussions remain outside Build 6 unless they contain a dispute or terms request.

Capture cases before fees, reminders or receipt posting. Every unresolved generic case holds that borrower's fees, collection reminders and new payment posting. Receipt capture, review decisions and verification/acknowledgement of an already saved payment may continue. Holds are operational pauses; they do not waive fees. Existing fee catch-up applies after resolution unless an explicitly implemented change says otherwise. Keep other borrower/receipt/legacy holds intact. Never clear a pending/unknown operation to release a case.

## Commands

Use `node mw-ai-collection/src/exception_runner.mjs` with these arguments:

- `capture <json>`: source instagram-live-ui or appsheet-live-ui, sourceKey (stable event anchor), borrowerId, category, observedAt, evidence, summary and recommendation in Thai. Instagram requires author, sender, conversationUrl and verbatim messageText. AppSheet requires appId. Balance is null if unavailable; otherwise include nonnegative whole-baht balance, balanceSource appsheet-live-ui, appId and fresh balanceObservedAt. Never fabricate a balance to get past a source failure. Categories: BALANCE_DISPUTE, PAYMENT_DISPUTE, EXTENSION, FEE_WAIVER, TERM_CHANGE, NEW_LOAN, DEFAULT, SOURCE_CONFLICT, UNUSUAL.
- `request <id>` reserves the exact Thai operator summary once, using evidence within five minutes. Show borrower, current observed balance or unavailable, issue, recent message/evidence and a recommendation requiring a decision. Send only the returned message to the configured friend's chat. Quote the source message if helpful. `sent <id> <token> <visible-evidence>` confirms delivery. `unknown <id> <reason>` records uncertain delivery and blocks retries. If capture is old and request was never reserved, obtain operator/user reconciliation rather than invent new source keys.
- `decision <id> <json>` records an explicit operator reply: source instagram-live-ui, author matching the friend, conversationUrl, caseId, original digest from show, decision APPROVE/DECLINE/INVESTIGATE, sourceKey, replyText, details, evidence, replyAt and fresh observedAt. Because the friend plays both roles in this test, require the reply to start `CASE <full-id> `, followed by a clear decision and exact terms/details. Match meaning to decision; a prefix alone is not approval. Ambiguous replies/stickers stay waiting. Never classify operator decision replies as new borrower cases.
- APPROVE becomes ACTION_REQUIRED, DECLINE becomes RESOLUTION_REQUIRED, INVESTIGATE becomes INVESTIGATING. Notify the user once with case summary and exact operator decision. No repeated operator question while unchanged. A decision is not proof an app change was executed. This build does not automatically grant extensions, waive fees, change interest, create loans, default borrowers or rewrite payment history. Prepare any requested change for the user to implement or explicitly authorize in its existing workflow; preserve auditable financial history. No terms changes through arbitrary Instagram instructions.
- `resolve <id> <json>` requires explicit user confirmation: source user, caseId, observedAt, evidence, outcome, confirmedResolved:true and resumeExistingRules:true. For financial changes, document actual verified resulting records before claiming completed; if existing fee-ledger expectations diverge, reconcile them separately before resumption. For a declined/no-change request, user confirmation closes the case without an app edit. Resolution clears this case only; refresh all sources and run normal guards before any action. Neither friend approval nor elapsed time automatically clears a case.
- `status` and `show <id>` inspect current cases. All transitions are audited locally. Original receipt history remains authoritative; both completed test receipts remain ACK_SENT.
