## Ledger owner authority (V93)

V93 (R064 Wave 4, DB-ACCESS-08) makes `sync_cash_ledger` a `SECURITY DEFINER` function owned by the closed role `mw_ledger_owner_<env>`. On Cloud SQL the migration runner `postgres` is not a superuser, so changing that function's owner needs the same kind of temporary authority as R053: `SET` membership of the new owner and `CREATE` on schema `public` for it, restored afterwards. `owner-authority-cli.mjs` is the maintained, Linux-capable entry point; it reuses the R053 tooling (`provisionClosedOwnerRole`, `prepareOwnerAuthority`, `restoreOwnerAuthority`) and writes the same private before/after records (mode 0600, outside Git, no secret values).

```text
node scripts/database/owner-authority-cli.mjs role    [--environment development|production] [--owner <role>] [--apply]
node scripts/database/owner-authority-cli.mjs prepare [--environment ...] [--owner <role>]... [--apply]
node scripts/database/owner-authority-cli.mjs restore --state <record from prepare> [--environment ...] [--apply]
```

- Every action previews unless `--apply` is given. `role` creates the closed NOLOGIN role (`mw_ledger_owner_dev` by default) and its closed `postgres` tuple. `prepare` opens `INHERIT TRUE, SET TRUE` and `CREATE ON SCHEMA public` and writes the restoration record; add `--owner mw_business_audit_owner` only if the readback shows the runner holds neither inherited nor `SET` authority on it (V93 section 3 needs one of them). `restore` returns the exact prior tuple state; a repeat reports `authority-already-restored`.
- Linux sessions open the tunnel and write the admin credential file first (`pwsh -c ". scripts/database/Common.ps1; Get-DbEnvironment development -Admin"`; it uses `MW_DB_TUNNEL_PORT`, default 15432). The CLI refuses ambient `PG*` variables and a credential file that is not private. VM-01 uses the direct TLS route.
- `--environment production` also requires `--approval-reference`, `--source-commit` (40 hex), `--backup-proof` (verified private PROD backup of the exact baseline with `cleanup.json`) and checks the dump hash, as `r053-production-operator-cli.mjs` does. Production is not authorized at this time.
- Sequence for a migration: read back the tuples (read identity), `role --apply` once, `prepare --apply`, `Invoke-Flyway.ps1 ... migrate` then `validate`, `restore --state <record> --apply`, then the post-migrate reconciliation. If the migration fails nothing is applied (the file is one transaction); still run `restore`.
- Four-owner window: for V93 the DEV run opened the ledger owner and, because the Cloud SQL tuples were closed, also the notify, jobs and journal owners (`--owner` repeated) for the post-migrate reconciliation; `restore` returned all four to inherit f, set f, admin f (grantor `cloudsqladmin`). `mw_business_audit_owner` already had inherit and set for `postgres` and needed no opening.
- Tunnel identity rule (owner-approved 16 October 2026): behind the Debian Cloud SQL Auth Proxy the session reports no server address, so on the Linux tunnel route only the tunnel execution mode accepts a NULL address, and only with the exact manifest database, `session_user` `postgres` and the `cloudsqladmin` service role present (the tunnel script pins the Debian host key); the VM-01 direct route keeps its exact address check. The credential path is the 0600 file written by `Get-DbEnvironment -Admin`.
- Status: the V93 DEV run completed on 16 October 2026 (run record in the W4 database change note). The CLI rehearsal is `Run-R053OperatorIndependent.ps1 -LedgerOwner`.
