# Shared PostgreSQL development

The repository root owns migrations, database runners/tests and CI; `project/` owns release coordination. Current consumers are native PWA/API/workers, Debian integration and governed reporting. AppSheet editor, RC and parity steps are retired.

## Current state

- One Cloud SQL instance (`mw-credit-pg-20261017`, PostgreSQL 18) holds the business databases `loan_manager_dev` and `loan_manager_prod`; the integration agent keeps its journals in the separate `mw_agent` database on the same instance. Project, instance and credentials: [Environment inventory](../project/Documents/Environment_Inventory.md). A code move does not authorize a database change, service activation or financial write.
- Deployed Flyway version, per environment, with the verification date: the Flyway row of the [Environment inventory](../project/Documents/Environment_Inventory.md). That row is the only place that states it; the newest file in `database/migrations/` is the candidate, not the deployed state.
- Shared-instance changes can affect both environments. Production changes need a verified restorable backup and the guarded runner (see [Each change](#each-change)).
- Next page to read for a SQL change: [Each change](#each-change) below; run `pwsh -NoProfile -File scripts/database/Test-CI.ps1` before publication.
- Tool locations: project tooling finds this checkout through `MW_CREDIT_APP_ROOT` when it is not adjacent (`project/scripts/database_location.py`, `project/scripts/database-location.mjs`). `MW_DB_TOOL_ROOT` selects an existing supported tool installation (`scripts/database/Common.ps1`). Private paths and resource names that contain "AppSheet" remain compatibility identifiers; they do not change ownership or authorize moving credentials.

Choose new versions from the actual migration directory and pending work, never from a stale document.

Use existing Secret Manager/unattended access procedures. Keep credentials/backups outside Git. New tables/columns and production changes require scoped owner authorization; reuse existing explicit approval. Never clean/repair, alter applied checksums or create competing history.

## Naming and identifiers

- Legacy names stay as they are: quoted tables and columns such as `"Payments"` and `"Row ID"`, `appsheet_ref_*` constraints and the V89/V90 IAM identities are never renamed. GUC guards remain depth- and owner-checked.
- New objects use snake_case; PWA tables and RPCs in `public` carry the `pwa_` prefix, while audit and monitoring objects live in the `agent_audit` and `monitoring` schemas. RPCs end in `_vN`; bump `N` only when the signature changes.
- Request ids are client-generated UUIDs; the database never invents one for a client command.
- Derived ids use one documented derivation each. Agent receipt request id: `receiptRequestId` in `services/agent-receipts/contract.mjs` (SHA-256 of `['mw-credit-agent-receipt-v1', environment, reviewId]`, first 16 bytes, UUID v4 bits). Receipt link id: `uuid5(NAMESPACE_URL, 'mw-receipt:' + receipt_id + ':' + payment_id)` in `integration-agent/src/mw_integration_agent/receipt_projection.py`. Advisory-lock key: `pwa_lock_key_v1` (next bullet).
- `pwa_lock_key_v1(kind, target)` is the one derivation of a per-database advisory-lock key (`hashtextextended(kind || ':' || target, 0)`); `services/business/borrowers.mjs` calls it, and `Test-StatementBatch.sql` asserts it equals the inline form. V94 (DB-LOCK-03) moved every SQL body to the function (ten routines; the two-integer request-id locks stay), retired the `pwa_job_runs` lease state (DB-LOCK-02; `pwa_job_run_v1` is pending to completed in one UPDATE) and made a reviewer payment-input edit fail with SQLSTATE 42501 and a named reason.
- Triggers on `"Payments"`, `"Loans"`, `"Charges"` and `"Repayments"` fire in name order; the blank-reference normalizer is named `a000_blank_refs` so it fires first. `scripts/database/Test-TriggerOrder.sql` holds the firing-order snapshot, so add or rename a trigger there on purpose.
- `pg_stat_statements` is created by V93 in schema `monitoring` (Cloud SQL preloads the library; no flag is needed).

## Each change

For changes to migrations or database tests/runners, run `pwsh -NoProfile -File scripts/database/Test-CI.ps1` before publication, in addition to affected feature tests. This is the same entry point used by GitHub Actions and rebuilds an empty disposable database through the latest migration. Keep older fixtures compatible with new required fields: `Test-CashAccountFixtures.sql` supplies synthetic accounts, and each source insert explicitly selects its account. Do not weaken production guards or top up a live balance to repair CI. Branch/PR builds remain enabled; release tags reuse the tested commit without a duplicate workflow run, Markdown changes do not trigger the workflow, and its `changes` job skips the rebuild groups when they already passed on this commit (pushed to another branch), a parent or an earlier head with identical database inputs (`scripts/ci/reuse-evidence.mjs`; the step summary links the run with the evidence).

These steps apply to SQL changes, not app-only or documentation-only edits. Work in coherent migration batches: run the relevant checks on the completed candidate and rerun only where later edits or changed dependencies invalidate them. Reuse applicable passing evidence under the [release workflow](../project/Documents/Rules/PWA_Orchestration.md#evidence-reuse-and-exact-candidate-identity); do not reinstall tools or rebuild a disposable database after every intermediate edit. Migration-chain checks below remain required for a changed migration candidate.

Generated reference: `database/current/public-functions.sql` holds the current body of every `public` function (`pg_dump --schema-only` of a fresh rebuild, normalized by `Normalize-Schema.ps1 -FunctionsOnly`). `Test-CI.ps1` and the migrations route fail when the committed copy differs from a rebuild. After a migration that changes a function, regenerate it with `MW_WRITE_PUBLIC_FUNCTIONS=1 pwsh -NoProfile -File scripts/database/Update-PublicFunctions.ps1` (or `-Write`) using the toolchain PostgreSQL major, and commit the result with the migration.

Adding a migration needs no edit to tests or tooling. A test that migrates to the head reads it with `migrationHead()` from [`tests/migration-head.mjs`](../tests/migration-head.mjs), and `Backup-ProductionPromotion.py` accepts `--expected-version` baselines up to the checkout's latest migration (the live history must still match exactly). Literal versions in tests name fixed historical baselines, such as V92 or V93, or deliberate upgrade targets like the Phase5 `-target=96`. When reviewing, check that a test does not hard-code the current head.

1. Create the next unused monotonically increasing `V<version>__description.sql` after all applied/reserved versions. Include functions/triggers in versioned migrations too. Preserve text Row IDs and case. Review transaction behavior, locks, dependencies and forward-fix SQL. Prefer **expand/contract**: additions first, old/new app compatibility during cutover/rollback, destructive removal in a later tested release. Include compatibility with affected current consumers and rollback versions in relevant tests. Do not include `BEGIN`/`COMMIT` unnecessarily; Flyway normally wraps PostgreSQL migrations in a transaction. Nontransactional operations require separate documented handling.
2. Use the migration-chain proof from `Test-CI.ps1`; run `scripts/database/Test-Migrations.ps1` separately only when that proof is unavailable/invalidated. It starts a temporary, empty PostgreSQL server bound only to loopback, rebuilds migrations, validates, checks repeat execution is a no-op and verifies checksum mutation is rejected. It stops the server and leaves diagnostic files outside Git. No production data is used.
3. Apply in development with `Invoke-Flyway.ps1 -Environment development -Command migrate`, then `validate`. Test affected native PWA/API/agent/worker flows. Cover changed calculations, refs, permissions, trigger-generated results after commit and financial reconciliation; record results and any required owner acceptance.
4. Update the Markdown change log and model documents when applicable; commit and push the exact intended files. CI rebuilds against disposable PostgreSQL, never Cloud SQL.
5. From the clean tested commit, run `New-Release.ps1 -ValidationReference 'path or link to accepted test evidence'` before later migrations advance DEV. This requires development validation and no pending/invalid migrations, and writes a release manifest outside Git. A reference must describe actual completed validation, not a placeholder. Pin this commit/manifest and target version in the frozen release package, retaining a sanitized manifest/hash record in Git. Later documentation commits do not replace the deployment commit. The runner uses the complete migration set in that checkout: every pending migration through its target must be in the approved batch or an explicitly approved prerequisite; it does not select migrations by R-number.
6. Before promotion, compare current production schema with the expected pre-release schema (export via `Export-Schema.ps1`; inspect drift). Verify a restorable backup, review migration files and application dependencies, and obtain explicit owner approval. Flyway `validate` checks migration history/checksums, **not** arbitrary live-schema drift or business correctness.
7. Promote the same clean commit:

```powershell
./scripts/database/Invoke-Flyway.ps1 -Environment production -Command migrate `
  -ReleaseFile '<private-root>/flyway/release-COMMIT.json' `
  -ApprovalReference 'actual owner approval for this release' `
  -BackupReference 'verified Cloud SQL backup or restore point'
./scripts/database/Invoke-Flyway.ps1 -Environment production -Command validate
```

The runner rejects mismatched commits/hashes, dirty checkouts and missing approval/backup references. The grouped-transaction guard (`Production-Transaction.ps1`) takes its scope from the tested release manifest: the pending set must be exactly every manifest migration above the baseline through the target, contiguous and once each, with matching hashes. There is no per-release list of hops to edit; `Test-ProductionTransactionGuards.ps1` covers the rule generically. These are operator safeguards, not an authorization service: the agent must verify the referenced evidence. No push triggers production deployment. Use a clean checkout of the pinned commit when the working branch has advanced; do not bypass manifest checks or disturb later DEV work. After promotion verify SQL history/schema and affected app workflows against the frozen package, not current DEV; capture results and update the release checklist/change log. Failed migrations require investigation, not automatic `repair` or retries of financial backfills.


## Recovery and delivery

Prefer compatible additive migrations before dependent API/worker delivery. An app rollback does not undo SQL or financial writes. Use a forward fix or separately authorized verified restore; preserve later transactions. Follow the project release recovery runbook. No app-only/documentation-only migration or database backup is required.

Use one promotion record and the guarded runner manifest. Existing validated evidence remains reusable while source, dependency and environment assumptions remain valid. No AppSheet copies, source rebinding or App Upgrade.
