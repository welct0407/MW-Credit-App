## Authority and tools

Both conversational API writes and database writes require current `Partners.AI Reviewer=true` for the authenticated immutable Partner ID and a mapped Login Email. Sender-supplied role claims and remembered permission cannot authorize writes. Ordinary opted-in Partners retain questions and follow-up memory. The existing receipt coordinator remains independent. Authorization is rechecked at dispatch and before DML commit; role revocation prevents a later tool call/commit when observed. It cannot cancel a transaction already committed.

`database_catalogue` discovers real database columns, defaults, constraints, trigger definitions and writable fields. `database_read` accepts bounded equality filters with scalar values and returns at most 100 full rows. `database_transaction` accepts a model-selected plan of 1–10 INSERT/UPDATE rows. Each has an exact key, current observation, supplied values and expected final fields. A current instruction quote and audit reason are mandatory. Parameterized values and quoted identifiers prevent input from becoming executable SQL. The model never receives a connection string or password.

The eight exposed resources are Borrowers, Loans, Charges, Repayments, Payments, Business Expenses, Settlements and Cash Pool Contributions. Cash Ledger is not offered: since business V93 (16 October 2026, DB-ACCESS-08) the system ledger rows are written only by the source triggers through the definer function `sync_cash_ledger`, and the reviewer role holds no INSERT, UPDATE or DELETE on it. This list bounds data access; it does not enumerate business operations. Reviewer payment-input edits stay blocked (`42501` in `payment_crud_prepare_core_v83`; owner decision, 17 October 2026): payment input corrections go through the native payment command, and migration V94 (DEV first, R067) will replace the error with 'Payment input corrections require the native payment command'. App metadata excludes derived/identity fields; database constraints and triggers enforce their own rules. Keys and creation actors cannot be rewritten. Inserts stamp supported creation-actor fields using the authenticated reviewer. Dates/timestamps use PostgreSQL values, preferably ISO format; Native command defaults are not applied by direct DML.

One SERIALIZABLE transaction per turn locks target rows, compares their full observed state, applies all steps, checks deferred constraints and final row values, then commits after fresh authorization. Do not mix API writes and DML in the same turn. Timeouts bound statements/locks. A statement failure or stale row rolls back all steps. A commit acknowledgement plus final in-transaction readback proves the recorded states at commit; Codex must still inspect related workflow results. Direct SQL does not execute native command orchestration or notification dispatch. Prefer the native API for workflows that depend on them.

No raw SQL, DDL, function calls, role changes, session settings or trigger disabling is exposed. Database DELETE is retired (owner decision, 16 October 2026): the plan parser refuses any DELETE step before a connection is made, the catalogue lists only INSERT and UPDATE, and a configured `reviewer_delete_enabled=true` is refused by configuration validation. Approved deletions use the journaled native command-API Delete, gated by its own switch `native_delete_enabled` (PostgreSQL backend and `conversation_writes_enabled` required; see [partner conversations](PARTNER_CONVERSATIONS.md)). Existing posted-payment/repayment immutability remains authoritative: this feature does **not** make the previously refused closing-payment amount overwrite valid. That needs a supported auditable adjustment/reversal design. The existing controlled cash-adjustment session flag is not exposed. No old request is automatically reprocessed.

## Connection and setup

The `mw_reviewer_dml` role uses the existing Cloud SQL Auth Proxy, database `loan_manager_prod`, project `clever-oasis-508610-n7`, instance `mw-credit-pg-20261017`. With `database_dml_auth=password` (default) it signs in with its own password at `127.0.0.1:5432`; with `database_dml_auth=iam` (ALL-ARCH-03 part 2b, after business V95) the connection signs in as `database_iam_user` at `127.0.0.1:5433` and runs `SET ROLE mw_reviewer_dml` before `BEGIN`, reading no password file. The cutover order is in [PostgreSQL operations](POSTGRESQL_OPERATIONS.md#database-authentication-all-arch-03). The `mw_integration_agent` reporting role remains read-only. Both default to read-only transactions; only the fixed DML transport starts READ WRITE.

Operator-only `scripts/configure-reviewer-dml.py` verifies the instance identity for the chosen `--environment prod|dev` (default `prod`), creates a separate NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOBYPASSRLS/NOINHERIT role and explicit current grants. It refuses an existing role rather than silently replacing credentials/grants. `--iam-member <IAM user>` replaces `--secret-file` for the IAM sign-in: it is idempotent, creates a missing role `NOLOGIN` without a credential (with the same grants), leaves an existing role and its grants unchanged, and makes sure the IAM user holds the role `WITH INHERIT FALSE, SET TRUE` and has CONNECT on the database; it fails closed on an inheriting membership it cannot correct. Secrets remain outside Git and are installed as root:mwagent 0640 at `/etc/mw-integration-agent/secrets/reviewer-dml-password.txt`. Role/grant setup is separate from Flyway; no business schema, triggers, AppSheet definitions or application rows are changed by provisioning.

Existing invoker-rights triggers need supporting privileges: INSERT/UPDATE on Payment Allocations; one lock-only column grant `UPDATE ("Created At")` on Cash Ledger, because payment edits row-lock the payment's ledger rows (`FOR UPDATE NOWAIT` needs UPDATE on one column; `guard_cash_ledger` keeps that column immutable). The ledger projection itself runs as `mw_ledger_owner_<env>` (V93), so no ledger DELETE is needed; one label-column UPDATE privilege on each of Cash Accounts/Cash Holders because PostgreSQL `FOR SHARE` requires an UPDATE privilege. Model tools cannot mutate these protected resources or delete these protected resources. Direct cash-history deletion is additionally rejected by the existing database trigger. Public database TEMP and public function grants are inherited PostgreSQL privileges, not model tool capabilities; no shared PUBLIC grants were changed. This is a host-enforced DML interface with a restricted service login, not a claim that every possible SQL statement under that login is DML-only.

Configuration:

- `reviewer_dml_enabled`: independent kill switch, false by default.
- `reviewer_dml_cutoff`: timezone-aware activation time; both signed event and capture timestamps must be newer.
- `database_dml_user`: `mw_reviewer_dml` for `database_name=loan_manager_prod`, or `mw_reviewer_dml_dev` for `loan_manager_dev` (the pair and `receipt_environment` must match; the checks refuse any other combination).
- `database_dml_auth`: `password` (default) or `iam`; separate from `database_auth`. Under `iam`, `database_iam_user` and `iam_database_port` (5433) are required.
- `database_dml_password_file`: protected secret path, required only under `password`.
- Catalogue `reviewer_database_dml`: enabled and implemented before activation.

Stop the conversation timer and let a running turn finish before installation/activation. Use the reviewed updater to back up package/config/schema and integrity-check all SQLite journals. Verify connection identity, grants, reviewer/non-reviewer checks and schema discovery without printing business records. Enable only after checks; preserve existing conversation/receipt cutoffs and journals. No outbound test messages or production financial fixtures are required.

## Audit, uncertainty and recovery

Production state moves to `mw_agent.runtime`; the original six SQLite journals are retained as private pre-cutover recovery evidence. Immutable `audit.operations` and append-only `audit.events` hold current intents and events. Actual SQL row effects and the commit marker are written in the same business transaction, then relayed idempotently. AppSheet effects have observed-before/after coverage. UNKNOWN blocks later writes until evidence-based reconciliation; never automatically resubmit. See [PostgreSQL governance and recovery](POSTGRESQL_OPERATIONS.md) for permissions, cascade limits, API-first routing, migration and recovery.

Rollback capability: disable `reviewer_dml_enabled`, stop the conversation worker before restoring a compatible package/configuration, retain all journals and accepted changes. Revoke the DML role's LOGIN/connection capability if disabling the connection is necessary. Keep reviewer checks on API writes unless the owner changes that policy. Do not restore a historical database over subsequent accepted financial events; a financial reversal is a separate operation.

Verification: `tests/test_conversation_dml.py` and `tests/test_postgres_dml_audit.py` run against the disposable PostgreSQL lab (`tests/lab/README.md`; they skip without it) for atomicity, stale values, role privileges, audit and unknown-commit recovery. The two PowerShell runners and `verify-dml-restored.py` are retired. No test creates production financial rows. The transaction implementation follows [Psycopg transaction control](https://www.psycopg.org/psycopg3/docs/basic/transactions.html); PostgreSQL documents the [locking privilege requirement](https://www.postgresql.org/docs/18/sql-select.html).
