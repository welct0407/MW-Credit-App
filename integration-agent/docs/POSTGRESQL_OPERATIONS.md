# PostgreSQL state and audit

The owner-approved R015 implementation uses `mw_agent` on the existing Cloud SQL instance `clever-oasis-508610-n7:asia-southeast1:mw-credit-pg-20261017`. It contains 30 audit/runtime/migration tables plus the independent deployment history. These are internal agent records, never business data sources. Business data stays in `loan_manager_prod`; DEV stays in `loan_manager_dev`. Instance/network settings are unchanged.

## Governance

The native MW Credit API is the preferred operational route for Find/Add/Edit/Delete (AppSheet is retired). Codex chooses calls from the authenticated native capability catalogue and the current request; there are no scripts for individual business operations. Conversational mutations require the current authenticated Partner's AI Reviewer role, a current instruction quote, exact keys and fresh observations. Partner membership alone grants no editing authority. Receipt approval retains its separate existing policy.

SQL is a fallback: `api_gap:` requires a verified missing native API capability; `atomic:` must explain the required transaction guarantee. SQL metadata and full canonical before-images support this fallback. Fixed reporting and authorization queries are separately authorized read-only database services. They are not model SQL tools.

Reviewer database DELETE is retired (16 October 2026): the plan parser refuses DELETE steps and the role holds DELETE only on Cash Ledger for the `cash_source_changed` trigger. A plan has at most 10 direct steps, 1,000 captured row effects and 10 MiB of captured images. Unexpected cascades roll back. Existing financial immutability, reference and cash-ledger guards continue to apply; approval does not bypass them. No DDL, arbitrary SQL, code, permissions or trigger settings are model-accessible.

`audit.operations` stores immutable intent; `audit.events` stores append-only events. Mutable status, queue ownership and journals live in `runtime`. All host/provider calls and journal mutations are recorded; sensitive image bytes, credentials and hidden reasoning are excluded. API audit coverage is observed before/after, not a claim of atomic capture of every API automation. SQL `agent_audit` triggers capture actual before/after rows and a commit marker in the business transaction. The relay copies events idempotently then acknowledges the source marker. It never uses a sequence high-water mark as a commit boundary.

Owner roles are NOLOGIN. Worker, relay and reporting/DML logins are separate, with explicit grants. Worker cannot change the generation control, schema or audit history. Relay cannot mutate business rows. Model inputs cannot select credentials or connection targets. Audit is append-only for runtime roles; the database administrator remains a trusted recovery authority. Retention/purge is not automated; see the design below.

## Cutover and recovery

1. Verify backups and restore the affected business databases privately. Apply the tested business Flyway migration in DEV, then pin the clean tested commit for PROD.
2. Provision the separate database and roles with `database/setup/bootstrap.sql` and run central immutable migrations explicitly (`state_migration`). No startup migration or automatic adoption. (The one-time provision script is retired.)
3. Freeze through `scripts/deploy-runtime.py freeze` as root on the verified VM. Stop timers, let workers finish, stop ingress, archive credentials/configuration/state/Codex sessions/package/systemd, restore privately and compare hashes. Keep the tunnel unchanged. During ingress pause, the origin is unavailable; no false successful acknowledgement is emitted.
4. Back up all six journals with `scripts/agent-state-admin.py backup --writers-stopped`, including immutable statement snapshots. Import one batch atomically and compare every source row, hidden ingress row ID, binary value, epoch, status and conversation binding. Do not import Codex-owned session/auth databases: retain their original files and private recovery copies.
5. Preserve existing service cutoffs and thread IDs. Establish a new backend generation and ingress cutover time. Newly arriving pre-cutover messages are quarantined; migration is not replay authorization. UNKNOWN, pending delivery and expiry history remain intact.
6. Install credentials as root:mwagent 0640, deploy the tested package/catalogue, verify configuration, confirm the business `agent_audit` grants (Flyway V93 since R064 Wave 4; no separate grants script), then activate the generation and resume one owner for each timer/ingress. Install the relay timer. Record actual completion in the implementation log.

After PostgreSQL accepts new work, never switch back to stale SQLite. Stop affected workers, keep audit/commit evidence and repair forward or perform an explicitly reconciled recovery. A business commit with central acknowledgement failure stays UNKNOWN until the outbox marker, matching intent and final state prove it. Absence of a marker alone is not permission to retry. API UNKNOWN requires deliberate evidence-based reconciliation; no automatic resend.

The five worker timers, receiver and relay use at most eight central connections with the current process topology; each process has a one-connection pool. Connections are not held across model/provider calls. Timeouts are set at connect time from `state.parameters`, not from role settings (which do not apply after `SET ROLE`): statement 15 s, lock 3 s, idle-in-transaction 30 s. Generation fencing fails closed. A journal opened `readonly` rejects any non-SELECT before connecting and runs `SET TRANSACTION READ ONLY` (AGT-STATE-02). A statement that changes zero rows writes no `state_change` audit rows (AGT-STATE-01), so the 20 s expiry sweep no longer adds an operation and an event per cycle. Cloud SQL latency adds overhead to journal actions; measure the actual VM path at rollout. No instance resize or connection-limit change is included.

`scripts/agent-db-maintenance.py audit-retention` (dry run unless `--apply`; `--export` exports and verifies only):

1. Selects whole operation trees (a root and its children) older than the cutoff (`--older-than-days`, default and minimum 7). A tree is eligible only if every action is READ, JOB, PROCESS or HEALTH, every idempotency key is random (uuid4), the service is not `ingress`, `reviewer_dml`, `statement_snapshot` or `legacy_import`, every state is terminal and no job run is still running. Effectful operations (SEND, INSERT, UPDATE, DELETE, IMPORT, RECONCILE, CONFIG, AUTH) and anything UNKNOWN or COMMITTED are kept, because their keys guard replay.

Exports the four tables (`audit.operations`, `audit.events`, `runtime.operation_state`, `runtime.job_runs`) as gzip JSONL plus a `manifest.json` (rows, bytes, sha256, md5, cutoff, script hash) under `gs://mw-credit-operator-private-737787224638/agent-audit-archive/<yyyy-mm>/<run_id>/`, each object created once and verified by size and md5 (sha256 readback with `--readback`). The prefix is owner-accepted. Local copies stay outside Git.

Agent V5 lets `audit.reject_rewrite()` pass a DELETE only for the owner with that flag set; UPDATE and TRUNCATE are always refused. The append-only triggers stay enabled, and a batch holds row locks only, so agent inserts are never blocked. A deadlock or lock timeout retries the batch, up to 5 attempts. Deleted counts must equal exported counts.
4. Writes one `audit-retention` CONFIG operation with counts and object names, then `VACUUM (ANALYZE)`.

`--resume-run <local export directory>` deletes from an earlier verified export instead of exporting again: it replans with that export's cutoff and refuses any planned row missing from the archive. `--resume-run … --rewrite` is for a write freeze only, and refuses while any other client is connected. ## Service heartbeats and lazy JOB records (agent V6)

Owner decisions of 17 October 2026 (R069, W4 optional follow-up), after a PROD readback of the last 24 hours: 8,431 pure no-op JOB trees a day (`partner-conversation-cycle` every 15 s 4,568, `audit-relay` every 30 s 2,588, `native-api-probe` 1,275, a few others; one operation, two events, one state and one job run each) and about 28,000 rows a day from the receipt cycle's two routine `masters()` reads per 20 s cycle (a READ operation with `requested`, `result_observed` and `completed` each).

- **Idle cycles record a heartbeat only.** `runtime.service_heartbeats` (agent migration `V6__service_heartbeats.sql`; worker SELECT/INSERT/UPDATE, retention and auditor SELECT; a mutable runtime table, not audit) has one row per service: the current or last run's `operation_id`/`run_key`, `owner` (host, pid, start token), `process_generation`, `code_version`, `state` (`RUNNING`, `COMPLETED`, `FAILED`, `INTERRUPTED`), `last_started_at`, `last_finished_at`, `last_outcome`, `exit_code`, `consecutive_noop`, `last_effect_at`, `materialised`. `audit.job()` takes the service advisory lock, retires a provably dead local owner or refuses a live or remote one (`JOB_OWNER_ACTIVE_OR_UNRESOLVED`, as before), and upserts the row `RUNNING`. The JOB operation is **lazy**: the first direct child operation of the run (`audit.begin()` with the job as parent) writes the JOB operation, its `requested` event and its `RUNNING` `runtime.job_runs` row inside the child's own transaction, before the child; a run that ends with `exit_code` other than 0, a crash, or an interruption is materialised at exit or retirement, so failures are audited exactly as before; a run that did nothing updates only `last_finished_at`, `last_outcome`, `exit_code` and `consecutive_noop`. Materialised runs produce exactly the rows an eager start wrote. The audit relay writes under other services' operations, never a child of its own JOB, so a relay cycle that exported or verified something sets `outcome['effect']` and is materialised at exit; an idle relay cycle is a heartbeat.
- **Fencing.** The owner fence is the heartbeat row plus the old `job_runs` check, both under the per-service `pg_advisory_xact_lock`. The start transaction, every direct child's transaction (materialisation and later children) and the exit transaction take that lock first, so they run in series: a start never sees a half-written first child (it waits for the commit, then finds the `RUNNING` job run and its live owner), and a run never writes after it was retired. The start locks the heartbeat row (`FOR UPDATE`) before it reads `RUNNING` job runs. A `RUNNING` heartbeat whose owner is alive on this host, or on another host, refuses the second start. A dead lazy owner is retired by writing the record it never wrote (`requested` then `interrupted`, job run `INTERRUPTED`, `last_outcome` `INTERRUPTED`, with the dead run's owner, generation and code version) and the heartbeat moves to the new run. Each child requires, under the lock, that its job run is absent (then materialised) or `RUNNING` and that the heartbeat still names this run (`operation_id`, `run_key`, `state='RUNNING'`); otherwise the child's transaction fails with `JOB_OWNERSHIP_LOST`, so a retired process can neither create a second `RUNNING` job run (the V3 unique index stays the backstop) nor add children to the `INTERRUPTED` record. The exit closes only this run's own `RUNNING` job run and only writes the heartbeat it still owns: a run retired while it was lazy leaves `requested`, `interrupted` as written by the retiring process, never `completed`/`failed` after `interrupted`. Whether a run is materialised is read from `runtime.job_runs` (one primary-key lookup per direct child), never from a process flag, so a child transaction that rolls back after materialising leaves the run lazy and the next child materialises it again under the same operation id.
- **Routine reference reads are summarised.** `receipt_master.masters()` runs through `audit.reference()`: inside a job it calls the unwrapped read and records `name`, `occurred_at`, `result_sha256`, `result_count` and the per-key row counts (or `exception_type`) on the run; when the run materialises, the JOB's `completed`/`failed` event payload and `job_runs.summary` carry the full `reference_reads` list; every child operation begun after a read carries `request_reference = {"reference_reads": n, "reference_reads_sha256": sha256(list[:n])}`, which the prefix of the JOB summary verifies, so a read that led to an action keeps its traceability. An idle cycle writes nothing. Outside a job (operator commands without `audit.job`, tests) and for every other `read_query` caller the `@audited` READ behaviour is unchanged. Request references are not part of the idempotency comparison, so a retry of a keyed operation with different reads cannot raise `AUDIT_IDEMPOTENCY_CONTENT_MISMATCH`.
- **Unwrapped probes.** `native-api-probe`, `instagram-probe` and `messages` run outside `audit.job()` like `serve-webhook`, `receiver-ready`, `status` and `check`: they are read probes with no journal write and no audit tree of their own, so the host monitor's `native-api-probe` every two minutes writes nothing in `mw_agent`.
- **Freshness.** `relay_health.freshness()` reads the audit-relay completion from the heartbeat and still reads `runtime.job_runs`; the newer completion wins and the oldest `RUNNING` start of either is the running marker, so mixed versions during a deploy keep the host monitor correct. `debian-health.py` uses `relay_health.inspect()` and needed no change. Deploy order: apply V6 (`state_migration.migrate`) before activating the package; a pre-V6 binary ignores the table and a V6 binary needs it.
- **Expected effect.** About 42,000 rows a day from the no-op JOB trees and about 28,000 from the masters reads stop being written (roughly 70,000 of the 88 MB-a-day growth), before the 7-day retention. `consecutive_noop` and `last_effect_at` show at a glance how long a service has been idle.

## Retrospective external-operator audit linkage

An operator-created SQL marker whose original plan is `direct_targets[0]` may use SHA-256 of PostgreSQL `jsonb::text` encoded as UTF-8 without a newline. This differs from the central canonical JSON hash. Never replace either digest or invent prior intent to make the generic relay accept it. The dedicated `operator_sql_reconciliation` contract validates both encodings independently and binds the exact source marker, transaction, operator labels and all ordered captured effects.

After explicit scoped owner approval, use `scripts/reconcile-operator-audit.py --manifest <private-file>` to plan. The private manifest must pin operation ID, original PostgreSQL and canonical hashes, marker/effect fingerprints, exact effect count and original evidence/repair authorization references. Verify a private backup and its restore/readback proof before adding `--apply --backup-reference <verified-reference>`. This appends truthful current-time retrospective linkage; it never performs business DML. Conflict, changed evidence or missing proof is a blocker. The source in-transaction timestamp is not an exact commit timestamp. Operator labels are not proof of reviewer membership.

Verify subsequent natural relay completions, exactly-once export events/acknowledgements and zero eligible backlog before declaring recovery. Do not rely on a transient green collector value while a worker is still running. Deployment/rollback is separately scoped through `scripts/deploy-runtime.py`; ordinary alert restart authority does not authorize this source change or reconstruction.

## Private logical backup script

`scripts/backup-agent-database.py --environments <file> --lab <file> --private-directory <dir outside the repo> --output <file>` dumps `mw_agent`, restores it into the isolated local lab and compares table fingerprints. `--dump-name <file>` (default `mw_agent-before-activation.dump`; no path separators or `..`) names the dump; an existing dump is never overwritten. On Windows the lab file's `bin` directory supplies `pg_dump.exe`/`pg_restore.exe`. On Linux/macOS pass `--pg-bin <dir>` or have `pg_dump` and `pg_restore` on `PATH`; otherwise the script stops with a clear error. The source connection requires TLS by default; `--source-sslmode disable` is accepted only for a loopback source host (the SSH/IAP tunnel to the Debian host's Cloud SQL Auth Proxy, which carries TLS to the instance and refuses SSL on its local listener), and is refused for any other host before a connection is made.
