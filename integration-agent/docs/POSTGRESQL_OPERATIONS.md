# PostgreSQL state and audit

The owner-approved R015 implementation uses `mw_agent` on the existing Cloud SQL instance `clever-oasis-508610-n7:asia-southeast1:appsheet-pg-prod-20260914`. It contains 29 audit/runtime/migration tables plus the independent deployment history. These are internal agent records, never AppSheet data sources. ## Governance

AppSheet is the preferred operational API for Find/Add/Edit/Delete. Codex chooses calls from current metadata and the current request; there are no scripts for individual business operations. Conversational mutations require the current authenticated Partner's AI Reviewer role, a current instruction quote, exact keys and fresh observations. Partner membership alone grants no editing authority. Receipt approval retains its separate existing policy.

SQL is a fallback: `api_gap:` requires a verified missing app/field/action capability; `atomic:` must explain the required transaction guarantee. SQL metadata and full canonical before-images support this fallback. Fixed reporting and authorization queries are separately authorized read-only database services. They are not model SQL tools.

Reviewer database DELETE is retired (16 October 2026): the plan parser refuses DELETE steps and the role holds DELETE only on Cash Ledger for the `cash_source_changed` trigger. A plan has at most 10 direct steps, 1,000 captured row effects and 10 MiB of captured images. Unexpected cascades roll back. Existing financial immutability, reference and cash-ledger guards continue to apply; approval does not bypass them. No DDL, arbitrary SQL, code, permissions or trigger settings are model-accessible.

`audit.operations` stores immutable intent; `audit.events` stores append-only events. Mutable status, queue ownership and journals live in `runtime`. All host/provider calls and journal mutations are recorded; sensitive image bytes, credentials and hidden reasoning are excluded. API audit coverage is observed before/after, not a claim of atomic capture of every API automation. SQL `agent_audit` triggers capture actual before/after rows and a commit marker in the business transaction. The relay copies events idempotently then acknowledges the source marker. It never uses a sequence high-water mark as a commit boundary.

Owner roles are NOLOGIN. Worker, relay and reporting/DML logins are separate, with explicit grants. Worker cannot change the generation control, schema or audit history. Relay cannot mutate business rows. Model inputs cannot select credentials or connection targets. Audit is append-only for runtime roles; the database administrator remains a trusted recovery authority. Retention/purge is not automated; see the design below.

## Cutover and recovery

1. Verify backups and restore the affected business databases privately. Apply the tested business Flyway migration in DEV, then pin the clean tested commit for PROD.
2. Provision the separate database and roles with `database/setup/bootstrap.sql` and run central immutable migrations explicitly (`state_migration`). No startup migration or automatic adoption. (The one-time provision script is retired.)
3. Freeze through `scripts/deploy-runtime.py freeze` as root on the verified VM. Stop timers, let workers finish, stop ingress, archive credentials/configuration/state/Codex sessions/package/systemd, restore privately and compare hashes. Keep the tunnel unchanged. During ingress pause, the origin is unavailable; no false successful acknowledgement is emitted.
4. Back up all six journals with `scripts/agent-state-admin.py backup --writers-stopped`, including immutable statement snapshots. Import one batch atomically and compare every source row, hidden ingress row ID, binary value, epoch, status and conversation binding. Do not import Codex-owned session/auth databases: retain their original files and private recovery copies.
5. Preserve existing service cutoffs and thread IDs. Establish a new backend generation and ingress cutover time. Newly arriving pre-cutover messages are quarantined; migration is not replay authorization. UNKNOWN, pending delivery and expiry history remain intact.
6. Install credentials as root:mwagent 0640, deploy the tested package/catalogue, verify configuration, confirm the business `agent_audit` grants (Flyway V93 since R064 Wave 4; no separate grants script), then activate the generation and resume one owner for each timer/ingress. Install the relay timer. Record actual completion in the implementation log.

After PostgreSQL accepts new work, never switch back to stale SQLite. Stop affected workers, keep audit/commit evidence and repair forward or perform an explicitly reconciled recovery. A business commit with central acknowledgement failure stays UNKNOWN until the outbox marker, matching intent and final state prove it. Absence of a marker alone is not permission to retry. API UNKNOWN requires deliberate evidence-based reconciliation; no automatic resend.

The five worker timers, receiver and relay use at most eight central connections with the current process topology; each process has a one-connection pool. Connections are not held across model/provider calls. Timeouts are set at connect time from `state.parameters`, not from role settings (which do not apply after `SET ROLE`): statement 15 s, lock 3 s, idle-in-transaction 30 s. Generation fencing fails closed. A journal opened `readonly` rejects any non-SELECT before connecting and runs `SET TRANSACTION READ ONLY` (AGT-STATE-02). A statement that changes zero rows writes no `state_change` audit rows (AGT-STATE-01), so the 20 s expiry sweep no longer adds an operation and an event per cycle. Cloud SQL latency adds overhead to journal actions; measure the actual VM path at rollout. No instance resize or connection-limit change is included.

## Audit retention (7 days; first purge run on production 16 October 2026)

Status (R064 Wave 4, 16 October 2026): the script and the systemd units are written and tested on a disposable copy. Owner decisions the same day: retention 7 days; purge now from a cloud session; `VACUUM FULL` postponed to the SSD move; an agent migration V5 for the retention role and purge function; archive prefix `agent-audit-archive/` accepted. A verified `mw_agent` dump (SHA256 `baf28e2d…`, isolated restore passed) and the dry run exist; the dry run on production found 682,425 operations in 226,464 trees eligible (1,242 old trees kept as protected, about 835 MB of rows, plan 153 s). The purge is running; its counts are in the W4 database change note. The timer units are not installed; the daily timer waits for V5 and an owner go.

Size readback (read-only, two readbacks on 16 October; 1,742 MB then 1,830 MB, about 88 MB a day): `mw_agent` is almost all in `audit.events`, `audit.operations`, `runtime.operation_state` and `runtime.job_runs`. There are no stored receipt images (`runtime.receipt_jobs.image` is empty). Growth is roughly 30,000 heartbeat and read operations a day, so a 12-month rule would remove nothing until September 2027. The owner decided on 16 October 2026 to keep one week of routine audit.

What a 7-day cutoff removes on the first run (counts and sizes only): about 681,000 operations, 1.47 million events, 681,000 states and 222,000 job runs, roughly 0.84 GB of tuple data, about 76% of operations. About 2,700 old operations are protected (1,116 effect operations, 609 with deterministic keys, non-terminal states) and kept with their trees. Steady state afterwards is about 0.6 to 0.7 GB for `mw_agent`; the instance disk stops growing at about 1 to 1.2 GB plus the business databases and WAL. Archive growth is about 14 MB compressed a day.

`scripts/agent-db-maintenance.py audit-retention` (dry run unless `--apply`; `--export` exports and verifies only):

1. Selects whole operation trees (a root and its children) older than the cutoff (`--older-than-days`, default and minimum 7). A tree is eligible only if every action is READ, JOB, PROCESS or HEALTH, every idempotency key is random (uuid4), the service is not `ingress`, `reviewer_dml`, `statement_snapshot` or `legacy_import`, every state is terminal and no job run is still running. Effectful operations (SEND, INSERT, UPDATE, DELETE, IMPORT, RECONCILE, CONFIG, AUTH) and anything UNKNOWN or COMMITTED are kept, because their keys guard replay.
2. Exports the four tables (`audit.operations`, `audit.events`, `runtime.operation_state`, `runtime.job_runs`) as gzip JSONL plus a `manifest.json` (rows, bytes, sha256, md5, cutoff, script hash) under `gs://mw-credit-operator-private-737787224638/agent-audit-archive/<yyyy-mm>/<run_id>/`, each object created once and verified by size and md5 (sha256 readback with `--readback`). The prefix is owner-accepted. Local copies stay outside Git.
3. Only then, deletes whole trees in batches (oldest first). By default this runs as `mw_agent_owner` in transactions that set the transaction-local flag `mw_agent.retention_purge`. With `--purge-function` it goes through `audit.purge_routine_trees()` as `mw_agent_retention`, which re-checks every rule on the server. Agent V5 lets `audit.reject_rewrite()` pass a DELETE only for the owner with that flag set; UPDATE and TRUNCATE are always refused. The append-only triggers stay enabled, and a batch holds row locks only, so agent inserts are never blocked. A deadlock or lock timeout retries the batch, up to 5 attempts. Deleted counts must equal exported counts.
4. Writes one `audit-retention` CONFIG operation with counts and object names, then `VACUUM (ANALYZE)`.

`--resume-run <local export directory>` deletes from an earlier verified export instead of exporting again: it replans with that export's cutoff and refuses any planned row missing from the archive. `--resume-run … --rewrite` is for a write freeze only, and refuses while any other client is connected. In one transaction it keeps every unplanned row, TRUNCATEs the four tables and inserts the kept rows back, so the tables get fresh files and no `VACUUM FULL` is needed. Used once, for the first backlog inside the SSD move freeze on 17 October 2026: 232 s, `mw_agent` from 1,877 MB to 435 MB.

`integration-agent/database/maintenance/vacuum-full-agent.sql` returns space to the database file with `VACUUM (FULL, ANALYZE)` of the five largest tables (stop the agent first; it takes exclusive locks and needs free disk about the size of the largest table). The first purge did not need it (`--rewrite` above). The Cloud SQL disk itself never shrinks; freed space is reused by all three databases. `agent-db-maintenance.py null-archived-images` nulls `runtime.receipt_jobs.image` only for ARCHIVED assets with object key, generation and hash recorded; it finds nothing today.

Daily run: `mw-audit-retention.timer` (03:40 Asia/Bangkok), enabled on the Debian host on 17 October 2026. It runs `mw-audit-retention.service` (`--apply --purge-function --older-than-days 7 --batch 50 --discard-local`) as `mwagent` through the IAM listener (127.0.0.1:5433; connection file `/etc/mw-integration-agent/secrets/audit-retention-connection.json`, no password), with `SET ROLE mw_agent_retention`. Agent V5 provides that role, the purge function, the gate and the two foreign-key indexes; the IAM user holds the role `INHERIT FALSE, SET TRUE`. The VM identity has create-only access on `agent-audit-archive/` (`google_storage_bucket_iam_member.agent_audit_archive_create`), so verification uses the server's size and md5, without `--readback`. Report: `/var/lib/mw-integration-agent/audit-retention/last-report.json`. The first run under the unit removed 5,245 operations in 18 s (longest batch 0.38 s). The units are installed by hand, not by `deploy-runtime.py`; reinstall them from the checkout when they change (their header comment still reads "ships disabled", from before activation). On the HDD instance before the SSD move, a batch purge ran about 6.5 operations a second. Do not run whole-tree readback queries on the shared instance: two such queries hit their time limits and wrote about 2.7 GB of temporary files; use single-scan counts.

Restoring rows: load each exported JSONL into `jsonb` and `INSERT ... SELECT (jsonb_populate_record(NULL::<table>, line)).*` in the order operations, events, operation_state, job_runs, or restore a `pg_dump`. Any failure before the delete step leaves the data untouched. Do not run it by hand without a verified export. The heartbeat volume itself (no-op cycles persisting a JOB tree) is the larger lever and is an open agent design decision.

## Retrospective external-operator audit linkage

An operator-created SQL marker whose original plan is `direct_targets[0]` may use SHA-256 of PostgreSQL `jsonb::text` encoded as UTF-8 without a newline. This differs from the central canonical JSON hash. Never replace either digest or invent prior intent to make the generic relay accept it. The dedicated `operator_sql_reconciliation` contract validates both encodings independently and binds the exact source marker, transaction, operator labels and all ordered captured effects.

After explicit scoped owner approval, use `scripts/reconcile-operator-audit.py --manifest <private-file>` to plan. The private manifest must pin operation ID, original PostgreSQL and canonical hashes, marker/effect fingerprints, exact effect count and original evidence/repair authorization references. Verify a private backup and its restore/readback proof before adding `--apply --backup-reference <verified-reference>`. This appends truthful current-time retrospective linkage; it never performs business DML. Conflict, changed evidence or missing proof is a blocker. The source in-transaction timestamp is not an exact commit timestamp. Operator labels are not proof of reviewer membership.

Verify subsequent natural relay completions, exactly-once export events/acknowledgements and zero eligible backlog before declaring recovery. Do not rely on a transient green collector value while a worker is still running. Deployment/rollback is separately scoped through `scripts/deploy-runtime.py`; ordinary alert restart authority does not authorize this source change or reconstruction.

Schema sources: `database/migrations/` (central immutable history), business R015 V33 in AppSheet-Loan-Project, and `database/setup/bootstrap.sql` for the separately managed `mw_agent` roles. The business-side `agent_audit` grants live in business migration V93 (R064 Wave 4); `business-grants.sql` is deleted. ## Private logical backup script

`scripts/backup-agent-database.py --environments <file> --lab <file> --private-directory <dir outside the repo> --output <file>` dumps `mw_agent`, restores it into the isolated local lab and compares table fingerprints. `--dump-name <file>` (default `mw_agent-before-activation.dump`; no path separators or `..`) names the dump; an existing dump is never overwritten. On Windows the lab file's `bin` directory supplies `pg_dump.exe`/`pg_restore.exe`. On Linux/macOS pass `--pg-bin <dir>` or have `pg_dump` and `pg_restore` on `PATH`; otherwise the script stops with a clear error.
