## Processing

1. Signed Instagram messages are durably captured before HTTP acknowledgement. Image attachment URLs are retained in the private ingress database. Text, audio, video, shares and other non-image content receive no business action or reply.
2. `receipt-cycle` processes only events with both event time and capture time at/after the immutable activation cutoff. A SQLite cursor handles bounded batches, and a process lock allows one worker. Delayed retries from before activation are excluded.
3. Match the signed sender ID to the current account's conversation/group participant ID. Use that participant's Instagram username to match Borrowers.Instagram Username, requiring exactly one AI Collection Enabled=true borrower. The owner authorized this existing conversation-to-master binding on 21 September; no profile endpoint or extra profile consent is required. Conflicting IDs/usernames and incomplete pagination fail closed. Disabled or ambiguous mappings receive no image extraction or email.
4. Download only approved HTTPS Meta CDN image URLs, with bounded redirects, image bytes and pixels. Codex sees the sanitized image and a fixed extraction prompt, never database credentials, borrower masters, account numbers to guess from, or delivery addresses. User configuration/rules, shell, subagents, web search, local image tools and apps are disabled. Output is schema constrained; the host independently validates extracted data. Image instructions have no authority.
5. Require a successful bank/PromptPay receipt, positive THB amount to two decimal places (a correctly grouped thousands comma such as `5,000.00` is accepted; ambiguous forms such as `5,00` are not), readable transaction reference, and Bangkok date today or yesterday with a readable transfer time. Convert Buddhist dates during extraction. The extraction lists every account or PromptPay number printed on the slip (`account_numbers`, renamed from `recipient_numbers` on 21 October 2026 because the model returned only the sender's number on a K+ slip; readers still accept the old key during the transition). The host keeps the numbers that match exactly one Active cash account: one account matches, two of ours are ambiguous, none is unmatched. A slip of our own outgoing transfer (our account as sender, one foreign account) therefore matches our account; Partner review approval is the human check. The same account can match either Cash Accounts Account Number or Alternative Account Number; the displayed bank name does not split Lisa's combined account or Dad's bank/PromptPay mapping. Only Active accounts match. Masks require equal total length, at least four visible digits, and one unique Cash Account across all candidates. Unknown/ambiguous/truncated numbers fail closed.
6. Reject bank references already in Payments or this agent's accepted receipts. Canonical image pixels also detect exact-image reuse independent of file metadata. Journal uniqueness is global across borrowers, messages and restarts. This is basic duplicate validation, not bank authenticity verification or a guarantee against a modified fraudulent slip.
7. Reserve receipt duplicate keys, then durable Partner notices. All Partner notifications start with Instagram in the Partner's Language Preference. Reuse unique Partner IG mapping, opt-in and signed-ingress messaging-window checks. Unavailable or uncertain Instagram delivery falls back to that Partner's current Email. No receipt image or full account number is included. Successful IG delivery suppresses email.
8. Re-read Partner delivery settings before dispatch. Changed settings hold the notice for review. Commit UNKNOWN before every provider call. Unknown IG never retries; it can use email fallback. Unknown email never retries. Definitely rejected email retries after five minutes, at most three attempts. The shared OAuth refresh lock remains. Legacy direct-email outbox entries are superseded only if definitely unsent; SENT/UNKNOWN history remains unchanged. The new notification cutoff excludes historical summary replay.

## Standard operator preparation

## Receipt run order, image budget and retries — 20 October 2026

Owner plan of 20 October 2026 (batch A, agent code only; no SQL, no new service, no catalogue revision, no change to the Cloud Run instance count, the receiving page, the Gemini model, the validation rules or the shared receipt API). One run of `mw-receipt-summary` (the `receipt-cycle` command, still one worker at a time under `receipt-worker.lock`) now runs in this order:

1. Ingest captured events.
2. Expire reviews past 24 hours.
3. Decide reviewer replies, then execute approved reviews, then send result notices. Approvals therefore no longer wait behind an image. A review is executed at most once per run. With Partner review off, the image loop runs first as before.
4. Process pending images under the time budget (`receipt_cycle_image_budget_seconds`), re-reading the controls before each image. The master-read backoff above applies per image, so a master failure on one image does not stop the next. A reply captured while a run is busy waits until that run ends.
5. Propose validated receipts, execute approved reviews again (automatic payments complete in the same run), send notices again, then project evidence.

**Retry ladder.** `RECEIPT_PROCESSING_UNAVAILABLE` (extraction timeout or provider failure) retries on the next run after attempt 1 and after 60 s following attempt 2; attempt 3 still ends REVIEW with `RECEIPT_RETRY_LIMIT`. A job retried this way is not picked again in the run that deferred it. `RECEIPT_PROCESSING_STARTED` (crash guard), `RECEIPT_MASTER_UNAVAILABLE` and `RECEIPT_ARCHIVE_PENDING` keep the five-minute delay.

**Archive exit.** An archive error no longer defers a job for five minutes forever. When the evidence asset is `SOURCE_UNAVAILABLE` or `INTEGRITY_CONFLICT`, the job ends REVIEW with detail `RECEIPT_ARCHIVE_UNAVAILABLE` (marking it REVIEW clears its source URL and image, so the reviewer asks the borrower to resend) and the existing hold alert asks the reviewers for manual investigation (see [Partner review](PARTNER_REVIEW.md)). Other archive errors, including a source still pending after `RECEIPT_DOWNLOAD_FAILED`, defer the job 300 s and keep the source URL. A job that stays PENDING with its archive incomplete longer than `receipt_archive_alert_seconds` keeps its state and source URL; the reviewers get one "Receipt delayed" alert (⌛) per job and reason, dropped at delivery once the job is resolved (the reason is the asset's last error code; the text says no reply is needed and replies to it are ignored). Other terminal asset codes (`RECEIPT_SOURCE_MISSING`, `RECEIPT_SOURCE_CONFLICT`, `RECEIPT_SPOOL_MISSING`) follow the same alert. [Receipt evidence](RECEIPT_EVIDENCE.md) describes the archive states.

**Instagram directory read.** One run caches the account's conversations directory pages on first use and answers sender identity, reply authorization, posting identity and notice recipient resolution from them. The snapshot lives for the whole run, so with a 60 to 180 s image budget it can be a few minutes old at the checks after the images; the fail-closed rules are unchanged. Ambiguous or incomplete pages still fail closed, and a failed read is not cached. Profile lookups and a forwarded group's read of the exact group stay live.

Out of this scope and unchanged: the duplicate, identity, account and date checks before every post, the 24-hour review expiry, the today-or-yesterday rule, the UNKNOWN never-replay rule, every cutoff. Held receipts (REVIEW) are not re-run automatically. The owner's targets are in the [change note](../Change%20Logs/CHANGE_NOTES_RECEIPT_CYCLE_SPEED_2026-10-20.md); measured results are recorded there after deployment.

After a run, if the wake file changed during that run, the command runs up to two more passes, because systemd may not restart a running oneshot on `PathChanged`. The unit is `WantedBy=paths.target`; a fresh install does not enable it (enabling is the owner's step in the batch B window), and the deploy helper pauses it like a timer and refuses to install or activate while it is active. A failed path unit is not monitored itself. The 20 s `mw-receipt-summary.timer` stays as the fallback for retries and expiries, so a missed wake only costs up to one timer interval. To halt the wake path alone: `systemctl disable --now mw-receipt-wake.path`.

## Receipt recognition API

Source, 18 October 2026 (catalogue revision 29); implemented, not enabled. The command services' payment receiving page sends an uploaded slip here for a suggestion; the agent's Instagram receipt cycle uses the same extraction module.

**Providers.** `receipt_image.py` keeps the shared prompt, JSON schema, image canonicalisation and host-side shape check (exactly the schema keys and types). `receipt_provider_codex.py` is the existing isolated `codex exec` call (model reported as `default`). `receipt_provider_gemini.py` makes one Vertex AI `generateContent` call: canonical PNG inline, the shared prompt, temperature 0, JSON response mode with the schema in Vertex's dialect, the least thinking the model allows (Gemini 3 and later: `thinkingLevel` `LOW`; Gemini 2.x Flash and Flash-Lite: `thinkingBudget` 0; Gemini 2.x Pro: none), the image downscaled to at most 1600 px on the long side (aspect kept, Lanczos) and sent as JPEG quality 85 or PNG, whichever is smaller, 36 s per attempt for the recognizer and one retry on 429, 5xx, timeout or connection error, only while at least 4 s of the deadline remain. It signs in with the VM service account's access token from the metadata server; there is no API key. `gemini_model` must be a fixed version: a stable GA id such as `gemini-3.8-flash` or a suffixed one such as `gemini-2.0-flash-001`; ids containing `latest`, `preview` or `exp` are rejected. `gemini_location` is a Vertex region or `global`. On 19 October 2026 the owner switched from `gemini-3.8-flash` to `gemini-3.5-flash-lite` (GA 21 July 2026), about three times faster in an 18-run synthetic comparison with no call near the time limit (3.8-flash had three calls of about 40 s). Vertex serves it from `global`, `us`, `eu` and `asia-south1`, not `asia-southeast1`; the configuration stays on `global` (host `aiplatform.googleapis.com`). A currency printed as Thai baht (`Baht`, `บาท`, `฿`, any case) counts as THB in the receipt check and the prompt asks for `THB`; any other currency is still rejected.

Enabling requires the PostgreSQL audit backend. The service needs Vertex AI enabled with `roles/aiplatform.user` on the VM identity, direct VPC egress from the command services and a firewall rule to the VM's service account on the port (infrastructure stage).

**Cycle audit.** Each receipt-cycle extraction is one `receipt_image_extraction` operation whose plan names the provider and model (`{"provider":"codex","model":"default"}` on route `codex`, or `{"provider":"gemini","model":"gemini-3.5-flash-lite"}` on route `internal`), so a check can tell the two apart directly.

**Contract.** `POST /v1/receipt-recognition` with `Authorization: Bearer <Google ID token>`, `Content-Type: image/png` or `image/jpeg`, `X-Content-SHA256: <64 lowercase hex of the body>` and the raw image (at most 5,242,880 bytes). The token must be RS256-signed by Google with issuer `https://accounts.google.com` (or `accounts.google.com`), the configured audience, verified email and the exact email and numeric subject of an allowed caller.

| Status | Body |
| --- | --- |
| 200 | `{"status":"recognized","provider","model","durationMs","imageSha256","result":{...schema fields}}`; shape checked, not business validated |
| 400 | `{"status":"rejected","reason":"invalid_image\|hash_mismatch\|unsupported_type"}` |
| 401 / 403 | `{"status":"denied"}` (missing or invalid token / caller not allowed) |
| 413 | `{"status":"rejected","reason":"too_large"}` (refused before the body is read) |
| 503 | `{"status":"unavailable","reason":"disabled\|busy\|timeout\|provider_error"}` |

`GET /healthz` returns `{"status":"ok","enabled":bool}` without a token and calls no provider. At most two extractions run at once; a third request gets `busy`, and a slot is freed only when its extraction really ends. Each request is bounded to 42 s (the provider stops at 40 s), under the command route timeout (45 s) and the PWA client limit (60 s). Recognition is stateless: the image is canonicalised in memory and never stored, no business database is read and account matching stays with the command API. Each authenticated request writes one audit operation `receipt_recognition_api` (caller email, image SHA-256, provider, model, duration, outcome) on audit route `internal` for either provider (the provider is in the plan); a result whose audit row cannot be written is withheld (503). The journal gets one line per request without image, token or result fields.

**Rollout.** Catalogue revision 29 needs the same two-step route as revision 28: `deploy-runtime.py` refuses a live catalogue whose revision or service names differ from the repository, and the installed validator rejects the unknown name `receipt_recognition_api`. First install code that knows the name while the live catalogue stays at revision 28, then add the key (disabled) by the config-only route; the owner chooses the exact route at activation.

**Recovery.** Set `receipt_recognition_enabled=false` or disable the catalogue entry (effective on the next request), then `systemctl disable --now mw-receipt-recognition.service`. Callers treat any failure as "recognition unavailable" and the form continues manually.
