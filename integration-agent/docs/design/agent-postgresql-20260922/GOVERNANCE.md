# Agent database governance — proposed v1

Status: owner-requested design and execution handover, 22 September 2026. **Not deployed.** The current task authorizes repository design artifacts only. The existing service catalogue remains the runtime authority until a later execution task implements and activates this design. Start with [HANDOVER.md](HANDOVER.md).

## 1. Ownership and scope

G01. Create one dedicated production database, proposed name `mw_agent`, inside project `clever-oasis-508610-n7`, instance `appsheet-pg-prod-20260914`. This is a logical separation, not separate CPU, memory, connection capacity, storage failure domain or restart scope. Do not change shared instance settings, networking or tiers as an incidental part of this work.

G02. `mw_agent` owns the integration agent's audit and application runtime state. `loan_manager_prod` remains the production business-data authority; `loan_manager_dev` remains the business migration test target. Neither an audit record nor a copied Partner snapshot becomes authority to conduct a later operation. Production audit/state must not be imported into DEV apps.

G03. No audit/runtime table is an AppSheet data source. No app view, menu, virtual column, Ref, report or synchronization mapping is added for these tables. A small `agent_audit` schema in each business database is an internal transaction journal, also absent from both apps. No business table is moved into the agent database.

G04. The model chooses business operations using generic discovery/read/create/update/delete capabilities. Host code implements transport, authorization, transaction/audit guarantees and limits; it must not become a catalogue of fixed scripts for named business requests. Resource and field boundaries are still explicit and default-deny.

## 2. Approval and route selection

G05. Conversational mutations require a currently authenticated Partner with `Partners.AI Reviewer=true` and a mapped Login Email. Recheck master identity/opt-in as today, and reviewer authority immediately before dispatch and before direct SQL commit. Record the snapshot and check time. Revocation cannot undo an already committed transaction; do not claim race-free role locking. Receipt proposals retain their separate exact correlated approval and expiry rules. Scheduled services retain only their current scoped authority.

G06. A current, unambiguous reviewer instruction naming an operation and identifiable records is its approval. No second confirmation is necessary merely because DELETE is involved. Missing keys, conflicting amounts, unclear parent/child scope or a proposed expansion beyond the instruction require clarification. Earlier dialogue supplies context, not renewed authority; neither records nor model-generated plans authorize an operation. Approval must cover the full planned deletion set and known destructive consequences.

G07. **AppSheet first** for reads, creates, updates and deletes whenever the owning production app/API can safely express the approved operation. Use current captured schema, actual API permissions and present records. It is unnecessary to send a knowingly unsupported call simply to manufacture a failure. Record capability evidence and the route decision before dispatch. Fixed reporting services may retain SQL for joins/aggregations that the API does not suitably express, with a recorded service-level capability reason rather than an API call every run.

G08. SQL fallback requires an explicit reason: unsupported API operation/field semantics, required transaction guarantees unavailable through the API, or a definite pre-dispatch transport failure where SQL is independently authorized. An API timeout, ambiguous HTTP error or missing response is **not** evidence of failure. Reconcile first; never switch transport while the API might already have acted. Never use a 401/403 or business-validation rejection as automatic permission to bypass policy. Distinguish an app UI restriction explicitly covered by approved SQL correction authority from a business integrity rule.

G09. Route changes stay within one logical operation/idempotency family. A definitely unexecuted API attempt may be followed by an audited SQL attempt; a successful or uncertain API mutation may not. Preserve the earlier ban on mixing potentially effective API and SQL mutations in one atomic-looking workflow. Multiple API calls are not atomic; report and audit partial completion rather than claiming rollback.

G10. Add DELETE to both generic mutation routes. This supersedes the earlier blanket host prohibition on physical deletion **for explicit reviewer-approved requests on supported operational resources**. It does not grant DDL, TRUNCATE, role changes, arbitrary SQL/functions, trigger disabling, identity changes or audit deletion. Existing posted-payment, repayment, cash-ledger and referential guards remain intact. A requested deletion blocked by those guards is reported with its actual boundary; no integrity-trigger removal is included in this design.

G11. Delete exact keys, not unrestricted predicates. Retain current baseline limits: at most ten directly selected mutation rows per conversational transaction; no automatic splitting to evade a limit. Inspect FK delete actions and trigger effects. Capture before-images; record affected references and an approved deletion manifest. For SQL, compare the actual DELETE row set from transactional capture with that manifest before commit. Any unexpected cascade rolls back. Known derived updates may be included as classified consequences rather than extra requested deletions. Initial effect budget: at most 1,000 captured row changes / 10 MiB of audit row images per SQL transaction, subject to synthetic benchmarking. Reject rather than truncate audit data.

G12. An API DELETE that cannot preserve or verify the required dependent-record scope is a legitimate capability gap for SQL fallback, if SQL is authorized and its guards permit it. Do not pretend host snapshots around an HTTP call provide atomic compare-and-swap or exhaustive cascade capture. Preserve full before-images for explicit API deletion targets, inspect known related results, and label observation coverage honestly. An API success response alone is not verification.

## 3. Audit contract

G13. Every externally meaningful agent activity has a stable operation ID and correlated events: ingress acceptance/duplicate, authorization/denial, model turn start/finish/failure, each tool invocation, reads, writes, route/fallback decisions, receipt extraction/decision/posting, provider requests/results, scheduled runs, retries, recovery, configuration changes and operator reconciliation. Use a parent operation to group a workflow. Record tool arguments in sanitized structured form, not hidden chain-of-thought or every model token. Repeated healthy polls can produce one run summary with counters; failures and effectful calls require individual events.

G14. Audit storage operations do not recursively audit themselves. A relay/import/maintenance run has its own summarized operation; each event INSERT is not another business operation. Unsigned invalid webhook traffic is rejected before business intake; capture bounded security counts/reasons without storing arbitrary unauthenticated payloads. Database-unavailable attempts cannot promise a central log at that instant: rely on the system service log and append an incident after recovery.

G15. `audit.operations` is an immutable intent; `audit.events` is append-only history. Corrections append a linked reconciliation event. Runtime projections can change but must be updated in the same central transaction as their audit event. Worker/relay roles cannot UPDATE, DELETE or TRUNCATE audit history or change its schema. Owners/migration administrators can technically override these controls; this is not cryptographic immutability against database administrators. Runtime SQL deletion authority never includes the agent database or its audit schemas.

G16. Preserve original request reference, actor identity, authorization evidence, policy/code versions, target environment, exact record keys, route decision, approval/plan digest, dispatch time, row/response evidence and outcome. Reads normally store predicate/scope, counts, selected identifiers, freshness and a digest, not unrestricted result copies. Mutations store relevant before/after images and effects. Binary receipts belong only to restricted runtime storage while needed; images, passwords, API tokens, auth exports and signed credential-bearing URLs are not audit-event payloads. Existing private retained payloads are migrated without exposing them in Git/logs; do not silently redact values that existing hashes depend on.

G17. IDs and hashes are generated by trusted host code. UUIDs are supplied explicitly; imports use a stable UUIDv5 namespace and retries reuse the same ID. SHA-256 hashes cover canonical, documented UTF-8 payload bytes; JSON serialization must preserve exact decimal strings. Idempotent INSERT conflicts require comparing the original immutable content. A duplicate key with different content is a hard reconciliation failure, not success. Sequence/timestamp order is not proof of commit order.

G18. Audit supports outcome distinctions: planned, authorized, dispatching, committed/provider-accepted, verified, completed, denied, definitely failed/rolled back, unknown and reconciled. Mark an effectful attempt durably uncertain/dispatching **before** its external call. No automatic retry of an uncertain business write/send. Preserve service-specific retry rules for definite non-delivery, and explicitly record the existing possible duplicate across IG-unknown then email-fallback. Read-only retries may be bounded separately.

G19. Before new side effects, the central intent and authorization must be durable. Direct SQL changes and local transaction audit must commit together; cross-database relay may lag without losing the business commit evidence. A visible transaction marker proves commit, not completion of all downstream workflows. No marker observed during an unresolved/in-flight connection is not proof of rollback. Investigate transaction termination/current rows before releasing an unknown operation.

G20. Keep all imported audit, deduplication, review, sent/unknown and processing history initially. There is no automatic purge or retention expiry in v1. Add a measured, owner-approved retention/archive policy later; it must preserve outstanding recovery and deduplication needs. This is an operational default, not a legal retention claim. Event storage growth must be monitored.

## 4. State, availability and performance

G21. Move application-owned SQLite journals and their data to PostgreSQL. Preserve keys, statuses, retries, amounts, epochs, bytes, exact serialized strings and original cutoffs. Do not rewrite Codex-managed state/authentication/session storage or move synthetic test databases into production state. Preserve all conversation bindings and full session folders. Keep statement snapshots and generated artifacts backed up; moving SQLite alone does not protect those files.

G22. Normal production operation has one authoritative backend and one owner per worker/route. No indefinite dual writes to SQLite and PostgreSQL. Retain current local process locks and add PostgreSQL coordination for any future additional host. A lease expiry does not authorize replay of a DISPATCHING/UNKNOWN effect. Backend generation checks fence new cooperating workers, not old binaries; stop and disable old units before cutover.

G23. Proposed v1 outage behavior is fail-closed, with **no new local SQLite emergency queue**. Webhook 200 is sent only after central inbox, work reservation and audit commit. If central storage is unavailable, return 503 and rely on upstream retries; alert promptly. Upstream retry duration is finite and not guaranteed here. The owner may choose a separately designed durable queue later, but the executor must not silently introduce one or acknowledge unpersisted messages. Existing local system logs remain diagnostic, never an authority for replaying financial writes.

G24. Use a small, process-wide connection budget. Initial design ceiling: two central connections per active worker process, no more than eight pooled central connections across the current VM, plus one active DML connection and one relay business connection. Pools must have bounded checkout waits and backpressure. The threaded webhook receiver uses a shared bounded pool, not a new pool per request. No connection is held across a model turn or provider call except a deliberately separate worker ownership connection counted in the budget. Never hold a SQL transaction across those external waits.

G25. Measure before tuning. Proposed acceptance targets are incremental p95 central persistence overhead below 100 ms per critical persistence transaction and webhook persistence p95 below 500 ms at observed peak and a synthetic 5x burst; these are design targets, not current results or provider SLA. Compare median/p95/p99, pool waits, job backlog, query counts, CPU/I/O and existing business-workflow latency. Optimize round trips/batching/indexes first; do not raise the shared instance connection limit/tier automatically. Audit-critical pre-dispatch records cannot be deferred for speed.

## 5. Change and recovery authority

G26. Keep schema migrations immutable and independently tracked per database. Agent schema migrations belong to this integration repository with a new dedicated history; business outbox tables/triggers belong to the AppSheet repository's next approved Flyway migration/release. Roles, grants and CREATE DATABASE remain separate operator setup. Recheck version/release reservations at execution; this design reserves none. No App Upgrade or dictionary exposure is needed merely to create non-app audit tables, but follow applicable business database release checks and record both apps as unchanged definitions.

G27. Test in a disposable PostgreSQL 18 lab, then business DEV for affected triggers/dependencies, before scoped production rollout. Back up each changed asset and prove restore of business DB, central DB and agent private files/journals as applicable. Cloud SQL backup retention/PITR must be inspected at execution, not inferred from database existence. A logical data restore alone does not restore roles/credentials, Codex sessions or files.

G28. Freeze all readers/writers involved in cutover, import/verify, record the boundary, then activate once. Rollback before the first PostgreSQL-authoritative event may return to the frozen SQLite state. After new accepted work, do not point old code at stale SQLite. Pause and fix forward, or perform a verified reverse migration that includes every new intent/outcome/dedup key and private artifact. Business audit triggers also make the old uninstrumented DML adapter incompatible; keep that path disabled until compatible code is installed. An audit record or backup does not authorize reversing a financial event.

G29. Public reports/evidence contain schema, counts, hashes and status only. Live records, SQL dumps, approvals containing personal data and credentials stay in existing protected storage. Do not transmit partner/borrower messages as test traffic. Use synthetic fixtures and simulated delivery for failure tests.

G30. The execution model owns implementation and evidence, not policy invention. Follow these defaults and the detailed handover; resolve routine implementation choices within scope. Ask only when the owner changes a stated rule, a required recovery/target identity cannot be established, or actual dependencies require expanded scope. Do not silently weaken authorization, audit capture or unknown-outcome handling to get tests to pass.
