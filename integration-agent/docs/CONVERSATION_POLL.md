# Official API conversation intake

Owner authorized scheduled API reads on 21 September 2026. Browser automation is prohibited, following the owner's prior account restriction. No browser is used. Group sending remains untested and is not enabled.

Live read evidence: the conversation-list endpoint returned 15 conversations, 12 with three participants, and messages for 13 conversations. Individual group-object/history endpoints returned HTTP 400; the working route is account conversations with expanded message fields. This is observed account behavior, not a claim of general vendor support.

`conversation-poll` runs one minute after the previous run finishes (five minutes before 20 October 2026; owner choice, one scan is one Meta request, about 60 requests an hour), under `mw-conversation-poll.timer`. Every scan discovers current conversations and selects those containing a currently AI-enabled borrower, including groups created that day. The first conversation-list call requests the newest 20 messages per conversation (enough for the about six-minute window of one-minute cadence plus the 300 s overlap); follow-up history pages request 100. It follows both outer conversation pagination and nested message cursors. Borrower images and authorized Lisa-forwarded images are eligible; from R151 an image from another non-business sender in an eligible group is queued as `UNIDENTIFIED` for review ([below](#sender-fallback-and-unidentified-senders-r151-no-switch)); non-image content is ignored. Images feed the existing receipt job table and worker; receipt validation, current borrower identity, bank aliases, duplicate checks and Partner IG-first/email-fallback notices remain shared.

The first activation establishes a timezone-aware cutoff. Each successful conversation check that captured a new message stores a watermark with a five-minute overlap; message IDs make repeat scans harmless. An idle check keeps the saved watermark (since 31 October 2026): every watermark write is an audited journal statement, and at one-minute cadence the unconditional write for every group was about 29,000 audit operations a day and kept every poll run out of the idle heartbeat. Everything newer than a kept watermark was captured by the run that wrote it, so the re-read window stays small; the watermark is still written on a group's first check and when the window no longer fits the first 20-message page (for example after a same-day backfill, which never moves it). Message and image reservations commit with that watermark. The same message/attachment job key is used by webhook intake. Polled events have their own provenance table and never become signed webhook evidence or refresh the IG delivery window.

New conversations start at the existing activation cutoff; existing ones start at their saved watermark minus the overlap. Read until reaching that boundary or exhausting accessible history. The working continuation is `messages.limit(100).after(cursor){...}` (the first page uses `messages.limit(20)`) on the account conversation-list endpoint, selecting only the original conversation from the result. Returned group `/messages` URLs still fail on this account and are not followed. Live probes on 25 September confirmed that a populated continuation returns older messages, while an exhausted expansion can omit `messages` entirely even though the preceding page had a `next` link. A present conversation with an omitted expansion is empty; a disappeared conversation, malformed page, invalid/repeated cursor or changed ordering is held.

At most ten message pages are read per conversation per scan (reach 20 + 9 × 100 messages). Poll reads use a 40 s timeout per socket operation (the 100-conversation list call exceeded the former 20 s on 86 of 2,447 runs, mostly 01:00-08:00 ICT); sends keep 20 s. A failed request names only the exception class, for example `Instagram API request failed (TimeoutError)` and `POLL_CONVERSATION_UNAVAILABLE:TimeoutError`; never the URL or token. If history cannot be completed within that bound, or participants/attachments are incomplete, that conversation's transaction and cursor stay unchanged. Other conversations continue. The command reports aggregate counts plus at most twenty hashed conversation keys/fixed error reasons and exits with status 2 if any conversation failed, so systemd records partial failure. The collector reports one failed run as Degraded, which does not page; Down means the timer or unit is inactive or not loaded, a run is hung over 600 s, or there was no successful run for over 600 s. The next scheduled run retries from the preserved cursor. No additional alert delivery is implemented. A manual API backfill needs explicit historical scope; existing deduplication prevents reprocessing captured images. The poller does not write payments; the downstream receipt policy controls automatic ordinary posting and reviewer/manual cases.

When a scan queues at least one image job it touches the receipt wake file, so the receipt cycle starts at once instead of waiting for its fallback timer (see [Receipts](RECEIPTS.md#wake-on-capture--20-october-2026)). A group receipt is therefore picked up within about a minute of capture.

Deploy with `scripts/deploy-runtime.py` ([Operations](OPERATIONS.md#deploying-a-reviewed-commit)); its activation step resumes the timer. The one-off activation script is retired. Inspect `systemctl status mw-conversation-poll.timer` and `journalctl -u mw-conversation-poll.service`; successful output contains aggregate counts only. Roll back by stopping/disabling this timer and restoring the recorded config/package backup without replacing current journals. The webhook remains active independently.

For an explicitly owner-requested same-day group backfill, use `conversation-poll --date YYYY-MM-DD` with the usual config/catalogue arguments. This mode reads from Bangkok midnight, restricts to group conversations, preserves normal polling watermarks/cutoffs, and queues only unseen images through the same receipt workflow. It does not reopen terminal receipt jobs or replay existing reviews. Earlier dates are rejected. A history gap holds only the affected group rather than skipping its messages.

## Recheck after a borrower-master change — revision 35 (R119, on in PROD)

The poll decides each group message once, so a slip from a sender who was not yet an enabled borrower is recorded `IGNORED` and never read again, and a hold whose cause the owner fixes later in the app stays held. With the configuration switch `conversation_poll_recheck_enabled` true (default false; it requires `conversation_poll_enabled`, otherwise the configuration is refused) the poll rechecks both when the borrower master changes. See the [change note](https://github.com/welct0407/MW-Credit-App/blob/b83bf3a/integration-agent/Change%20Logs/CHANGE_NOTES_R119_AGENT_RECHECK_2026-11-04.md).

- **Snapshot.** Next to `conversation-poll.lock` the poll keeps `conversation-poll-master.json` (mode 0600, written atomically): the enabled Instagram usernames (`receipt_master.masters()`, normalised) and a digest of the active cash accounts' numbers and alternative numbers. No database column. The first run, or an unreadable file, only writes the snapshot and rechecks nothing. The snapshot moves only after the whole recheck succeeded; a group that could not be read keeps the old one and the next run tries again.
- **Ignored slips.** For each group with a newly enabled participant the poll re-reads history from yesterday's local midnight and finds that participant's image messages. Each is matched to an `IGNORED` row in `conversation_poll_messages` by message id or, because Meta returns different ids for the same message on different reads, by conversation and event time within 5 seconds (a larger skew misses the match). It is skipped when a receipt job for the same conversation, sender and sent time exists. In one transaction the row becomes `BORROWER` and the job is queued with the usual poll source and job key. The cursor and every other recorded outcome stay. The worker then applies the payer, duplicate, archive and idempotency guards as for any slip.
- **Held slips.** Under `receipt-worker.lock`, taken without waiting (a busy worker skips the recheck and keeps the snapshot), today's and yesterday's `REVIEW` jobs held `PAYER_UNRESOLVED` (the enabled set grew) or `RECIPIENT_UNKNOWN_OR_AMBIGUOUS` (the accounts changed) are requeued with detail `AUTO_RECHECK_MASTER_CHANGED`, keeping the saved extraction. A job whose partner review was decided, a job with no archived original (the recheck needs `receipt_archive_enabled`) and a job already requeued from the same hold since the snapshot was written are skipped, so a job is rechecked at most once per change.
- A `--date` backfill never rechecks. With the switch off none of this runs; the snapshot is not read or written.
- Run counts add `recheck_jobs`, `recheck_errors`, `held_requeued` and `held_skipped`, and `recheck` (`snapshot_written`, `rechecked` or `recheck_incomplete`).

## Sender fallback and unidentified senders (R151, no switch)

Owner request of 13 November 2026 after a borrower's slip was recorded `IGNORED` because Instagram dropped the borrower from the group's `participants` list seconds after the post (no job, no notice). Catalogue revision 38 is unchanged. See the [change note](../Change%20Logs/CHANGE_NOTES_R151_RECEIPT_SENDER_FALLBACK_2026-11-13.md).

- **`SENDER`.** The sender is not among the participants but the message `from.username` is exactly one enabled borrower: the poll queues a job (row outcome `SENDER`). A group is also scanned when any sender on the first page is an enabled borrower even though no participant is. The receipt cycle then checks the identity binding (`SenderUnbound`, `taken`) and the strong context, and posts automatically as C1/C2 under the usual guards.
- **`UNIDENTIFIED`.** An image from any other non-business sender in an eligible group gets a job (row outcome `UNIDENTIFIED`), only from `payer_name_cutoff` onward. After extraction the borrower is resolved by the slip payer name across the enabled borrowers, narrowed by the group's borrowers. The job always goes to Reviewer approval and is never posted automatically; an unresolved or unreadable name holds as `PAYER_UNRESOLVED` or `PAYER_NAME_UNREADABLE` with the existing notice ([Partner review](PARTNER_REVIEW.md)). A `NOT_PAYMENT_RECEIPT` image stays silent, so photos from non-borrowers are now read and archived as non-receipts.
- **`poll-reprocess`.** The operator one-shot ([Operations](OPERATIONS.md#poll-reprocess-r151)) turns a recorded `IGNORED` image message of yesterday or today into a job under these rules. The R119 recheck of ignored slips shares its core. A shadowed variable in the poll's cursor-advance input was fixed; behaviour differs only for re-read C4 messages.

## Group chat summary marker and cycle — revision 38 (R146, disabled)

The poll is also the source of the [group chat summary](../SERVICE_CATALOGUE.md) service (`group_chat_summary`, `mw-group-chat-summary.timer`, every 2 minutes). Source only; nothing is enabled. With `group_chat_summary_enabled` false the poll does not read or write the summary state and behaves as before.

- **Who gets a summary.** (R152: the members of a group are its participants plus the senders of the messages in the 3-day window, because Instagram can stop listing a borrower who left or was removed as a participant; a sender whose username, other than the business account's, matches exactly one borrower counts as a member for referrers, subjects, tokens and labels, and the ambiguity rule and the three-member minimum include them. The summariser reads the window before it resolves, and the poll passes the scan's messages as senders at its one call site in `capture_conversation`. `subjects_sha256` stays the participants-only digest on both sides, so there is no re-mark loop; a change visible only through senders marks the group at its next substantive text.) Only groups with at least three members. Participant borrowers are the group members, other than the business account, whose Instagram username (normalised) matches one borrower's "Instagram Username", enabled or not. Referrers are the participant borrowers that another participant borrower names in "Ref Referrer". Subjects are the participant borrowers with AI Collection enabled who are not referrers; only subjects get the summary, and two or more subjects share one summary. A username that matches two borrower rows skips the group; a group with more than 20 subjects fails with `GROUP_TOO_MANY_SUBJECTS`. A referrer therefore never gets that group's summary on their own page. Speaker roles are decided once per message by the first match: business account, partner, referrer, borrower, other.
- **Routine or substantive.** A fixed rule in code, no model. A message is routine when it has no text (image, video or other), when fewer than `group_chat_summary_min_letters` (default 9) letters remain after removing mentions, emoji, digits, punctuation and spaces (ticks, pings, arithmetic lines, short acknowledgements), or when it is from a partner and starts with one of `group_chat_summary_routine_prefixes` (default `["📌"]`, the daily amount reminder). Everything else is substantive. A longer acknowledgement can pass as substantive and cause one unneeded run; tune the two settings from real use.
- **Cutoff.** `group_chat_summary_cutoff` is the earliest message ever read for a summary: nothing before it is read, so the 3-day window is cut short while the cutoff is later than three days ago. R146 set it to the activation time; R147 moves it back to `2026-11-10T00:00:00+00:00` so the 3-day window governs.
- **Backfill (R147).** `group-chat-summary --mark-all` is a one-shot command that marks every eligible group as due (state row inserted if missing, `changed_at` set only where empty; `last_text_at`, `attempts` and `next_attempt_at` untouched) so the normal cycle summarises its existing 3-day window; it reads participants only, makes no model call or post and prints counts only. See [Operations](OPERATIONS.md).
- **Marker.** Inside the poll's own transaction, a newly recorded substantive text at or after `group_chat_summary_cutoff` sets `changed_at` (if unset) and `last_text_at` in `runtime.group_chat_summary_state` (agent V12). Routine messages never set it. The first state row of a group is created by the first substantive text after the cutoff, so nothing is summarised at switch-on. A change in the group's subject digest (subjects, referrers, participant borrowers) also marks a group that already has a state row, including a group whose last subject was disabled, so its summary row is pruned. An idle scan writes nothing. The table holds no chat text.
- **Summariser cycle.** Per run: select up to 5 groups with a marker, `next_attempt_at` passed and either `last_text_at` at least 600 s ago or `changed_at` at least 600 s ago (R151: a group is due after 10 quiet minutes or 10 minutes after its first new substantive message, whichever comes first; it was 1 hour); stop taking groups after 150 s; with nothing due, exit with no Instagram or model call. Read the group through the same conversation-list route and `history_since` as the poll for the last 3 days, keep the newest 100 messages and nothing before the cutoff, and recompute subjects and roles from fresh master data. A window with no substantive text posts a prune-only command. Otherwise one `claude-opus-5-5` call (low effort, adaptive thinking, text only, no tools, the PROD federation rule only), validation, then `POST /internal/agent/group-chat-summaries` (body exactly `{command}`, at most 16,384 bytes, the shared receipt API's token and policy; replies 200 `{kind}`, 400 `invalid_summary_command` mapped to `POST_REFUSED`, 422 `unknown_borrower` to `POST_UNKNOWN_BORROWER`, 503 to `RECEIPT_API_OUTCOME_UNCERTAIN`; `requestId` must equal the agent's derivation, pinned by one shared test vector in Node and Python). On a stored, unchanged, superseded or cleared reply the marker clears unless a newer substantive text arrived meanwhile (a new wait then starts). On any failure the marker stays and the group backs off from 10 minutes, doubling to 6 hours; the post is an overwrite, so a retry is safe.
- **Model input.** One line per message, oldest first, Bangkok time, role tokens (`business`, `partner`, `referrer_n`, `borrower_n`, `other_n`) instead of names. Placeholders are `[image]`, `[video]` and `[other]` (the API returns nothing finer). Mentions of group members become their token, other mentions `@someone`. Master-data names and usernames are never sent; text typed in the chat is sent as typed.
- **Relevance (R148).** The output schema has a required boolean `relevant`. `false` means the window holds nothing a collection officer needs (group setup, names, rules, greetings, routine reminders, images): it is accepted with no content checks and the run posts this group's prune command (empty borrower list, null summary), counted under `cleared`, so the group's rows are removed and it shows no card and no mark; the marker is cleared and the digest stored. `true` goes through the checks below; a missing or non-boolean `relevant` is `MODEL_OUTPUT_INVALID`. The prompt version is 3 since R152 (2 in R148), so every source digest changes and each group is summarised again once after the deploy. A group that is not relevant still costs one model call per new substantive burst.
- **Output checks.** Headline 1 to 160 and up to four points of 1 to 200 characters per language (Thai and English), speakers only tokens that appeared, no control characters, no run of nine or more digits and no `@`. A failing response is a failed run (`MODEL_OUTPUT_INVALID`, or since R151 one of 15 fixed sub-codes; see [Operations](OPERATIONS.md)); a refusal or `max_tokens` stop is a failed run and the previous summary stays. The agent computes the last speaker and last message time from the newest substantive message.
- **Card text (R152).** Numbered role tokens in the headline and points (`borrower_1`, `referrer_1`, `other_1`) are replaced with role words (Borrower / ผู้กู้, Referrer / ผู้แนะนำ, Partner / หุ้นส่วน, MW Credit, Other / อื่น ๆ; the bare tokens `partner` and `business` are not replaced), and the instructions forbid tokens in the text.
- **Remembered members (R152, agent V13).** `runtime.group_chat_summary_state.member_borrower_ids` (`text NOT NULL DEFAULT '[]'`, a JSON array of borrower Row IDs, at most 16 KB; ids only, no usernames or text) remembers the borrowers seen in a group. A group's members are now its participants, the senders in the 3-day window and the remembered borrowers; remembered ids still in the master count for referrer detection, subjects and the three-member minimum, and ids of deleted borrower rows are dropped. The summariser stores the union after each run; the poll reads the column but never writes it; the subject digest stays participants-only. Accepted risk: a remembered borrower is forgotten only when her row is deleted, so a borrower who truly left stays a subject of that group (if she is also in another group, the newer conversation's summary wins on her card). The SQLite fallback gains the column (`ensure_group_chat_summary_state` for pre-V13 journals).
- **Limits (R152).** The fix learns a departed borrower's id only if her messages are still inside the 3-day window at the first cycle after the deploy, so the release has to run before that window closes. `--dry-run` and `--mark-all` stay participants-based, so a group whose subjects exist only through a departed sender is marked by the poll at its next text.
- **Source digest.** `sourceSha256` covers the ordered (sender id, created time, kind) tuples, the subject ids, the prompt version (2 since R148) and the model (the effort is not included); Meta message ids are not stable across reads and are not part of it. `requestId` derives from the environment, the hashed conversation key and that digest.
- **No text at rest.** Chat text and the summary exist only in memory during a run. Audit plans and results, command output, `last_error` and exceptions carry counts, the hashed conversation key, digests and fixed error codes only.

## Lisa forwards — 22 September 2026

`receipt_forwarding_enabled` applies only after its new `receipt_forwarding_cutoff`. The sender must match the configured `receipt_forwarder_partner_id` through current Partner Instagram username. The group must have exactly three distinct IDs/usernames: that Partner, the authenticated account matching `receipt_group_account_username` (tttlll8709), and one unique AI Collection Enabled borrower. The real sender is preserved; the poll provenance is marked FORWARDED. `receipt_identity.py` re-reads that exact group through the working conversation-list API before extraction and again before posting. Changed/missing/ambiguous membership blocks processing. No inferred borrower based on an image name or caption. Historical ignored messages remain ignored; no backfill is implied.

Unexpected/malformed conversation failures preserve that group checkpoint and do not stop other groups. Partial scans exit nonzero for existing service monitoring; outer directory/authentication failures fail the cycle instead of claiming a complete scan.
