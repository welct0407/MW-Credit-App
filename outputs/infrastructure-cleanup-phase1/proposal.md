## Phase 2 — operational credentials in Secret Manager

Move operational credentials needed by tools/runners before adopting resources through those tools. Do not rotate them merely to relocate them. Inventory identifiers such as `uid`, client ID, tenant, project, datasource UID and secret resource name separately: they identify objects and are not secret payloads.

**Bootstrap must remain outside the store it unlocks.** An operator first uses an existing supported GCP sign-in/ADC path, workload identity or approved external credential to authenticate to GCP; only then can that identity read an authorized Secret Manager version. Terraform backend access must work at `init`, before provider resources and secret lookups. Never place the sole GCP recovery credential or sole backend-unlock mechanism behind that same inaccessible Secret Manager path.

For the proposed external runner, prefer GitHub-issued OIDC federation to a narrowly scoped GCP principal for backend/selected-secret access and separately to an Entra principal for Azure. Establish trust/IAM once through an existing authorized admin route; the runner cannot bootstrap its own missing trust. Verify issuer, audience, repository/ref or environment restrictions, exact Azure tenant/subscription, backend path and allowed secret versions. If that federation cannot be supported, document the existing external private credential path and its rotation/recovery owner before selecting a fallback. Do not invent a Codex OIDC issuer or assume Azure login also authorizes GCP.

Migration unit: one credential and its known consumers. A practical first batch is the existing SQL administrative password and maintained operator helpers, with only read-only identity/connection checks; the already working Cloudflare Secret Manager route needs reconciliation, not a duplicate credential. Create/import secret **metadata and IAM** through Terraform where appropriate; securely add the preserved payload through the secret API/CLI or a genuinely write-only provider field verified for the pinned provider. Fetch it directly into a consumer's environment, file descriptor or private temporary file; never route ordinary passwords/token payloads through generic Terraform resource attributes, outputs or secret-version data sources. Use a numeric tested version for cutover and record which consumer can read it. Keep originals until new-path tests and independent recovery pass; rollback is consumer configuration/version rollback while the original remains valid.

Checkpoint: masked local value comparison where safe, correct principal/version access, denied access from an unrelated identity, one bounded read-only consumer operation, failed-fetch behavior, no payloads in logs/plans/artifacts, original recovery access verified. Tests should not send messages, alter financial data or rotate credentials. Consumer-specific API limitations are recorded rather than hidden by broad privileges.

**Known exception — Google Identity Platform.** `google-beta` 8.6.0 `google_identity_platform_default_supported_idp_config.client_secret` is required, persistent and has no write-only alternative; the provider reads it into state. Its upstream schema does not itself declare `Sensitive: true`. Treat the field as secret-bearing regardless of display masking, keep caller variables sensitive, disable debug/trace logs, restrict/encrypt/version the backend and protect saved plans and state copies. Existing state may already contain this value. Moving its source to Secret Manager does not remove it from state or historical versions. Retain this known exception with explicit documentation; do not claim universal zero-secret state, expand it to ordinary passwords or replace a lost OAuth secret without a recovery/rotation decision. [Pinned provider source](https://raw.githubusercontent.com/hashicorp/terraform-provider-google-beta/v8.6.0/google-beta/services/identityplatform/resource_identity_platform_default_supported_idp_config.go), [Terraform sensitive-data behavior](https://developer.hashicorp.com/terraform/language/manage-sensitive-data).

## Phase 4 — replace VM controller operations with Terraform actions

Recommend a small manually dispatched GitHub-hosted workflow in the infrastructure owner repository, authenticated via the Phase 2 federated identities. It must start and finish while VM-01 is deallocated, have independent backend/auth/receipt access and remain usable from the owner's normal control device. A self-hosted runner on VM-01 cannot start itself. Debian is an alternative only if the owner chooses its persistent-runtime dependency; do not make that service change implicitly. No automatic idle policy or schedule is included.

Terraform 1.14+ supports `azurerm_virtual_machine_power`; its actions include `power_on`, `restart`, `deallocate` and `power_off`. Choose and lock an AzureRM version that demonstrably supports the required action schema. Define three fixed-target actions; preview/invoke an exact address, for example `terraform plan -invoke=action.azurerm_virtual_machine_power.start_vm01` followed by the reviewed `terraform apply -invoke=action.azurerm_virtual_machine_power.start_vm01`. CLI invocation excludes ordinary resource configuration changes; a full infrastructure apply is not required. No lifecycle `action_trigger` should attach power operations to unrelated infra edits. [Provider action](https://registry.terraform.io/providers/hashicorp/azurerm/latest/docs/actions/virtual_machine_power), [CLI invocation](https://developer.hashicorp.com/terraform/language/invoke-actions).

Use `deallocate` for the current Stop behavior. `power_off` leaves the VM allocated and is not the same cost outcome; retained disks/network resources can still cost money after deallocation. Show observed Azure state and distinguish power availability from executor readiness. [Azure states and billing](https://learn.microsoft.com/en-us/azure/virtual-machines/states-billing).

Target remains subscription `50f792fa-803e-4280-833d-1fe60fef5293`, tenant `9e29c895-606a-420b-acc2-1c24375df4d9`, `RG-MWCREDIT/VM-01`, immutable VM ID `0af4bbf5-ce75-43d7-931f-9e8c4a13dfe9`; reverify before operation. Expose an action choice, never arbitrary resource IDs/commands. Reuse the minimum fixed-VM role model; separately inspect the provider's actual async polling calls and scope any necessary operation-read permission. A working Azure login is not evidence that these action permissions are present.

## Phase 5 — runtime credentials and Grafana

Dependencies: Phase 2 bootstrap and per-consumer access work; affected runtime ownership/catalogues and rollback are established. Existing app secret resources are already managed; avoid duplicate secrets. The inventory found 21 Secret Manager resources: 9 DEV application, 7 PROD application and 5 Grafana bridge. Fresh version metadata finds `mw-credit-app-dev-agent-receipt-policy` has no versions; the other 20 containers have enabled versions. The inventory records numeric Cloud Run template references, including the bridge's Google client-secret version 2. These reads do not prove payload correctness, effective IAM, traffic-revision binding or successful consumer access; older enabled versions cannot yet be declared unused.

Batch stable runtime secrets by consumer/environment: DEV first, then separately authorized production consumers; use version pinning/controlled restart or reload and read-only health checks. GCP-hosted consumers should use their runtime identity with secret-level access. For non-GCP hosts, establish supported federation or a separately managed external bootstrap identity before fetching. Preserve old values and originals until both runtime and recovery tests pass. Verify schedules/service switches remain as intended; a restart must not accidentally activate dormant workers.

**Graph OAuth is a distinct mutable-credential batch.** `GraphEmail` locks its existing token-file inode and persists rotated refresh tokens. A read-only Secret Manager mount or periodic overwriting download breaks that contract. First locate every writer/reader and choose one writer. A practical design keeps the locked private operational file, durably rewrites refreshed tokens according to its existing locking semantics, and publishes a recoverable version to Secret Manager through a bounded writer path; ordering, crash recovery and access to the latest usable token must be tested. Do not replace/rename the file behind a held inode lock or let two hosts refresh independently. If a more direct Secret Manager writer is chosen, it needs explicit concurrency/version selection and durable writeback. Preserve current working token state; old refresh tokens may be unusable after rotation, so rollback restores compatible code while retaining the newest usable token, not blindly an old secret version. This is implementation design work, not authorization to refresh tokens during inventory.

**Grafana platform secrets differ from bridge secrets.** The five `mw-grafana-*` secrets serve the alert bridge's OAuth/cookie/HMAC/JWKS/state functions; they are not the Grafana Cloud admin API token or GCP/Azure/Railway datasource credentials. Existing monitoring code provisions those datasource credentials through `secureJsonData`; live Grafana inventory is currently unavailable through the established credential paths. Do not rerun initialization installers that create new credentials or refuse existing UIDs as a migration strategy.

When access is restored within scope, inventory existing datasource UIDs, folders/dashboards, rules, contact points, notification policies and secure-setting presence through the API. Secure values may be write-only and unrecoverable from Grafana; obtain the existing original through its recovery path or explicitly plan a separate rotation. Adopt definitions under Terraform only where import/schema behavior preserves them; provision secret settings from Secret Manager via a narrow runtime API step when provider attributes would persist ordinary tokens in state. Keep exact UIDs, query behavior, alert routes and recipients. Update the dashboard visual guide for any actual dashboard change. Validate datasource connectivity, saved definition parity and the existing alert path with a scoped test; do not create a duplicate monitor/subscription or send a new live notification merely to migrate storage.

## Phase 6 — separately approved retirement

Prepare an exact candidate list after replacement verification, with resource ID, ownership, last consumer/dependency, replacement evidence, private recovery location, cost consequence and rollback limit. The parked production project, controller-only Function/storage/RBAC/registrations/DNS, unused credentials and superseded helpers are **candidates**, not an approved deletion list. Never treat an apparently empty inventory response as proof of no hidden dependency.

Disable/fence the superseded entry point first; observe the agreed acceptance window and verify the replacement and independent recovery path. Check identities, domains, schedules, backups, alert routes and shared storage before deletion. Retain necessary controller operation/audit evidence and credential recovery originals through the agreed retention window. Revoke only exact credentials/roles with no remaining consumers. Any irreversible deletion, lost recovery ability, changed production route or service retirement requires its exact scoped authorization. Do not delete the shared Cloud SQL, receipt bucket, existing user/financial records, integration runtime or application-managed sign-in stores as cleanup.
