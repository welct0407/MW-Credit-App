## SQL boundary: EXECUTE-only on V78 is insufficient

V78 declares `pwa_submit_selected_charges_v1(text)` and `pwa_command_status_v1(uuid,text,text)` SECURITY INVOKER, revokes PUBLIC execution and gives no runtime grants. Submit reads Partners, locks Borrowers, reads Cash Accounts/Cash Holders, inserts Payments and inserts the journal. The ordinary Payments trigger chain invokes current V59 `post_payment`, reads/locks Loans and Charges, writes Payment Allocations and Repayments, updates Payments/Loans and invokes current refresh/history functions. Granting only EXECUTE on V78 cannot authorize this path. Granting direct table writes to the reader or command login would expose the financial engine outside the intended API boundary.

Recommended future design, subject to A review: a higher immutable migration creates narrow SECURITY DEFINER submit/status, current-actor resolver and actor-scoped retained canonical identity/receipt-descriptor lookup wrappers owned by a new proposed `mw_pwa_command_owner` NOLOGIN/NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOINHERIT/NOBYPASSRLS role. Runtime cannot SET ROLE to or inherit this owner. Keep V78 bytes and invoker functions unchanged; wrappers invoke them under the restricted owner. Do not transfer existing business tables/triggers to this role or make a privileged migration administrator the runtime's definer owner.

Proposed runtime ACLs are CONNECT on `loan_manager_dev`, USAGE on only the wrapper schema, and EXECUTE on precisely the reviewed wrapper signatures. No direct EXECUTE on V78, no journal/table SELECT/INSERT/UPDATE/DELETE/TRUNCATE, no schema CREATE or owner membership. Audit effective PUBLIC/inherited database CONNECT/TEMP and function permissions too: revoking a login-specific grant does not remove PUBLIC access. Do not globally revoke shared privileges merely to satisfy this plan; any required PUBLIC/consumer reconciliation needs a separately reviewed exact compatibility delta. A fixed safe search path must withstand temporary-object shadowing whether TEMP remains available or is removed in that later design. A schema and wrapper names/signatures must be settled in the later SQL design; none is invented as an existing object here. Actor resolution and retained canonical identity/receipt-descriptor lookup must use narrow wrappers (or be combined inside a command wrapper) rather than direct Partners/journal SELECT if this interface is adopted. The current 4E disposable candidate reads Partners and retained canonical journal data itself, so it is not yet a production wrapper client. Return only the authenticated actor's needed descriptor/identity data; do not expose arbitrary journal rows.

The definer owner needs explicit source-table/column and function permissions for the actual full-chain trigger path. A source-level starting set is Partners, Borrowers, Cash Accounts, Cash Holders, Payments, Loans, Charges, Payment Allocations, Repayments and `pwa_payment_commands`, plus `cash_account_holder`, V78 submit/status and invoked payment/refresh/history functions. This set is **not a complete executable GRANT matrix**: row locks require additional privileges and current V60–V73 triggers may traverse materialized/cache/history sources. Before any grant proposal is applied, produce a disposable catalogue of exact effective trigger/function definitions, object/column ACLs and owner memberships, then exercise the full path under the proposed login/owner. Expand only for observed required dependencies; never `GRANT ALL`, all public tables/functions or future default privileges. Keep journal UPDATE/DELETE/TRUNCATE denied to owner and login.

Wrappers must pin `current_database()` to `loan_manager_dev` and `session_user` to the exact proposed command IAM SQL login; reject a different database/login before any work. Wrappers require fully qualified objects, a safe explicit search path with temporary-schema shadowing prevented, no dynamic SQL driven by caller identifiers, PUBLIC execution revoked in the same migration, and current verified actor scope on submit and status. Inputs alone are not a cryptographic identity: only the separate authenticated service can supply canonical actor values. A compromised command runtime remains within the deliberately authorized command interface; no claim of a database-native Firebase verification is made.

Required future permission proof: exact valid submit/status succeeds under command login; direct Payments/journal writes, arbitrary actor/source reads, cross-actor status, wrapper/schema creation, owner SET ROLE, direct V78 execution and PROD access fail; AppSheet-style contenders still preserve accounting and triggers. Run maintained database CI once for that later migration batch. Reserve no migration number and issue no GRANT/ALTER now.
