## Terraform and secret boundaries

Use separate state ownership for Grafana definitions and GCP monitoring infrastructure; avoid dual ownership with existing application roots. GCP adoption candidates are `mw-grafana-events`, `mw-grafana-dispatch`, `mw-monitoring`, the five bridge secret containers, associated exact SAs/IAM and existing uptime/Firestore dependencies once enumerated. Adopt current configuration first with deletion protection and no-change proof; do not redesign resources during import.

Terraform owns secret container metadata and reviewed IAM, not ordinary payloads or token creation resources. Inject Grafana provider auth transiently from a reviewed numeric Secret Manager version; never put tokens in tfvars, outputs or saved evidence. Datasource/contact credentials may enter provider state through secure configuration fields: verify the pinned schema before choosing ownership. Keep such payload fields outside Terraform through a narrowly scoped API step unless a tested write-only mechanism exists; document any unavoidable exception explicitly. Redaction alone does not remove state exposure. Preserve original credentials and recovery until cutover and rollback are proven.
