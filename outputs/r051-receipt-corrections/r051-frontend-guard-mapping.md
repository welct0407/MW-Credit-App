# R051 database guards and frontend correction guidance

Owner requirement, 6 October 2026, `Sentinel_2a86562ef7e481918e837f84f4f29e48`: expected invalid operations must be prevented and explained in the app before save, rather than first appearing as database errors. Hiding a button or locking a field alone is insufficient. Keep database checks for stale clients, concurrency, direct SQL and other writers.

This is a **mapped/proposed design**, not a saved app configuration or GUI acceptance result. DEV remains V69; V70 is a local candidate. No frontend access, schema exposure, permissions change or live migration is performed by this document. Preserve existing independent role/security predicates, Ref/IsAPartOf relationships, supported ordinary CRUD and source ownership. Do not introduce blanket reversal-only rules or locks on every previously saved row.

For editable inputs, prefer existing `Valid_If`, `Required_If`, filtered Ref choices and `Invalid value error` text. Preserve valid current values while filtering new choices; do not use a universal existing-row exemption. For actions and immutable rows, combine availability/editability rules with an always-visible explanation in the relevant detail/form: use an existing Description or Show field where possible, otherwise a proposed app-only virtual Show field. No stored database column is needed just to show a reason. Name the blocked action and the next supported step; do not replace a destructive action with a misleading informational action using the same label.

The messages below are Thai/English candidates, consistent with the bilingual app convention. Use the existing language-preference expression or display both languages. Each explanation must appear when its restriction applies, even when the corresponding action is hidden. A confirmation on an allowed delete summarizes its source-owned effects and preserved independent rows; confirmation is not a substitute for rejecting a known invalid operation.

## Edited receipt capacity: remove the existing-row bypass

Use the **proposed** borrower, date, target and method to form the same eligible set `E` as the payment engine. An owned charge whose current remainder is zero must still be considered when it remains in the proposed scope. A charge that fails the new scope is not restored to eligibility merely because the old receipt paid it. For each `c` in `E`:

`editable capacity(c) = synchronized Amount Remaining(c) + this receipt's existing Allocated Amount to c`.

Sum only over `E`. This excludes other receipts and excludes this receipt's old allocations outside the proposed scope. Check nonnegative component consistency and the supported command's preparation state separately; `Loan Close` must use its existing prepared-source semantics, not a guessed new principal charge. The retained prepared charge remains a separate obligation when a closing receipt is corrected/deleted.

Candidate `Eligible Outstanding` expression using the already-proposed `Eligible Charges` list:

```appsheet
SUM([Eligible Charges][Amount Remaining])
+ SUM(SELECT(
  Payment Allocations[Allocated Amount],
  AND(
    [Ref Payment] = [_THISROW].[Row ID],
    IN([Ref Charge], [_THISROW].[Eligible Charges])
  )
))
```

Candidate amount validation, composed with existing independent authorization and command-specific checks:

```appsheet
AND(
  ISNOTBLANK([_THIS]),
  [_THIS] > 0,
  [_THIS] = ROUND([_THIS]),
  IN([Allocation Method], LIST(
    "Single Full", "Single Partial", "Receive All", "Lump Sum",
    "First-day Auto", "Loan Close", "Selected Charges"
  )),
  IF(
    IN([Allocation Method], LIST(
      "Single Full", "Receive All", "First-day Auto", "Loan Close", "Selected Charges"
    )),
    [_THIS] = [Eligible Outstanding],
    [_THIS] <= [Eligible Outstanding]
  )
)
```

These are design candidates, not validated saved expressions. Confirm the current `Eligible Charges` formula against SQL and the parent reviewer's exact saved predicates before application. A posted Selected Charges receipt supports selection replacement through normal source UPDATE: V59's `a00` preparation removes its old generated results before `a1` validates the proposed scope and posting recreates the results. Do not blanket-lock the selection. Validate dependencies, every proposed charge and exact eligible capacity; incompatible replacement rejects atomically and preserves the old receipt/results. Cover both compatible and incompatible replacement in regression and GUI acceptance. A financial edit is revalidated; unchanged legacy metadata-only edits should not acquire new invalid-state requirements without assessing their supported backend behavior.

Acceptance examples: a receipt of 20 on a charge of 110 leaves 90; editing that same partial receipt has capacity 110, so 30 is valid and 111 is invalid. If another independent receipt paid 5, capacity is 105. Moving to a different eligible charge with remainder 50 does not add the old charge's 20: new capacity is 50. Reject zero, negative, fractional and over-capacity edits before save; full methods require equality. Test own fully paid charge, changed borrower/date/target, unchanged metadata, Error/Processing states and missing/security-filtered allocation data. Client missing-data cases must not be treated as zero or authoritative eligibility.

## Expense dependency visibility: small, trustworthy exposure only

OLTP does **not** contain Cash Ledger, so a `SELECT(Cash Ledger[...])` expression is not an implementation. The expense form's selected account determines the proposed holder; its submitted/stored holder can lag until SQL normalization and sync. Current cross-holder validation must use the selected account owner without reintroducing the previously rejected account/holder formula cycle.

Design preference: expose only a read-only, expense-keyed dependency summary to the owning app, for example `Expense ID` plus `Has linked reimbursement` (or a count), and a supported navigation target to the existing OLAP reimbursement workflow. The server summary must include every relevant manual Expense Reimbursement link regardless of whether the user's detail list happens to hide it. It need not expose ledger amounts, counterparties or unrelated cash history. These names describe a data contract, not existing database/AppSheet columns.

First assess whether an existing read-only source/view can supply that summary. If not, a narrow view/app source or equivalent approved projection needs separate dependency/security/regeneration assessment; **do not add it to V70** or invent a stored editable flag. Confirm expense-key coverage, orphan/missing-row semantics, authorization, sync freshness, and whether a boolean reveals information beyond the user's allowed expense scope. Do not broaden Cash Ledger access merely to compute a count.

With an explicit known-false flag, ordinary authorized cross-holder/nonpositive corrections remain available subject to their other rules. With true, proposed amount must stay positive and proposed selected-account holder must stay Tommy; same-Tommy account changes remain available. With missing/unknown dependency state, display **ยังตรวจสอบรายการคืนเงินไม่ได้ กรุณาซิงค์หรือเปิดแอปวิเคราะห์ / Reimbursement status is unavailable.
