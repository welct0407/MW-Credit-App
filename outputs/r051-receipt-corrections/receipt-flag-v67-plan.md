These are parent observations, not executor GUI claims.

V67 preserves the allowed stored values using a validated, named `CHECK ("Delete Requested" IS NOT NULL)`, then removes the column's explicit NOT NULL attribute. The replacement is installed before the old constraint is removed, and both DDL statements run in the normal PostgreSQL Flyway migration transaction. There is no null-permitting window. `DEFAULT false`, Boolean type, V65 insert/mixed-command guards, invoker permissions, source-delete triggers and Ref/IsAPartOf remain unchanged. No source data is modified.

PostgreSQL explicitly documents this check as functionally equivalent to NOT NULL, with NOT NULL being more efficient ([constraint documentation](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-NOT-NULL)). The observable differences are intentional: `pg_attribute.attnotnull=false`, `information_schema.columns.is_nullable=YES`, and an explicit NULL produces SQLSTATE23514/check violation naming `payment_delete_requested_present`, instead of23502/not-null violation. This is not `CHECK(flag)`, which would accept NULL and reject false.

The candidate's GUI benefit is an inference, not a guarantee. AppSheet documents table regeneration and action required-value validation, but its PostgreSQL documentation does not establish whether its schema importer also examines CHECK constraints. It may still infer Required, or retain an existing override. Actual regeneration, saved metadata and action validation must decide whether this representation resolves the cycle.
