### Immediate event-driven notification delta — owner revision, 11 October

This supersedes minute polling as the normal notification trigger. Owner requires prompt push from PWA and integration-agent commits; the minute Scheduler tick is recovery only. Add no table, Debian change or CDC service. V88 is still unapplied, so B can add the wake-up to its reviewed capture definition.

After an actual new event INSERT (check FOUND/ROW_COUNT; not a dedupe no-op), call `pg_catalog.pg_notify('mw_pwa_notifications_v1','')` in the same transaction. The fixed empty signal carries no source IDs, identities, financial data or destination secrets. PostgreSQL releases it only after commit; rolled-back captures never signal. Notifications are visible to database users and are not an authorization boundary: spoofed/duplicate signals may only request guarded durable-queue inspection. The durable event/delivery tables remain authoritative. The PostgreSQL notification queue is finite; long transactions on listening sessions impede cleanup and queue exhaustion can fail a notifying transaction at commit. Keep the owned listener out of transactions; record this operational limit without changing instance settings. [PostgreSQL NOTIFY](https://www.postgresql.org/docs/17/sql-notify.html)

The activated notify runtime owns one dedicated PostgreSQL client, separate from its existing pool(max2): at most three connections per instance, plus transient revision overlap. Use the existing verified connector/IAM identity with fresh connection setup on reconnect; no new password. Register handlers, verify exact database/principal/capability, execute and commit LISTEN in autocommit, then drain the durable backlog. Repeat this order on every reconnect. Listening before inspecting durable state closes the initial subscription race; duplicate observations are harmless through existing unique keys/leases. Never run provider work or a long transaction on the listener. [PostgreSQL LISTEN](https://www.postgresql.org/docs/17/sql-listen.html)

Implement one coalesced wake/drain coordinator per process shared by listener signals and authenticated recovery HTTP requests. A wake arriving during a drain sets a pending flag; clearing/consuming that flag must not lose the last wake. Bound each batch, yield between batches and re-arm promptly while runnable backlog remains. Do not busy-loop on future retries or transiently unavailable recipients. The one-minute recovery request covers missed hints, known retry deadlines and listener outages. Multiple instances/revisions can receive the same hint; durable RPC claims and fencing continue to control effects. No exactly-once push or permanent single-instance assumption.

Listener error/end marks it disconnected, closes the failed client and starts one bounded exponential reconnect loop with jitter (for example 1s to 30s). Prevent duplicate reconnect timers/clients. Startup/reconnect always performs LISTEN then catch-up, even when no signal arrives. A transport keepalive and a small bounded liveness query on the autocommit listener can detect half-open sockets; this is connection health, not business polling. Recovery HTTP must still drain through the normal pool if LISTEN is temporarily unavailable. Log only state/count/duration/reason, not payload or source data; expose sanitized listener-connected/last-catch-up state for operational evidence.

Notify Cloud Run only: while activation is enabled use minimum1 instance, 1vCPU/512Mi and instance-based billing (`cpu_idle=false`). Disabled remains min0/no listener; jobs remains min0/request-based. Prefer service-level minimum so tagged old revisions are not unintentionally kept warm. Cloud Run may restart a minimum instance, so “normally seconds while healthy” is an intended measured behavior, not a hard delivery SLA. Trap SIGTERM: stop new claims/reconnects, close LISTEN, allow only bounded in-flight completion and close resources within the platform's shutdown window. Forced termination after send-start uses existing uncertain/fencing recovery. [Cloud Run billing](https://docs.cloud.google.com/run/docs/configuring/billing-settings), [minimum instances](https://docs.cloud.google.com/run/docs/configuring/min-instances), [container shutdown](https://docs.cloud.google.com/run/docs/container-contract)
