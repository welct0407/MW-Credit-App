## F — identities, secrets, storage and capacity

Separate build, infrastructure operator, runtime, deployment and SQL migration authority. DEV/preview credentials cannot impersonate the production runtime/deployer, read PROD secrets/state or update PROD Hosting/services. Runtime cannot deploy, administer IAM, read Terraform state or acquire migration/journal-owner authority. Build jobs receive public build configuration and artifact permissions only; secret payloads belong to explicitly permitted runtimes or integration operators.

Use OIDC/attached identities and version-pinned Secret Manager. Create secret containers/IAM declaratively; keep payload initialization outside Terraform where supported. OAuth-provider resources may still place sensitive values in provider state: document that exposure and keep that state private rather than claiming Secret Manager eliminates it. Do not copy DEV UID pin, native receipt catalog or VAPID values into PROD. Retain originals/recovery until replacement access is independently verified; no credential rotation/migration is needed merely to prepare this batch.

Cross-project SQL access is an explicit later additive binding plus IAM database principal and minimum database grants, not implicit permission from creating a service account. Keep retained instance ownership unchanged. Automatic IAM authentication replaces application passwords; IAM login does not itself grant business table access. [Cloud SQL IAM administration](https://docs.cloud.google.com/sql/docs/postgres/add-manage-iam-users).

Current generated and native receipt roots are DEV-specific. Production catalog/receipt prefixes require exact owning AppSheet/SQL evidence and a separate private catalog. Do not infer native PROD names by replacing dev with prod. Keep object GET/create permissions scoped to the exact approved purpose/prefix; no bucket listing or broad object administration for application runtime.

Prepare a connection budget using actual maximum connections, existing measured peaks, administrative/recovery reserve and all coexisting services. Account for revision rollout overlap and per-instance pool maxima: sum(max instances × pool maximum × simultaneously active revisions), plus other database consumers. Existing documented alert threshold160/200 is a monitoring boundary, not spare capacity. The historical DEV503 remains unproven; it does not justify increased limits. The contained foundation without data probes needs no pool. Later initial data probes can propose a small explicit envelope only after capacity evidence is attached; no instance flag/size/network change is part of this batch.
