## Preparation checklist

For a requested replacement from PROD, start with the [DEV refresh runbook](Development_Refresh_Runbook.md) to select apps/database/both, preserve unreleased work and manage recovery and old-app deletion. This checklist supplies its automation/source isolation gate.

Both DEV apps, including replacement copies, remain in **Prototype** mode under the owner's 18 September 2026 rule. Do not switch them to Deployed mode or run/require deployment checks. Retain automation definitions and intended schedules/states; record any prototype-mode execution limitation without deploying DEV or claiming unexecuted tests passed.

1. **Record the starting point.** Use [Environment Inventory](Environment_Inventory.md) to identify both DEV app UUIDs, versions and database host/instance. Capture rollback versions before edits. Old deleted apps and versions bound to PROD are not safe DEV rollback targets. Record the PROD baseline version used for automation parity and any active release differences.
2. **Prevent premature execution.** Before copied/restored automation can execute, pause affected bots/schedules until their routes are reviewed. Review schedules immediately; never assume a copy disables them. Do not run processes or make test writes through unverified paths. Record temporary pauses and intended final states.
3. **Verify sources and navigation.** Confirm every business table uses DEV and test companion navigation in both directions: DEV OLAP ↔ DEV OLTP. Inspect expressions/actions and notification/deep links for embedded PROD app IDs. Review exports, webhooks and external tasks for DEV destinations; a DEV database alone does not isolate their effects.
4. **Reconcile automation parity.** Inventory bots, called processes/tasks/actions, and database/external schedules. Record each app/job, event/condition, schedule/time zone, side effects/destinations, expected and observed state, evidence and release-owned difference. Match the released PROD definitions and enabled/disabled states except documented environment substitutions and in-progress release changes. Do not disable a reviewed job merely because it is not needed for today's test. Do not re-enable superseded financial bots or add a second scheduler for an existing job.
5. **Restrict notification recipients.** Review To/CC/BCC, dynamic recipients, nested calls, reminders, error alerts and all channels. DEV delivery is exclusively to `welct0407@mw-credit.com`; AppSheet push tasks use `LIST("welct0407@mw-credit.com")` as the sole recipient expression. Preserve intended event, template and processing behavior. Unknown/unsafe paths remain disabled while corrected and are recorded as parity blockers; unavailable isolation needs an explicit owner-approved exception. PROD destinations are not changed by DEV preparation.
6. **Save and recheck.** Save reviewed settings and reload the current editor's definitions/Automation list. Verify actual enabled/disabled states, routes and versions. Confirm one active scheduler per business job and environment; reconcile temporary pauses. Do not disable database integrity/calculation triggers as a substitute. Record sanitized evidence in the release log/checklist.
7. **Test affected behavior.** Use the new AppSheet GUI with synthetic DEV data and applicable SQL checks. Reviewed owner-only notification delivery is permitted. When scheduling/notifications change, check execution/delivery as relevant through available logs and owner feedback; saved recipient settings alone do not prove delivery. Record expected/actual results and unavailable checks. Preserve or retire fixtures safely so later scheduled runs do not cause unintended test activity.
   Apply AGENTS.md Section 6's DEV warning-clearance gate to both apps: save/reload, rerun current-editor diagnostics, resolve all editor configuration warnings/errors including pre-existing ones, and record final versions and evidence. Outstanding applicable issues or unavailable required editor checks block preparation completion and promotion readiness. Prototype status, deployment-only findings and unrun/unavailable deployment checks do not; a general preparation exception does not waive the editor gate.
8. **Close preparation.** Update the release record and applicable environment/development-difference records with saved versions, parity results, remaining blockers/exceptions and test evidence. Preparation is complete only when isolation and intended parity are verified, or a specific owner-approved exception is recorded. At the end of development, provide the readiness recommendation required by [AGENTS.md, Section 6](../AGENTS.md).

Use one inventory/checklist and link it from these documents; do not maintain a duplicate bot list here. [Database workflow](../database/README.md) governs SQL migrations; AppSheet configuration and scheduler activation must be recorded separately where Flyway does not manage them.
