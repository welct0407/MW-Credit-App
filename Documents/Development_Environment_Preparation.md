## Preparation checklist

1. **Identify and preserve.** Verify app IDs/internal names, database host/instance, current modes and rollback versions against the inventory. Record released baseline and unreleased work. The database name alone does not establish DEV. Preserve unrelated tasks' work.
2. **Pause before exposing copied data.** Pause affected DEV writers/jobs before refresh and keep replacement apps inaccessible while sources or recipients are unverified. Restored PROD contacts must not be available to active DEV notification jobs. Keep old/new duplicate schedulers from overlapping; never disable integrity/calculation triggers.
3. **Verify DEV sources and navigation.** Bind business tables to DEV and check DEV OLTP ↔ DEV OLAP links. Inspect affected external exports/webhooks/files separately; a DEV SQL connection does not isolate shared external destinations.
4. **Apply owner-only DEV recipient settings.** Follow the procedure below before deployment/resuming bots. Retain a compact mapping of each DEV override to its production recipient configuration so RC preparation can restore it. Do not change Partner email data for routing.
5. **Restore intended automation.** Preserve released bot definitions, schedules/time zones and intended states plus recorded unreleased differences. Superseded jobs remain disabled. Use the [canonical-app guard](Release_Workflow.md#scheduled-bot-execution-guard) for scheduled processes: allow the actual DEV/PROD internal names, exclude RC names. Update the DEV literal for replacements; don't change frozen RCs or live PROD during DEV setup. Confirm one executing scheduler per business job/environment.
6. **Deploy DEV.** Once sources, recipient settings and guards are ready, run the initial deployment check for an undeployed/replacement app, resolve applicable findings and mark it Deployed. Already-Deployed apps require no repeat check or mode toggle. Save/reload and check both DEV editors for zero configuration warnings/errors. This is the intended future setup; no live deployment was performed by this documentation update.
7. **Test once, then reuse.** Confirm both apps open/sync, relevant navigation and affected workflows. Test owner-only delivery using appropriate synthetic DEV events; record actual recipient resolution, execution and owner receipt separately. Check intended schedule execution through current Automation Monitor. Keep event conditions and audit fields unchanged; the DEV recipient override replaces recipient selection only. Reuse evidence until inputs/routes/jobs change; don't repeat every schedule per development task.
8. **Close.** Reconcile pauses, saved versions, DEV recipient overrides, guard/schedule evidence and any limitations in the existing log/environment/difference records. Update affected model documentation only for actual model changes. Report readiness honestly; a prepared environment does not itself prove a feature is ready to promote.

## DEV recipient override procedure

An owner-only recipient override does not guarantee that an event condition fires or a device receives the message.

Record each overridden task/property and its corresponding exact production expression/value, with the PROD baseline version or existing evidence reference. Reuse this compact mapping; update it for new/changed routes or intervening production changes. RC preparation restores those production values before freeze and verifies the saved substitutions once. Never carry DEV owner-only literals into PROD through App Upgrade or repair recipients manually after upgrade.

For apps-only or combined refresh, apply the overrides to copied apps before enabling notification execution. For database-only refresh, retain the app-level overrides and verify they still isolate delivery before jobs resume. Do not rewrite the owner's, Lisa's or other Partner email records, login identities or permissions as part of notification setup/refresh. Do not automatically undo any earlier data edits; reconcile observed exceptions within the requested scope.

Routes that cannot deliver to an email/AppSheet user need a documented owner-only destination or remain paused while resolved; do not invent an SMS number or assume the email override isolates an external provider. Only the affected unresolved path pauses; independent work continues. Ordinary DEV tasks reuse established coverage, rechecking only changed routes/dependencies or concrete routing problems.

Keep push notifications as push notifications; an email address can identify the receiving AppSheet user. Actual device delivery still needs that user's registered device. See [AppSheet notification routing](https://support.google.com/appsheet/answer/11513089?hl=en). No conversion of every job to email is implied.
