# Development environment preparation

Owner revision, **R009 / 19 September 2026**. DEV, RC and PROD use **Deployed** mode. DEV runs intended scheduled bots and notifications with owner-only delivery controlled by database master data. Partners.Login Email stores the distinct sign-in identity; Partners.Email stores the possibly shared delivery address. Shared app expressions exclude the recorded actor's Partner Row ID, then select delivery addresses. This supersedes direct DEV literals and the earlier deferral. PROD changes only through authorized promotion.

Use this procedure for initial setup, requested refresh/replacement/restore, or affected routing changes. Routine feature work reuses verified setup. For refresh scope, recovery and old-app deletion use [DEV refresh](Development_Refresh_Runbook.md). RC preparation uses [Release Workflow](Release_Workflow.md), not DEV recipient overrides: RC reads PROD data but scheduled business execution is blocked.

## Preparation checklist

1. **Identify and preserve.** Verify app IDs/internal names, the complete database instance/host/database tuple, current modes and rollback versions against the inventory. Record released baseline and unreleased work. DEV and PROD share an instance, so host or instance alone does not establish the environment. Preserve unrelated tasks' work.
2. **Pause before exposing copied data.** Pause affected DEV writers/jobs before refresh and keep replacement apps inaccessible while sources or recipients are unverified. Restored PROD contacts must not be available to active DEV notification jobs. Keep old/new duplicate schedulers from overlapping; never disable integrity/calculation triggers.
3. **Verify DEV sources and navigation.** Bind business tables to DEV and check DEV OLTP ↔ DEV OLAP links. Inspect affected external exports/webhooks/files separately; a DEV SQL connection does not isolate shared external destinations.
4. **Apply owner-only DEV recipient data.** Follow the procedure below before deployment/resuming bots. Preserve distinct login identities; set delivery addresses to the owner in the DEV database only. Reuse shared expressions. Document any remaining non-Partner or legacy routing separately.
5. **Restore intended automation.** Preserve released bot definitions, schedules/time zones and intended states plus recorded unreleased differences. Superseded jobs remain disabled. Use the [canonical-app guard](Release_Workflow.md#scheduled-bot-execution-guard) for scheduled processes: allow the actual DEV/PROD internal names, exclude RC names. Update the DEV literal for replacements; don't change frozen RCs or live PROD during DEV setup. Confirm one executing scheduler per business job/environment.
6. **Deploy DEV.** Once sources, recipient settings and guards are ready, run the initial deployment check for an undeployed/replacement app, resolve applicable findings and mark it Deployed. Already-Deployed apps require no repeat check or mode toggle. Save/reload and check both DEV editors for zero configuration warnings/errors. This is the intended future setup; no live deployment was performed by this documentation update.
7. **Test once, then reuse.** Confirm both apps open/sync, relevant navigation and affected workflows. Test owner-only delivery using synthetic DEV events; record recipient resolution, execution and owner receipt separately. Check intended schedule execution through current Automation Monitor. Preserve event conditions and recorded actors. Test each mapped actor with shared addresses; unknown actors resolve to no recipients and require investigation. Reuse evidence until inputs/routes/jobs change.
8. **Close.** Reconcile pauses, saved versions, DEV recipient overrides, guard/schedule evidence and any limitations in the existing log/environment/difference records. Update affected model documentation only for actual model changes. Report readiness honestly; a prepared environment does not itself prove a feature is ready to promote.

## DEV recipient override procedure

The heading is retained for existing links; the override is now **DEV data**, not an app expression. After schema migration, verify each Partner's Login Email against their distinct sign-in account. Never derive identity from already-overridden delivery data. Set both current Partners.Email values to `welct0407@mw-credit.com` using a transaction pinned to the verified DEV host; preserve Row ID, Login Email, role, permissions and financial fields. The guarded [R009 DEV data runner](../scripts/database/Set-R009DevRecipients.ps1) checks the current two-partner population; review it if the population changes. Never include this DEV address update in a promotable Flyway migration.

Preserve the same approved recipient expression in DEV, RC and PROD. It resolves the recorded transaction actor through Login Email to Partner Row ID, excludes that ID, then selects distinct nonblank Email values. Blank/unmapped actors yield no recipients; correct their mapping rather than guessing or comparing delivery email. RC uses PROD contacts after source rebinding; no routine expression restoration for converted routes. Historical restoration maps remain evidence only and must not overwrite R009 logic.

For database-only or combined refresh, restore PROD, apply reviewed retained migrations, then override DEV delivery data **before** jobs or app writes resume. For apps-only refresh, preserve/recheck existing DEV delivery data and reapply retained R009 app logic if PROD predates it. On first migration, distinct pre-override Partner emails seed Login Email; verify that assumption before promotion. Preserve actual login accounts and authentication. Never copy DEV delivery overrides into PROD.

Check To/CC/BCC, nested tasks, error alerts and non-Partner destinations once for setup/changed routing. Existing push tasks remain push; do not switch notification channels. Non-Partner routes need their own documented owner-only destination; record legacy literals and restore only those during RC preparation. A database address override does not isolate a hard-coded or external recipient automatically.

Routes that cannot deliver to an email/AppSheet user need a documented owner-only destination or remain paused while resolved; do not invent an SMS number or assume the email override isolates an external provider. Only the affected unresolved path pauses; independent work continues. Ordinary DEV tasks reuse established coverage, rechecking only changed routes/dependencies or concrete routing problems.

Keep push notifications as push notifications; an email address can identify the receiving AppSheet user. Actual device delivery still needs that user's registered device. See [AppSheet notification routing](https://support.google.com/appsheet/answer/11513089?hl=en). No conversion of every job to email is implied.
