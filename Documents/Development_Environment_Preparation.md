## Preparation checklist

1. **Identify and preserve.** Verify app IDs/internal names, database host/instance, current modes and rollback versions against the inventory. Record released baseline and unreleased work. The database name alone does not establish DEV. Preserve unrelated tasks' work.
2. **Pause before exposing copied data.** Pause affected DEV writers/jobs before refresh and keep replacement apps inaccessible while sources or recipients are unverified. Restored PROD contacts must not be available to active DEV notification jobs. Keep old/new duplicate schedulers from overlapping; never disable integrity/calculation triggers.
3. **Verify DEV sources and navigation.** Bind business tables to DEV and check DEV OLTP ↔ DEV OLAP links. Inspect affected external exports/webhooks/files separately; a DEV SQL connection does not isolate shared external destinations.
4. **Apply owner-only DEV master data.** Follow the procedure below before deployment/resuming bots. Keep recipient expressions the same as PROD. Existing hard-coded owner-only DEV overrides require a one-time, recorded reconciliation to the shared data-driven expressions after coverage is proven; do not repeat this per release. Paths outside master data receive a targeted documented treatment, not an assumption that changing Lisa covers them.
5. **Restore intended automation.** Preserve released bot definitions, schedules/time zones and intended states plus recorded unreleased differences. Superseded jobs remain disabled. Use the [canonical-app guard](Release_Workflow.md#scheduled-bot-execution-guard) for scheduled processes: allow the actual DEV/PROD internal names, exclude RC names. Update the DEV literal for replacements; don't change frozen RCs or live PROD during DEV setup. Confirm one executing scheduler per business job/environment.
6. **Deploy DEV.** Once sources, recipient data and guards are ready, run the initial deployment check for an undeployed/replacement app, resolve applicable findings and mark it Deployed. Already-Deployed apps require no repeat check or mode toggle. Save/reload and check both DEV editors for zero configuration warnings/errors. This is the intended future setup; no live deployment was performed by this documentation update.
7. **Test once, then reuse.** Confirm both apps open/sync, relevant navigation and affected workflows. Test owner-only delivery using appropriate synthetic DEV events; record actual recipient resolution, execution and owner receipt separately. Check intended schedule execution through current Automation Monitor. Respect creator exclusions rather than changing audit fields to manufacture a passing test. Reuse evidence until inputs/routes/jobs change; don't repeat every schedule per development task.
8. **Close.** Reconcile pauses, saved versions, DEV contact overrides, guard/schedule evidence and any limitations in the existing log/environment/difference records. Update affected model documentation only for actual model changes. Report readiness honestly; a prepared environment does not itself prove a feature is ready to promote.

## DEV recipient master-data procedure

The preferred approach is **data only**: set the existing notification email field on the owner's and Lisa's DEV Partner rows to `welct0407@mw-credit.com`, and cover any other reachable recipient records needed to ensure owner-only delivery. Both rows can use the same email if the existing schema permits it. Don't change Partner keys/names, financial ownership, login identities, permissions or PROD records. Check once whether the email field also participates in uniqueness, authentication/security filters or identity lookups; resolve actual conflicts rather than blindly rewriting an identity field.

During initial setup and **every PROD-to-DEV database refresh**, use a reviewed DEV-only data update: assert DEV host/instance, identify rows by stable keys, check expected affected rows, apply in a transaction, then read back and verify resolved recipients before writers/bots resume. Keep sensitive before-values outside Git. This is an environment-specific data override, not a versioned Flyway migration to promote to PROD. For apps-only refresh, preserve the existing DEV database and verify the override remains effective. Record and reuse a compact coverage list; newly introduced recipient records/routes must remain owner-only before execution.

Check all actual recipient paths once: To/CC/BCC, nested notifications, lookup/list expressions and relevant error/integration destinations. Changing Lisa alone is sufficient only if all messages resolve through that row. Literal recipients, other contact tables, user-based recipients, SMS numbers or provider-managed alerts are not redirected by a Partner email change. Keep only an unresolved affected delivery path paused while resolving its data/configuration treatment; independent development continues. No blanket rewrite of notification tasks is required.

**Known creator-exclusion case:** recorded R008 recipient expressions select `Partners[Email]` while excluding the payment's `Created By` email. If both Partner emails equal the owner and the owner creates the payment, both rows are excluded: recipient list is empty. A different approved DEV test actor can exercise the existing delivery path; otherwise record that self-created-event delivery is not covered. Do not fake `Created By`, remove the exclusion in PROD, or promise that duplicating an email guarantees every notification. If the owner wants self-notification despite that rule, treat that behavioral change separately with its intended DEV/PROD scope.

Keep push notifications as push notifications; an email address can identify the receiving AppSheet user. Actual device delivery still needs that user's registered device. See [AppSheet notification routing](https://support.google.com/appsheet/answer/11513089?hl=en). No conversion of every job to email is implied.
