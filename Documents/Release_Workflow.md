# Release workflow

Detailed procedure for [AGENTS.md Section 6](../AGENTS.md#6-release-development-and-production-promotion). Read only the stage needed for the current task; the standing rules in AGENTS.md still apply. New releases use the structured delta and helpers below. Existing active releases may keep their equivalent exact-value records; do not transcribe historical evidence just to adopt a new format.

Use one release change log with a linked checklist/evidence folder when needed. New releases keep exact AppSheet targets in `outputs/<release>/release-delta.json` and generate the checklist from it using [the release tools](../scripts/releases/README.md). The change log remains the authoritative narrative history, decisions and approval record; it links the exact delta instead of duplicating it. Existing releases may retain equivalent exact-value records. SQL continues to use the Flyway manifest; the JSON helper does not replace it. Maintain the record as work happens, not by reconstructing it at deployment.

At the top of the release log keep a short continuation note, or link the generated **Continue here** section: current versions, completed work, next action, pending decisions/approval scope and evidence links. Update it at a coherent checkpoint or handoff. Start continuation tasks there; read older evidence only when needed. This note summarizes state and never grants authorization.

**Delta-based capture — owner rule, 17 September 2026:** Capture and verify the complete release delta, not the whole app. Complete app exports, full before/after app comparisons and per-save snapshots are optional tools, not prerequisites for development or promotion. Missing export coverage of untouched settings does not require an exception or block authorized edits. This standing rule applies to current and future releases, including R005, and supersedes earlier whole-app coverage requirements and the need for release-specific coverage exceptions. Existing backup/version, environment isolation, warning-clearance and production approval rules remain in force.

**AppSheet warning-clearance gate — clarified by owner, 18 September 2026:** Both DEV apps stay in **Prototype** mode. At DEV completion/readiness and refresh/preparation completion, require zero outstanding **current-editor configuration warnings/errors** and relevant functional tests; do not run or require deployment checks and do not switch either DEV app to Deployed mode. Prototype status, deployment-only findings and unavailable/unrun DEV deployment checks are not readiness blockers. This supersedes those blockers in earlier release records, including R005, without automatically clearing other outstanding tests or granting acceptance/production authorization. PROD still requires zero outstanding AppSheet warnings/errors through editor diagnostics **and deployment checks** before promotion completion/Released.

- At the start, reuse existing applicable diagnostic evidence for the same saved app versions when available; otherwise inspect both apps' current-editor warning/error diagnostics, plus deployment checks **only for PROD**. After the final relevant saves, reload and check the final versions once. Include pre-existing issues covered by the environment's gate, even when unrelated to the changed feature; “unchanged”, “non-blocking” or Runnable/Deployable status is not clearance. Do not hide/dismiss warnings or disable checks merely to obtain a clean result.
- Record each issue's app/environment, affected object, exact warning/error, correction and recheck result in the existing change log/checklist. Record final app versions, check time and evidence of zero warnings/errors for each app. Trace warning fixes through affected consumers, tests and model documentation; if they change the frozen release scope, revise the package and obtain approval for the changed scope under Sections 6.2–6.3 before production edits.
- A remaining applicable warning/error or unavailable required diagnostic check blocks completion/readiness: report **Not ready** for DEV or **Deployment applied; verification incomplete** after production changes, with the unresolved items. DEV deployment checks are excluded, not pending. Keep bot/schedule definitions and record any prototype-mode execution limitation honestly; do not deploy DEV to obtain a test result or assume configuration proves execution. General checklist exceptions do not satisfy the applicable zero-warning gate. DEV evidence belongs to the frozen candidate; PROD must have its own final checks, without comparing to subsequently changed DEV.

## 6.1 Develop and capture the release

1. Read/reserve the release number, define intended behavior and acceptance checks, and identify affected apps, shared consumers and prerequisites. Inspect current definitions/schema and record starting versions and rollback points under Section 4. Reuse completed DEV preparation; rerun it only for setup/refresh or the relevant changed paths under Section 2, not as a mandatory step in every task.
2. Implement the smallest practical, reversible change in DEV. Keep a lightweight running record of every configuration edit made by Codex, including script-driven edits, refinements, warning fixes and known generated/dependent changes. Record affected objects/properties and previous values as they are inspected; an unavailable historical value may be marked unknown rather than triggering a whole-app capture, provided the required rollback version is recorded. Use the checklist itself, concise notes or saved edit payloads; do not export both apps after every save. Consolidate the record at development completion and before handoff/context loss. Store sanitized evidence in Git and private exports outside Git. SQL remains managed through immutable Flyway migrations/hashes.
3. At development completion, maintain stable checklist IDs and exact per-property targets for every release change in each consuming app. Record the object/property path, add/change/remove/rename/reorder operation, previous value when available, final saved/tested DEV value and version, intended PROD value, actual PROD before value, saved PROD observed value/version, evidence and separate DEV/PROD statuses (Pending, Verified, Blocked or Owner-approved exception with reason/approval reference). Capture full expressions, literals, labels, lists/order, nested options and changed blank/default/inherited states without paraphrase or truncation. For new objects, record the settings needed to recreate their tested behavior; for removals/renames, record absence and affected references. Do not inventory untouched defaults merely to prove export coverage. Linked exact-value artifacts can replace duplicated text; “same as DEV” or “configured” is insufficient. Protected values use controlled external references, never secrets or personal data in Git.
4. Cover the changed configuration and its affected dependencies across OLTP/OLAP: tables/columns, expressions, permissions, slices/membership, views and explicit column orders, navigation/events/actions, bots/tasks/templates/schedules, formatting, dashboards and any app-level setting actually changed. Trace changed user-facing fields through the consuming slices/views/entry points. Include automatic changes caused by regeneration or grouped edits by reviewing the affected objects; broaden inspection only when there is evidence of wider effects, conflicting edits or an unreliable change record. Read changed settings missing from exports in the current editor; unrelated omitted settings need no inspection or exception. Include directly affected export/report dependencies under Section 1's AppSheet-first priority.
5. Before declaring development complete or freezing the release, reconcile the running edit record, implementation scripts/payloads, refinements and affected-object readbacks into one complete final delta. Every actual release change must have a checklist target or a recorded superseded/reverted disposition; the final target must match the saved DEV value or intended absence. Capture final readback once per coherent completed change set and repeat only where later edits invalidate it. If a changed value cannot be verified, mark that item pending and resolve it before claiming readiness; continue independent authorized development. Do not block work because untouched configuration is unavailable. Preserve other releases' ownership and resolve overlapping changed properties. A targeted comparison of all recorded changes and affected dependencies is sufficient; a whole-app diff is optional when it helps resolve a specific uncertainty.

## 6.2 Test, recommend readiness and freeze

1. Select the relevant tests from the tiers below, through the current AppSheet GUI and appropriate SQL/configuration checks. Cover the changed behavior and affected consumers; add boundaries, permissions, sync, duplicate/retry/concurrency, schedule, delivery or performance checks only where relevant. Use synthetic/redacted DEV data and the existing test runners; do not rerun unrelated suites without a reason.
2. Record expected/actual results, versions, evidence and unavailable checks honestly. Separate configuration inspection, executed tests and owner feedback. At the end of each development task state **Ready to promote**, **Ready subject to listed checks/owner decision**, or **Not ready**, with reasons, remaining risks and a short owner testing checklist. A task recommendation covers its scope; batch readiness requires all release items and dependencies to be reconciled. Wait for owner feedback before recording acceptance; do not claim tests that were not run.
3. Before promotion, freeze the tested release package: complete delta checklist and exact intended PROD values, saved DEV evidence for changed objects/properties and app versions, test evidence, accepted scope/limitations, exact implementation Git commit, Flyway manifest/hashes and target version, dependency order and coordinated rollback/forward-fix instructions. Full app definitions are optional. Record the package revision in the change log/tracker. For database releases, run `New-Release.ps1` from the clean tested commit while DEV still represents that candidate, before later migrations advance DEV; retain a sanitized manifest/hash record in Git and the runner's original manifest externally. Subsequent documentation commits do not change the pinned deployment commit.
4. Freeze scope, not the entire DEV environment. Later development may continue after capture; promotion and validation use the frozen release package, never current DEV as the acceptance baseline. A change to the candidate requires a new recorded revision, affected tests and renewed acceptance/approval for the changed scope. Retain the prior evidence. If a missing manifest or mixed DEV state prevents isolating the tested candidate, reconstruct and validate it in an isolated test setup or resolve the dependency before promotion; do not bypass runner checks or reset active DEV work.

### Test selection and evidence reuse

Choose by behavior and impact, not task size. Combine rows where necessary; a label that changes a financial choice may need logic tests. Record the selection and results briefly in the existing log, without a second test-plan document.

| Change | Minimum relevant DEV checks | Broaden when |
| --- | --- | --- |
| Documentation/governance/tooling | Links, consistency and affected tool tests; no live app tests for documentation alone | A tool can alter artifacts or falsely report verification |
| UI text, order, visibility, formatting | Exact saved-property readback; open affected view/form in current GUI, verify presentation and relevant conditional visibility | Permissions, workflow actions or calculations also change |
| App expressions, slices, actions, permissions or automation | Normal path plus relevant invalid/boundary cases; affected consumer workflows and saved/synced readback | Retry, duplicate execution, schedules, delivery, access, performance or shared consumers are affected |
| SQL/schema/financial behavior | Flyway validation; relevant existing SQL regression checks; affected app workflow, reconciliation and boundary cases | Add relevant concurrency/idempotency/performance suites for the changed behavior; migration-chain testing when migration behavior changes |

The both-app final zero-warning gate still applies to app release completion regardless of tier. A database-only change affecting apps also needs the relevant consumer checks. Routine route checks follow AGENTS.md Section 2, not a blanket notification test.

- Reuse evidence with a link to the original test date, tested configuration/migration hashes or versions, environment, relevant dependencies, data/setup assumptions, expected/actual outcome and limitations. Check these against the current candidate; the previous test must have passed and still cover the claim. Unknown or changed relevant inputs require the affected check to run again. A new chat, documentation commit or unrelated app version alone does not invalidate a behavioral test.
- Optional `fingerprint` output records hashes of explicitly selected implementation/test files plus the test context. Compare fingerprints to detect changes cheaply. Equal hashes are supporting evidence only: live settings, database state, role/device and dependencies outside those files still need an applicability review. Never describe reused evidence as a new execution.
- Capture final saved delta readbacks and both-app final diagnostics after the last relevant save. Reuse already captured final evidence for that exact saved state; do not repeat it just to produce a second report. PROD needs its own saved-delta readbacks, final diagnostics and focused GUI smoke checks. DEV tests do not substitute for these.
- Batch model updates once per completed change set and after promotion. Update affected dictionary rows and overview sections together; retain production values and label DEV differences. Do not rebuild or restyle the entire workbook. Coordinate a single writer when parallel tasks touch the shared workbook; an active task must not overwrite another task's rows.
- Prefer existing runners and compact script outputs to repeated manual browsing. Read the release tools' technical documentation only when using them. Use one agent for routine work; parallel development is useful only with independent scopes and coordinated shared DEV ownership. Model/Fast-mode choices remain the owner's settings; do not change them automatically.

## 6.3 Approve and promote the complete batch

**Exact configuration contract:** The checklist's PROD target must equal the frozen tested DEV configuration for every release-owned property except explicitly recorded environment substitutions (such as database bindings, app IDs/links, recipients, access or DEV theme). Record each substitution's exact DEV and PROD values and reason; do not infer additional differences while deploying. Any business/UI deviation requires a revised, tested and approved release scope. Freeze the exact-value artifacts and the completeness reconciliation with the package so no later DEV edit can change the deployment instructions.

1. Recheck current PROD identities, affected configuration/dependencies, schema/migration history and relevant automation against the package's expected starting state. Review drift and intervening releases where they intersect the delta; preserve unrelated PROD changes. Resolve overlapping changes and update/retest the candidate where necessary instead of replacing whole apps. Preserve PROD database bindings, companion app IDs, access rules and recipients; record environment substitutions only where the release delta touches them. Do not repeat recipient or companion-link validation in promotion preflight/final checks unless Section 2's targeted triggers apply. No whole-app comparison is required for this preflight.
2. Confirm owner acceptance and explicit authorization for this package/revision before production writes. Record current rollback versions for each affected app, a verified restorable database backup for database writes, report backups where applicable, and the ordered deployment/recovery plan. State any required write pause or temporary scheduler pause. Existing specific approval suffices; a release number, approval-reference string or push does not grant approval.
3. Apply all included changes as one managed release batch in the dependency-safe order recorded in the package; database and two app saves are not a single atomic transaction. Promote only the exact tested commit/manifest through the existing runners. Review every pending migration from PROD's current version to the candidate target: all must belong to this approved batch or an explicitly approved prerequisite. Do not silently include another release, skip an intervening migration, edit applied files or run from a newer checkout containing later migrations.
4. Apply every checklist item using its frozen exact PROD value, including all nested options and ordered lists, and record saved versions/evidence. Verify already-matching items rather than dropping them from the checklist. Reconcile regenerated metadata and each slice/view independently. Do not substitute a similar-looking configuration or assume a successful save applied every property. Preserve production automation/recipient behavior except approved changes; reconcile temporary pauses before closure. Never copy DEV financial/test data.
5. On failure, record exactly what was applied and stop dependent steps. Assess current state before retrying; use the coordinated rollback or reviewed forward fix within the approved scope. Do not replay financial operations or restore a database over newer writes without explicit recovery authorization. Partial application is not a completed release.

## 6.4 Validate production and close

1. After the final saves, reload the affected PROD configuration and verify **every delta checklist property against its frozen exact PROD target**, including changed nested settings, list order, removals and explicit environment substitutions. Use actual saved values from targeted exports or the current editor, not the edit payload, to mark each row Verified. Check affected dependencies and known generated changes; investigate unexpected results where observed. Record and resolve missing, mismatched or unverified delta items before closure. Complete delta verification is sufficient; full PROD before/after exports or whole-app comparisons are not required. Successful sync or zero warnings alone does not verify the delta. Preserve per-item evidence in the release package. For SQL, verify migration history/hashes, affected objects and appropriate read-only correctness checks. Never use subsequently changed DEV as the post-promotion comparison target.
2. In the current production GUI, sync/open both apps and exercise the affected entry points, checking field visibility, labels/order, references, permissions and intended read-only/edit access. Inspect forms without saving and cancel them. Reuse accepted DEV behavioral tests as supporting evidence; do not repeat the entire DEV suite in production. Production financial writes, mutating actions and forced notification tests require separate explicit authorization. Record unavailable role/device/conditional or write-dependent checks and their practical limits; configuration checks cannot be described as successful delivery/execution.
3. Do not mark Released while a required item is missing, mismatched, Pending or Blocked. Use **Deployment applied; verification incomplete** for partial application/validation and list outstanding items. Only an explicit owner-approved exception may close an otherwise unverified item; retain its reason, impact and approval, and report it as an exception, never as verified. New defects/corrections must remain linked to the release and be retested; do not silently drop scope to close the batch.
4. After validation, reconcile the final checklist, release tracker and change log; update the environment inventory, development differences and both model documents when applicable. Close only the promoted release's differences, preserving later DEV work. Record actual deployment date, PROD app/SQL versions, pinned commit/manifest, owner acceptance/approval, results, exceptions and rollback instructions. Keep these distinct from development completion.
5. Finish the required commit/push and report the release number, implemented and verified scope, readiness or deployment status, documentation/evidence, rollback point and any remaining owner checks/downstream limitations. A documentation-only methodology change requires no live app tests or product release number; it does not assert that existing environments already satisfy the new policy.
