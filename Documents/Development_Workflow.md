## Data operations and access boundaries

Codex Cloud is the normal executor for an explicitly authorized data task. Identify the exact app or project/instance/host/database tuple, intended role, records, business date/timezone and expected effects before execution. An environment label or a successful connection alone is not target verification. Reuse existing authorization only within its recorded scope.

- Prefer bounded AppSheet reads/operations where appropriate; inspect relevant current metadata and dependent SQL/automation effects. For access-only probes, use `Action: Find` with **`Properties.Selector = FILTER("Loans", FALSE)`** and expect zero rows. **`Rows: []` alone does not bound a Find.** Authentication/read transport success proves no write permission, financial correctness or complete table access.
- PROD OLTP and OLAP reads use **Personal network secrets** `APPSHEET_PROD_OLTP_KEY` and `APPSHEET_PROD_OLAP_KEY`, restricted to **`api.appsheet.com`**. Keep the key/app pairing and destination restriction; reject redirects to other hosts. Do not print, copy, export or commit secret values, and do not enable DEV API as a workaround. Recheck the affected PROD API switches and bounded probes after App Upgrade under the existing inventory procedure.
- Existing installed `gcloud` and `/workspace/.setup/cloud-access` provide private **IAP SSH** access to Debian with **strict host verification** and no public port 22. Use the established setup in place; do not print private setup files, disable host checking, open ingress, expand IAM or introduce another credential/network path. An unexpected host identity is a blocker to that connection.
- Keep DEV SQL administrator access separate from the **PROD restricted reader**. A reader's `SELECT 1`, sudo availability or prior successful correction grants no general PROD DML right. A future write needs its own authorized execution identity/path; if unavailable, hand off or resolve within explicit authority rather than elevate the reader.
- Before PROD writes, require the applicable verified restorable backup and recovery plan. Rehearse the exact bounded change on an isolated restored copy where required by the operation, protect keys/before-state and expected affected counts, and preserve financial integrity/calculation/audit triggers. Use transactions, locking/concurrency guards and failure rollback appropriate to the reviewed operation. No unrestricted exports or DEV financial-data copy into PROD.
- Reconcile the actual commit and independently read back the resulting business state through the appropriate read path. A timeout/unknown result requires reconciliation before retry; never replay a financial operation or notification on assumption. Preserve auditable reversal/void/adjustment semantics and later writes. Record sanitized evidence and private recovery references, not borrower details or raw backups.
- The Debian agent's API-first/reviewer SQL fallback has its own [catalogue and governance](https://github.com/welct0407/MW-Integration-Agent/blob/main/docs/POSTGRESQL_OPERATIONS.md#governance). An interactive owner task does not change that runtime's role checks, activation flags, audit, retry or messaging authority.

Secret storage is environment-specific and always outside repositories: VM-01 retains the existing `C:\Users\MWCredit\Documents\ChatGPT` project credential location; Codex Cloud uses the existing managed secrets and private setup outside the three checkouts; Debian keeps private service configuration under `/etc/mw-integration-agent` or `/etc/mw-report-charts` and Codex-owned files under its service home. Leave application-managed sign-in stores in place. References may name paths and secret identifiers, never values. Git publication, bucket metadata access and a successful logical restore each prove only their own scope of recovery.

## Handoff and fallback contract

Dots passes a compact task/continuation note to the executor containing:

1. Requested outcome, owning repository/branch/starting commit, affected paths/objects and current Open release if applicable; identify concurrent work and draft PR dependencies.
2. DEV/PROD target and verified identities, intended role/account, route (browser, Cloud CLI/IAP, VM-01 or Debian), and model preference. Pass secret **references**, never values.
3. Exact authorization already granted, exclusions and any approval still needed for a concrete next action; distinguish local commit, publication, deployment, data writes and notifications.
4. Baseline/rollback references, tested package/app/SQL pins, completed checks with timestamps and expected/actual results, and remaining tests or uncertainties.
5. Next bounded action and stop conditions. The executor returns changed paths, branch/commit, tests/results, actual applied state, recovery evidence and blockers so Dots can coordinate the next step without repeating completed work.

If cloud UI authentication, CAPTCHA, a Windows-only tool or a local access dependency blocks progress, use the authorized VM-01 task and its mapped Chrome/Edge identity. **Cloudflare remains on VM-01 by current choice; correct account/zone DNS and tunnel read verification is still outstanding.** A previously running tunnel does not establish current control-plane access. Do not bypass challenges or substitute accounts.

If Cloud startup, IAP or a helper fails, preserve sanitized failure evidence and use an existing authorized fallback only if it satisfies the same identity, host trust and target controls. Built-in private HTTP/browser access is not proof of native SQL/SSH capability. If no suitable route exists, stop the dependent mutation and continue independent repository/review work; do not invent permissions or a public-port workaround. Historical startup failures remain useful diagnostics, not a current blanket ban on Cloud work.
