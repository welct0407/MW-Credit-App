## Handoff and fallback contract

Dots passes a compact task/continuation note to the executor containing:

1. Requested outcome, owning repository/branch/starting commit, affected paths/objects and current Open release if applicable; identify concurrent work and draft PR dependencies.
2. DEV/PROD target and verified identities, intended role/account, route (browser, Cloud CLI/IAP, VM-01 or Debian), and model preference. Pass secret **references**, never values.
3. Exact authorization already granted, exclusions and any approval still needed for a concrete next action; distinguish local commit, publication, deployment, data writes and notifications.
4. Baseline/rollback references, tested package/app/SQL pins, completed checks with timestamps and expected/actual results, and remaining tests or uncertainties.
5. Next bounded action and stop conditions. The executor returns changed paths, branch/commit, tests/results, actual applied state, recovery evidence and blockers so Dots can coordinate the next step without repeating completed work.

If cloud UI authentication, CAPTCHA, a Windows-only tool or a local access dependency blocks progress, use the mapped Chrome/Edge identity on VM-01 through this **manual browser fallback**:

1. Dots prepares a scoped prompt with the exact service/tenant, authorized action, completed evidence, expected result and evidence to return.
2. The owner starts VM-01 local Work in the mapped session and supplies that prompt. Local Work performs the bounded task; the owner returns its results to Dots for reconciliation and continuation.
3. Count that manual session as busy in any future idle-shutdown design. Automatic startup/idle policy remains review item 3, design pending; this document enables no controller policy or schedule.
