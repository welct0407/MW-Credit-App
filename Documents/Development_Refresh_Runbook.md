# DEV refresh from PROD

Established 16 September 2026. Use this runbook when the owner requests a future DEV refresh. It covers the existing two-environment architecture: one database and OLTP/OLAP apps per environment. This document does not execute or schedule a refresh and is not production deployment approval.

## 1. Select scope and preserve work

Record the requested mode in one dated refresh change log, with linked evidence under `outputs/` where useful. Reuse an existing release log if the refresh belongs to that release; a routine environment refresh does not itself need a new feature release number.

| Mode | Refresh | Preserve and reconcile |
| --- | --- | --- |
| Apps only | Copy the PROD OLTP/OLAP definitions into replacement DEV apps | Existing DEV database/data; current DEV themes; selected unreleased app changes; compatibility with the existing DEV schema |
| Database only | Replace the application database on the existing DEV instance from a PROD logical dump | Existing DEV apps/IDs/themes; DEV instance settings/credentials; reapply reviewed unreleased migrations needed by those apps |
| Both | Refresh the DEV database and replace both DEV apps | DEV instance identity, DEV themes and selected unreleased work; validate the database before connecting the replacement apps for testing |

If only one app is explicitly requested, replace only that app and reconcile links in its retained DEV companion. Do not broaden the request to the database or other app replacement. If “refresh DEV” does not establish the mode, resolve that before writes; proceed with read-only preparation meanwhile.

Before changes:

1. Read [AGENTS.md](../AGENTS.md), the [release tracker](Release_Tracker.md), [environment inventory](Environment_Inventory.md), active release records and [development differences](Development_Changes.md). Verify live identities/versions; dated inventory entries are not proof of current state. Record source PROD app versions, database schema/Flyway version and intended refresh cutoff. If PROD is mid-deployment or verification is incomplete, establish a coherent source checkpoint and record its known limitations before copying it.
2. Identify concurrent sessions, in-progress tests, unsynced DEV edits and unreleased work. Agree a bounded maintenance window for the affected shared DEV apps/database; separate Git work can continue. Preserve definitions, exact property changes, migration hashes, fixtures that must survive and test evidence before replacing anything. List each release as **reapply**, **retain untouched**, or **owner-authorized discard**. A refresh is not permission to lose undocumented/unreleased work. Already-frozen promotion packages remain immutable; do not impose a production-wide DEV freeze from the older conversation recommendation.
3. Check cross-component compatibility. Apps-only refresh must work with the retained DEV schema; database-only refresh must restore all schema prerequisites for the retained apps. For both, define the final combination of PROD baseline plus selected DEV changes. Reconcile an incompatible scope with the owner rather than silently expanding it.
4. Record rollback and recovery before mutation: current DEV app IDs/versions and recoverable definitions for affected apps; a restorable DEV database backup before database replacement; DEV grants/ownership/settings, schedules, links, access settings and theme values. App version numbers alone are not recovery after deleting the app. Keep private backups/raw exports under `C:\Users\MWCredit\Documents\ChatGPT\AppSheet-Loan-Project`, with paths/hashes and restore evidence in the log, never contents in Git. An archive listing alone is not a restore test.
5. Record the exact targets, downtime, replacement/reapplication sequence, data handling, recovery and old-app deletion gate. The owner's scoped refresh request authorizes its necessary DEV replacement and the old-app cleanup below once validated; do not repeatedly seek the same approval. Resolve ambiguous targets, unreleased-data loss or additional destructive scope before proceeding. No PROD app/database/recipient changes, instance replacement, credential rotation or collection-service operations are included.

## 2. Database refresh procedure

Default to `pg_dump` → recreate the **DEV application database** → `pg_restore` → reviewed Flyway migrations. Keep the existing DEV Cloud SQL instance, connection identity, users, credentials, network policy and instance settings. Whole-instance restore/clone is an alternative only when separately requested and reviewed. Use the configured direct SSL connection and established external credential handling.

1. **Verify endpoints and quiesce DEV.** Read `database/environments.json`, verify the connected host/instance and database, and assert source and destination instances differ. Both databases may be named `loan_manager_prod`; the name must never identify the destructive target by itself. Pause DEV users/writers, old DEV AppSheet bots, database jobs and external schedules; settle or explicitly preserve unsynced edits. Prevent reconnection during replacement. Leave PROD writers/automations unchanged. Coordinate the source app/schema capture with other sessions so no PROD schema/configuration change straddles the refresh checkpoint.
2. **Capture a consistent source archive.** Use compatible PostgreSQL tools and a full custom-format application-database dump (`--format=custom`, `--file`, `--no-owner`, `--no-acl`), with schema, data, sequences and `public.flyway_schema_history`. Use a private file path and check the exit code, archive contents, timestamp and SHA-256. Do not use `scripts/database/Export-Schema.ps1` as the refresh backup: it is schema-only and deliberately excludes Flyway history. Do not restore an old DEV history table over the PROD schema. The dump represents its own snapshot, not a promise to match continuously changing PROD data. PostgreSQL documents consistent dumps and custom archives in [pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html).
3. **Review restore prerequisites.** Inventory required extensions/versions, schemas, owners, grants, database encoding/locale/settings and scheduler/external destinations. Prepare required supported extensions and an explicitly reviewed restore table-of-contents list for Cloud SQL restrictions; record any skipped entry and how its dependency is supplied. Never filter out Flyway history or business objects just to make restore pass. Inspect pg_cron/other job metadata and prevent copied schedules from executing during restore; do not rely only on pausing AppSheet bots. Follow [Cloud SQL dump/restore guidance](https://docs.cloud.google.com/sql/docs/postgres/import-export/import-export-dmp) for extension handling.
4. **Replace only the DEV application database.** After verifying the DEV recovery backup and target again, disconnect only its remaining sessions through a maintenance connection on the verified DEV instance, then drop/recreate the intended database with reviewed DEV ownership and database settings. Do not drop the instance, affect other databases or use Flyway `clean`. This is an authorized DEV restore operation, not a new schema migration or permission to rewrite migration history. Capture exact commands/results without secrets; maintain any reusable implementation in `scripts/database/`.
5. **Restore and reinstate DEV access.** Restore into the empty DEV database with `pg_restore --no-owner --no-acl --exit-on-error` and the reviewed TOC where needed. For custom archives, ownership suppression must be applied at restore time; `pg_dump --no-owner` alone is insufficient. Check every error and keep DEV unavailable on failure. Reapply the recorded DEV object owners/grants/default privileges and database-specific settings; review security-definer function ownership. Instance roles/passwords are not copied from PROD. See PostgreSQL's [pg_restore options](https://www.postgresql.org/docs/18/app-pgrestore.html).
6. **Reconcile the restored baseline.** Verify schema/objects, constraints/indexes, sequence state, extensions and complete Flyway history/checksums against the source archive/checkpoint. Compare appropriate row counts and aggregate/fingerprint evidence tied to that snapshot, not later live PROD totals. Keep raw records and private validation outputs outside Git; report redacted aggregates. Include an actual restore verification before declaring the refresh successful.
7. **Reapply selected DEV work.** From the reviewed Git commit, use the existing `Invoke-Flyway.ps1 -Environment development` runner for `info`, `validate`, then `migrate` and `validate`. Inspect the full pending migration set first; it must exactly match the retained/reapplied releases and their prerequisites. The runner migrates all pending files in that checkout, not a release-number selection. Restore PROD history intact, then apply higher immutable migrations normally; never baseline, repair, edit checksums or skip intervening versions to hide drift. Review backfills and data assumptions on the refreshed dataset. No automatic replay of historical fixture/seed scripts. Retained DEV fixtures require an explicit, isolated recovery/recreation plan with no key collisions.
8. **Isolate restored data and automation.** Record the permitted copy/data-handling scope and DEV access. Keep copied borrower data/documents private; use synthetic/redacted examples and synthetic records for mutating tests. If masking is required for the intended DEV audience, apply a reviewed DEV-only procedure preserving keys, relationships and calculation consistency before access. Inspect copied storage paths, integration destinations and scheduled requests; no DEV test may write shared PROD documents or invoke PROD services. Restore desired job states only through Section 4's preparation and validation gates.

SQL history and schema must advance together. For example, if PROD is V20 and retained DEV work is V21–V22, restore PROD schema/data/history at V20, then apply the reviewed V21–V22 files. These are illustrative versions, not current deployment instructions.

## 3. App refresh procedure

Use the current AppSheet editor and new app interface. The old DEV apps stay available as recovery candidates until replacements pass validation; pause their writers/schedules during cutover so old and new copies never run the same DEV jobs concurrently.

1. **Capture the current DEV appearance and recovery state.** For each affected DEV app, record its exact current theme mode, primary/accent color values and relevant branding settings with version/evidence before copying. Carry those values to its replacement; do not guess a color, take PROD's theme, or assume OLTP/OLAP use the same value. If the current theme cannot be read, resolve it from verified evidence or the owner before finalizing. Also retain the DEV names, intended access settings and recoverable definitions from Section 1.
2. **Copy PROD definitions to replacement DEV apps.** Copy each requested PROD app at the captured version with temporary, clearly recognizable DEV replacement names. Preserve the PROD app. Establish controls that prevent a new copy executing bots or accepting writes while it may still reference PROD; inspect copy options and do not assume bots are disabled. If safe containment cannot be established, stop before copying. Avoid duplicate database/data creation or document copying unless explicitly part of the plan. Keep both old and new app IDs in the refresh record.
3. **Rebind every data source.** Point all business tables/views in each replacement to the verified DEV database, checking host/instance, schema and table/view mappings individually. Review auxiliary sources, file/template paths and integrations as well. Keep database-connection labels as evidence only; never infer a safe target from a label. Regenerate only where necessary, comparing saved metadata/formulas, references, permissions, slices and views afterward. In a combined refresh, the database must first reach its planned final schema.
4. **Rebuild within-DEV linkage.** Map the new DEV OLAP ID to the new DEV OLTP ID and vice versa; if one app is retained, use that retained ID. Inspect actions, expressions, deep links, notification links, bookmarks and tracked launch/configuration references for both PROD IDs and obsolete DEV IDs. Replace DEV-facing references and verify actual navigation in both directions. PROD links continue to join the PROD pair. Record stale external shortcuts requiring owner replacement.
5. **Restore DEV appearance and selected work.** Apply the captured DEV theme/color values to the corresponding replacements and retain clear DEV display names. Reapply only the preserved release-owned configuration differences with their exact expressions/properties and dependency checks. Compare the final result with the captured PROD baseline plus the documented DEV substitutions/differences, including all changed slices and explicit form/detail view orders.
6. **Preserve automation with owner-only delivery.** Retain PROD bot/event/process/task definitions, schedules/time zones and intended enabled/disabled states, adjusted for the selected DEV changes. Route every DEV notification exclusively to `welct0407@mw-credit.com`; use `LIST("welct0407@mw-credit.com")` for push recipients and inspect To/CC/BCC, nested calls, reminders, alerts and other channels. Review export/webhook targets. Run the [development preparation checklist](Development_Environment_Preparation.md); unresolved routes stay disabled as blockers. Restore intended states only when old duplicate schedulers are stopped and all routes are safe. Record any copy-specific deployment/sharing setting needed for intended schedules to work; do not equate definition parity with execution.

## 4. Validate, cut over and delete old apps

Use the same refresh checklist for evidence and status (**Pending**, **Verified**, **Blocked**, or an explicitly **Owner-approved exception**). Record the expected state, saved observed value/version and evidence; do not create a second duplicate inventory.

Apply AGENTS.md Section 6's warning-clearance gate to both final DEV apps in every refresh mode: save/reload, rerun current-editor diagnostics and deployment checks, resolve all warnings/errors including pre-existing ones, and record final versions and zero-warning evidence. Outstanding issues or unavailable checks block declaring DEV ready and deleting the old apps; a general checklist exception does not satisfy this gate.

- **Database, when refreshed:** successful restore, reconciled baseline, exact retained migration set applied/validated, required objects and DEV access correct, no unintended job executions, and both apps compatible with the resulting schema.
- **Both DEV apps in every mode:** saved definitions confirm DEV-only business bindings; current-GUI sync/load succeeds; OLTP ↔ OLAP navigation stays in DEV; representative affected forms/details, Refs, permissions and calculations work. Check shared-table consumers and any changed slices/view orders. Use scoped synthetic test writes only after isolation is verified. Database-only refresh does not authorize app redesign; reconcile any compatibility gap within scope or report it.
- **Replacement apps:** captured DEV theme values match saved settings and visible appearance; intended users can open them; retained release changes are present; expected schedules/states and owner-only recipients are verified. Use available automation logs and a controlled synthetic test when appropriate; record unavailable natural scheduled-run or device-delivery checks rather than claiming delivery from configuration alone.
- **Cutover:** update the canonical DEV IDs/links and start URLs, arrange reopening/resyncing clients without replaying old pending edits, and ensure exactly one active scheduler per business job. Make replacements available only after the source/link/isolation checks pass. No production write or forced PROD notification is part of validation.

**Delete the old DEV apps only after all required replacement checks pass**, recovery artifacts are verified, unreleased work is preserved/reapplied, and no required DEV link or active writer still depends on an old ID. Record the exact old IDs and verify each is a DEV app distinct from PROD and the replacement. Then delete only those old app definitions, retaining shared databases, files/templates, historical reference sources and private recovery artifacts. If the UI couples app deletion to backing-data deletion, do not proceed until an app-only deletion path is verified. Existing DEV access/schedules must not be duplicated while waiting.

For a requested app refresh, old-app deletion is part of completion; do not leave extra copies silently. A missing prerequisite means **refresh prepared/applied; validation or cleanup incomplete**, with the blocker reported. No app deletion occurs in database-only mode. If an exceptional check is owner-waived, record its practical limit; source isolation, correct identities and recoverable work cannot be inferred from that waiver. Recheck replacement load/navigation after deletion, and record deletion evidence and final versions.

## 5. Recovery and closure

On failure, stop dependent steps and keep unsafe DEV paths unavailable. Before old-app deletion, return to the captured old app configuration only if it is compatible with the database currently in place; never restore an app version that points DEV at PROD. For a failed database refresh, restore the verified pre-refresh DEV backup with its matching history/app definitions and recheck isolation. App restoration alone cannot reverse a database replacement. Reconcile any writes made since the recovery point before restoring over them. After old-app deletion, recovery uses the preserved definitions or a fresh reconstruction; do not assume deleted app IDs or version history are recoverable, and remap links if IDs change.

Update the change log, environment inventory, development differences and release links for retained work. Update both model documents if model content or app-specific availability changed; do not present newer DEV-only work as production. Record mode, source checkpoint/cutoff, old/new IDs and versions, database/Flyway commit/hashes, backup/recovery references, theme values, automation/link checks, tests, cleanup/deletion results, exceptions and remaining owner checks. Commit/push sanitized documentation and any reviewed scripts under the standing repository rule. Private dumps/credentials/data remain outside Git, and their backup coverage must be stated separately.

Finish with a concise result distinguishing **DEV ready**, **validation incomplete**, or **rolled back**, including where to open the final DEV apps and what owner checks remain. A refreshed environment is not automatic acceptance or production-promotion readiness for an unreleased feature; affected tests must be rerun if refreshed data/configuration changes their assumptions.
