# Promotion documentation checklist

Use this register for **every product release**, from DEV capture through PROD closure. Put its rows in the existing release checklist/log; no separate narrative report is needed. The release workflow governs live validation; this register governs documentation closure.

## Completion rules

1. During DEV work, record the release checkpoint in `Development_Changes.md` and link its concise change record/tests (exact delta optional). Preserve production references and label unpromoted model changes. At freeze, identify affected document rows.
2. Before closure, enumerate `Documents/` recursively and compare its paths with this register. Add/classify any new or moved file; no silent omissions. The generator below compares inventory and flags uncatalogued paths. Inspect relevant sections, not the full contents of every file or historical record.
3. Give **each document its own row**, with release number, disposition and a section/row/evidence link or concise reason. Dispositions: **Updated**, **Verified current**, **Not applicable**, **Preserved history**, **Pending**, **Blocked**. `Verified current` requires reading the relevant final content for this release; file existence or a previous task's claim is insufficient. No generic “documentation updated” checkbox.
4. The three **Always** records require Updated or Verified current. Conditional records require an update/current-content verification when triggered; otherwise use Not applicable with a reason. Historical records normally use Preserved history; never rewrite dated decisions as fresh facts. Repeated closure may verify already-correct entries instead of touching them again.
5. Cross-check release number, DEV/immutable RC/PROD-before/PROD-after versions, deployment date, implementation/Flyway pins, final evidence tag, concise scope, tests/approval and remaining differences across affected records. Link the machine-readable manifest and table/substitution verification, including each RC's corresponding PROD theme. Close **only this release's** differences; preserve later DEV work, environment substitutions and DEV-only fixtures. If DEV capture was omitted, reconstruct its dated checkpoint from retained evidence, label it retrospective and explicitly close it.
6. No Pending/Blocked, missing row or uncatalogued path may remain when declaring documentation closure complete or marking Released. If runtime validation passed but documentation is unfinished, report **Production validated; documentation closure incomplete** and retain tracker status `Deployment applied; verification incomplete` with the documentation cause. Gaps do not themselves require rollback or repeated live tests. Correct an already-Released entry found incomplete with a dated repair note; its status is not proof of complete documentation.
7. Complete applicable model/workbook consistency checks, link checks and intended-file review, then commit/push and link publication. These rows supplement basic App Upgrade validation and applicable SQL/external verification; they do not alter frozen deployment targets or require fresh Deployment Checks.

## Checklist generation and evidence

`node scripts/releases/delta.mjs render DELTA.json NEW-CHECKLIST.md` includes all document rows with Pending status. For releases without an optional delta or with existing checklists, run `node scripts/releases/documentation.mjs NEW-DOC-CHECKLIST.md` and link the output from the release log. Use the bundled Node runtime. Fill documentation rows during closure; preserve completed evidence and use a new path when regenerating. Generation does not verify documents or authorize Released.

Outside Documents, reconcile the machine-readable release manifest, frozen RC identity/version evidence, source/substitution mapping (including themes), Markdown change record/checklist, optional delta, basic/targeted verification evidence, applicable Flyway manifest and recovery/retention record. Commit/push final evidence and verify the unique release tag. The document rows do not replace these gates or make the delta a manual deployment recipe.
