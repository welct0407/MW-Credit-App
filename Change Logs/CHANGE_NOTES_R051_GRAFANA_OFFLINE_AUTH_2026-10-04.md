## Standards discovery correction and bounded rollout plan

Parent supplied native UI evidence that there are no scope or additional authorization-parameter controls. The candidate now advertises a fixed prompt=consent query on the authorization endpoint in both generated issuer discovery documents. This is the existing standard consent flow, not an expiresWithSession exception. [RFC6749§3.1](https://www.rfc-editor.org/rfc/rfc6749#section-3.1) permits the endpoint query and requires clients to retain it when adding parameters. The locked provider rejects duplicate prompt/scope parameters; conflicting/overwritten consent never creates offline authority. Explicit same-owner browser approval remains mandatory. No request scope or prompt is silently changed by the server.

The original staged resource metadata addition of offline_access is removed before any production rollout. [MCP2026-07-28 refresh guidance](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#refresh-tokens) permits clients to add it from AS discovery and says protected resources should not list it. Resource/WWW-Authenticate scopes remain mcp:events and mcp:read. [OpenAI host documentation](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt) is not empirical proof of prompt-query retention or an active offline grant.
