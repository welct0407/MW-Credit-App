# Change notes — R106 chat writes (proposal and confirm), 2026-10-30

## Purpose
The in-app chatbot (read-only since R090) may modify data: the model proposes one exact command, the PWA shows a confirmation card, and nothing executes until the Partner taps Confirm. Owner decisions of 30 October 2026 (fixed): every existing write command of the PWA screens is in scope; writes go through the existing command contracts and command service with the same authorization, idempotency, audit and reconciliation (no raw DML, no reviewer DML tools); a confirm card every time; only Partners flagged `Partners."AI Reviewer"` who also hold the `command` capability may propose or confirm; one tested migration for chat proposal records is approved (DEV first; PROD on a later owner instruction). This note holds the design (Archie) and the implemented changes (below). Status: released to DEV for testing on 30 October 2026, with a Hosting-only follow-up redeploy ([DEV deployment](#dev-deployment-forge-30-october-2026-utc)); not deployed to PROD.

### Design decisions (Archie, 30 October 2026)

| # | Decision | Reason |
| --- | --- | --- |
| D1 | **Execution path: the chat service calls the command service over HTTPS on the Confirm request**, forwarding the Partner's own Firebase ID token (`Authorization: Bearer`), no `Origin` header, `X-MW-Wake-Deadline` as the PWA sends it, client timeout 15 s. The command service already journals the actor from the token, so audit, idempotency (`requestId`), optimistic versions and the busy/reconcile protocol are unchanged. In-process execution is rejected: `pwa_submit_operation_v2` and the payment functions require `mw_app_<env>` membership, and `services/chat/guard.mjs` refuses that membership on the login that runs model-written SQL (keep the refusal; add a regression test). The device offline queue is not used: a chat confirm is online only, nothing is queued on the device. | Simplest reversible design; no new IAM, DB role or grant; the AI Reviewer gate lives in chat code because the command service cannot tell chat requests apart. |
| D2 | **Tool shape: one generic `propose_action` over a static command catalogue**, plus `action_catalogue(operation)` for the argument definitions. Catalogue file `services/chat/assets/command-catalogue.json` (one entry per supported operation: label EN/TH, target rule, fields with type, enum, description, which fields are references the host verifies, `destructive` flag, consequence rules). The host fills `requestId` (= proposal id, `crypto.randomUUID()`), `targetId` for creates, `expectedVersion` (fresh read at proposal time: `_nativeVersion` from the read provider, or `pwa_*_version_v2` through the SQL tool), `predecessorRequestId` for `payment.*` (`pwa_payment_head_v2`), `receiptId:null`; it then validates with `canonicalOperation` / `canonicalCommand` and refuses with a tool error naming the field. A unit test proves every catalogue entry's sample canonicalizes and that the catalogue and `canonicalOperation`'s operation list agree (minus the exclusions below). | Per-command tools would mean ~45 declarations in every round (tokens, drift); one tool plus a catalogue keeps the registry small and the argument contract testable. **As implemented (Byte, 30 October, accepted by Archie)**: the catalogue has 45 entries; `expectedVersion`, `predecessorRequestId` and the card's before-values come from the command service's own record routes (`/api/loan-records/:id`, `/api/borrower-records/:id`, `/api/payment-records/:id`, …) with the Partner's token, not from `_nativeVersion` or the SQL tool, so one path (D1) serves every read and write; every host-owned amount is refused when the model supplies it (correction total, loan-close payoff, settle-all reviewed amount, next-charge amounts, any per-charge split), while `payment.record` keeps the Partner's `amountReceived` (D3). The tool declarations change the prompt digest, so every thread opens a new epoch on its first turn after the deploy (the seed transcript carries the earlier exchanges, as for a model change). |
| D3 | **Payments** (owner answer, 30 October 2026: partial amounts included): `propose_action('payment.record', …)` takes borrower, `amountReceived`, date, method, cash account, notes and optionally the charges to pay (`chargeIds`, or `nextChargeOf:[loanId]` for a loan's next projected charge). The model gives the amount, **never the per-charge split**: the host obtains the split from the command service's own draft routes with the Partner's token, the same code the Payments screen calls. Amount only → `POST /api/payment-drafts/:borrowerId/auto-assign {amountReceived}` (the screen's Auto-assign rule: due charges, newest first, interest before principal; an `unallocated` remainder above 0 refuses the proposal with `AMOUNT_EXCEEDS_DUE`). Named charges → `POST …/review {selectedChargeIds}` and the full remaining of each (`amountReceived` must equal the total, else `AMOUNT_MISMATCH`). Next projected charge of a loan → `GET /api/payment-drafts/:borrowerId?scope=all` supplies `upcoming` (id, date, amounts, `bookVersion`); the line pays the whole projected charge and enters `materialize`, so the command is **schemaVersion 9** when `materialize` is non-empty and 8 otherwise. Every plan is posted back to `…/review` in the plan form before the proposal is stored, so `plan_changed` is caught at proposal time as well as at confirm. The card shows the resulting split per charge (loan key, date, principal, interest). v9 joins cheaply: all reads go through the command service, no chat-role grant. Receipt images stay out. | Owner decision 1 and the 30 October answer; the screen's rules are reused, not re-implemented. |
| D4 | **Excluded commands** (not in the catalogue): `partner.create/update/delete` (changes login email, role and the AI Reviewer flag itself: an assistant must not alter its own authorization; the Management screen keeps it); `cash-openings.initialize` (needs the screen's reviewed basis hash); `payment.correct` with `receiptMode:'replace'` and `loan.close` with a receipt (image passthrough; the PWA flow stays; owner confirmed 30 October); `analytics.refresh` with mode `Full` (long job; `Recent` allowed). Every delete and `settlement.reverse/cancel` and `loan.default` stay **included** per owner decision 1 (confirmed 30 October), flagged `destructive` so the card says so; the Confirm tap is the scoped authorization for that one action. `partner.*` exclusion confirmed by the owner on 30 October. No notification is forced by any path: the chat service never calls the notification routes and no push is sent for proposals (decision: no push in this batch). | AGENTS.md hard rules (authority, credentials); DESIGN.md §1 out of scope (attachments). |
| D5 | **Who**: at turn begin the store reads `"AI Reviewer"` for the actor (same transaction, read role) and resolves the actor for `command` through the capability policy; only when both hold is `propose_action` registered for that turn and `/proposals` routes answer. Otherwise the tool is absent, the prompt tells the model to answer "I can only read records for you; use the app screens", and the routes answer 403 `reviewer_required` / `command_required`. | Owner decision 3; a non-reviewer gets a plain reply, no card (Echo). |
| D6 | **Proposal record** (migration V118, table `pwa_chat_proposals`): `id uuid` (= the command's `requestId`), `thread_id`, `message_id` (the user message of the proposing turn), `partner_id`, `kind` (`operation`\|`payment`), `operation`, `command text` (the exact JSON body sent to the command service, ≤ 64 KB), `card jsonb` (server-built: label, target, values, `changes:[{field,before,after}]`, `consequences:[text]`, `destructive`), `state` CHECK IN (`pending`,`executing`,`done`,`failed`,`expired`,`cancelled`,`unknown`), `created_at`, `expires_at`, `claimed_at`, `settled_at`, `attempts smallint`, `outcome jsonb` (`{status,code,result,recordedAt}` from the command service), `record jsonb` (`{type,id,paymentId}` for the UI link), `cancel_reason`. Owner `mw_chat_owner_<env>`, V104 conventions (`REVOKE … FROM PUBLIC`, boundary comment, DELETE/TRUNCATE refused `55000`, UPDATE only through the owner functions, PROD agent default privileges revoked); **not** granted to `mw_chat_read_<env>` (a Partner's command details are not readable through the other Partner's `sql_query`). | Card state must survive reloads and devices and be exactly-once; the existing tables are append-only journals of a different shape. |
| D7 | **Lifecycle**: `pending` for **15 minutes** (`expires_at`); a new user message in the thread cancels its pending proposals (`cancel_reason:'superseded'`); explicit cancel route; typed "yes" never confirms. Confirm: `pwa_chat_proposal_claim_v1` moves `pending→executing` under the row lock (expired → sets and returns `expired`; `executing` → 409 `proposal_executing`; a settled state → returns the stored outcome, so a repeat tap or second tab gets the same answer). Then the service reads the command status (`GET /api/operations/:id` or `/api/payment-commands/:id`); `recorded` → settle; `unresolved` → `POST`; busy 409 `command_busy` → retry twice (1 s, 2 s) then `failed` `command_busy`; `recorded` applied/posted → `done`, rejected → `failed` with the command service's code; timeout, network error or 5xx after the POST → `unknown`. `unknown` (and `executing` older than 2 minutes, a dead instance) is reconciled by the status read on every `GET …/proposals/:id` and on the next Confirm with the same id; the UI polls `unknown` every 3 s for up to 5 minutes and never shows it as failed or offers retry. **As implemented (Byte, accepted by Archie)**: a proposal still `unknown` 2 minutes after its claim settles as `failed` `command_unavailable` when a fresh status read at that moment still answers `unresolved` (the command service journals the outcome in the write's own transaction and times out at 14 s, below the 15 s client timeout, so no journal row after 2 minutes means nothing was applied); elapsed time alone never settles it, a `recorded` answer always wins, and the old request id is never re-POSTed afterwards (a new proposal gets a new id). Stale record: the command service's own checks answer `source_conflict` / `plan_changed` / `selection_unavailable`, which the card shows with the PWA's existing localized table (`savedRejectionMessage`), distinct from `proposal_expired`. | Owner decision 2; AGENTS.md reconciliation rule (reconcile an unknown outcome before retrying); idempotency key is the command's own request id. |
| D8 | **Grounding**: the card renders only server fields (`card`), never model text; amounts are decimal strings formatted by the PWA. `before` values come from a fresh read at proposal time (read provider or SQL tool), `after` from the validated command. Consequences are rule-based and bounded (Byte implements exactly: payment settles every due charge of the borrower; `loan.close` with the payoff amount from the close preview; `payment.correct` replaces the plan; `destructive`). The tool result is an observation, so figures the model repeats in its text pass the grounding check. | Echo; R088 grounding stays enforced. |
| D9 | **Protocol**: SSE event `proposal` `{proposal}` when a proposal is created in the turn (before `message`); assistant message rows carry `proposal` (null or the object) in `pwa_chat_messages_v1`/`pwa_chat_message_v1` (helpers replaced in place in V118), so history shows the card with its current state on any device. Routes: `GET /api/chat/threads/:tid/proposals/:id` (state, reconciles `unknown`), `POST …/proposals/:id/confirm`, `POST …/proposals/:id/cancel`; all 404 for another Partner's thread, 403 for a non-reviewer. Proposal object: `{id,threadId,messageId,kind,operation,state,card,expiresAt,outcome?:{code},record?,createdAt,settledAt?}` (the raw command is never returned). One proposal per turn (`ONE_PROPOSAL_PER_TURN` tool error); a new proposal cancels earlier pending ones in the thread. | Echo's state list; §3.5 event order kept. |
| D10 | **Feedback to the model**: the turn's opening JSON gains `recent_actions` (the thread's last five proposals: operation, target label, state, outcome code, settled time) read with `pwa_chat_proposals_v1` at turn begin; the replay journal is untouched. | The model sees what happened without rewriting append-only history. |
| D11 | **Switch**: Terraform `chat_commands.enabled` (default false in PROD) → env `CHAT_COMMAND_URL`, pinned by `business-config.mjs` for role `chat` to the exact per-env command URL; absent → no tool, routes 404, catalogue not loaded. Rollback is the variable; V118 is additive and stays. | Reversible for two users. |

| D12 | **"One card, Confirm all"** (owner decision, 30 October 2026, after the DEV test where six requested charge edits produced one proposal: the one-per-turn rule plus supersede-on-new-message). **Data model**: a *group* of 1..20 `pwa_chat_proposals` rows sharing `card.group = {id, index, count}`; `group.id` is the first line's proposal id (the head); a single change is a group of one, so the UI has one shape. Each line keeps its own request id, command, `expectedVersion`, journal row and row-level state (D6/D7 unchanged per line). **Migration V119, functions only** (no table, column, grant or role change; V118 is applied on DEV and immutable): `pwa_chat_proposal_create_v1` replaced in place to accept `{group:[line…]}` (1..20 lines validated as today, distinct ids, one `created_at`, inserted in one transaction; the 23505 one-group-per-turn rule and the supersede of earlier pending rows stay); `pwa_chat_message_json_v1` re-patched so an assistant message carries `proposals` (array ordered by `card.group.index`) instead of `proposal`. Claim, settle, cancel and listing are unchanged. Rejected alternative (no migration): one row whose `command` is an envelope of lines; `pwa_chat_proposal_json_v1` strips per-line outcomes, progress could not persist and `record` (4 KB) would be misused for line states. V119 is cheapest and safest: two in-place function replacements, the chat owner window only, and PROD receives V118 and V119 together on the later owner instruction. **Tool shape**: `propose_action({changes:[{operation,target_id,inputs}…]})`, one call per turn carrying every change (the engine runs a round's calls concurrently and a second round is not guaranteed, so several calls per turn are unreliable with both providers); the prompt says "put every change the Partner asked for in one call; never split across turns". **Limits**: 1..20 lines; one group per turn; one Partner and thread by construction; operations may mix. **Dependencies**: duplicate targets in one group are refused (`DUPLICATE_TARGET`: an update carries the full field set, so two edits of one record are always one line); a line may not reference an id another line creates (`DEPENDS_ON_NEW_RECORD`); versions are neither chained nor re-read, so every before→after on the card is verifiable and a stale line fails with `source_conflict` while the others run. **Payments**: `payment.record` is allowed as a line but must be the only line for its borrower in the group (`PAYMENT_LINE_ALONE`: another line on that borrower's charges or loans would drift the plan); `loan.close` follows the same rule (`PAYMENT_LINE_ALONE` names both: a payment or a close is the only line for its borrower, so charge edits run as their own group first, then the payment or close as the next card, which matches the owner's Oum sequence of 30 October); `payment.correct/delete/move-interest` are covered by the duplicate-target rule (one per payment, one predecessor). DEV evidence (Chase, thread `c867d053…`): the model made exactly one `charge.update` (applied) and deferred the other five "one card each, in later turns" because the tool description, `prompt.mjs` and `V118:141` all said one proposal per turn; the five remaining edits were separate records (one 29-Oct charge per loan), so D12's group covers that request in one card. **Execution**: `POST …/proposals/:head/confirm` runs the lines sequentially in proposed order on the Confirm request; with `Accept: text/event-stream` it streams `line {index,id,state,code?,record?}` after each line, then `group {state}` and `done` (JSON at the end otherwise). Each line is claimed only when its turn comes (pending→executing), then the D7 protocol per line (status read, POST, busy retries, settle). A failed or unknown line does not stop the group. Group deadline 180 s from the confirm start (Cloud Run 300 s, HTTP 290 s): lines not yet claimed at the deadline stay `pending`; no background continuation. **Skipped** is a UI-derived state: a pending or expired line in a group that has at least one settled line; the card's button then reads "Confirm N remaining" and a new confirm runs only the pending lines. Expiry stays 15 minutes from creation for every line. **Exactly-once and reconcile**: per line as in D7 (an `unknown` line is never re-POSTed; `GET …/proposals/:head` returns the group and reconciles its unknown or stale-executing lines). Group state is derived: `executing` while any line runs; `unknown` if any line is unknown; `pending` if any line is pending and none settled; else `done` when every settled line is done, `failed` otherwise. `recent_actions` lists lines. **UI**: one card with the count in the header, one block per line (operation label, target label, changed fields only as before → after; unchanged fields collapsed behind "+n unchanged"; Chase's DEV finding: a long carry-forward note was repeated unchanged on the card, so an unchanged `notes` is never shown expanded), a per-line status chip (pending, running, done with the record link, failed with the localized code, unknown polling, skipped, cancelled, expired), the destructive warning when any line is destructive, Confirm label "Confirm 6 changes / ยืนยัน 6 รายการ" (one line: "Confirm change / ยืนยันรายการ"), and a stacked layout at 320 px. Cancel on the head cancels every pending line. | The owner's four requirements; proportional to two users; V118 stays immutable. |

Rejection codes the chat layer adds (localized by the PWA, one line each): `reviewer_required`, `command_required`, `proposal_expired`, `proposal_cancelled`, `proposal_executing`, `command_busy`, `command_unavailable` (503 or malformed answer from the command service), `outcome_unknown` (state, not a failure). Command-service codes pass through unchanged.
