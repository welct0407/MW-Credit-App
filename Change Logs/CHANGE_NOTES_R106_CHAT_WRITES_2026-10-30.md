# Change notes — R106 chat writes (proposal and confirm), 2026-10-30

## Purpose
The in-app chatbot (read-only since R090) may modify data: the model proposes one exact command, the PWA shows a confirmation card, and nothing executes until the Partner taps Confirm. Owner decisions of 30 October 2026 (fixed): every existing write command of the PWA screens is in scope; writes go through the existing command contracts and command service with the same authorization, idempotency, audit and reconciliation (no raw DML, no reviewer DML tools); a confirm card every time; only Partners flagged `Partners."AI Reviewer"` who also hold the `command` capability may propose or confirm; one tested migration for chat proposal records is approved (DEV first; PROD on a later owner instruction). This note is the executable design (Archie) and is updated by Dewey as the batch lands.

## Changes

### Design decisions (Archie, 30 October 2026)

| # | Decision | Reason |
| --- | --- | --- |
| D1 | **Execution path: the chat service calls the command service over HTTPS on the Confirm request**, forwarding the Partner's own Firebase ID token (`Authorization: Bearer`), no `Origin` header, `X-MW-Wake-Deadline` as the PWA sends it, client timeout 15 s. The command service already journals the actor from the token, so audit, idempotency (`requestId`), optimistic versions and the busy/reconcile protocol are unchanged. In-process execution is rejected: `pwa_submit_operation_v2` and the payment functions require `mw_app_<env>` membership, and `services/chat/guard.mjs` refuses that membership on the login that runs model-written SQL (keep the refusal; add a regression test). The device offline queue is not used: a chat confirm is online only, nothing is queued on the device. | Simplest reversible design; no new IAM, DB role or grant; the AI Reviewer gate lives in chat code because the command service cannot tell chat requests apart. |
| D2 | **Tool shape: one generic `propose_action` over a static command catalogue**, plus `action_catalogue(operation)` for the argument definitions. Catalogue file `services/chat/assets/command-catalogue.json` (one entry per supported operation: label EN/TH, target rule, fields with type, enum, description, which fields are references the host verifies, `destructive` flag, consequence rules). The host fills `requestId` (= proposal id, `crypto.randomUUID()`), `targetId` for creates, `expectedVersion` (fresh read at proposal time: `_nativeVersion` from the read provider, or `pwa_*_version_v2` through the SQL tool), `predecessorRequestId` for `payment.*` (`pwa_payment_head_v2`), `receiptId:null`; it then validates with `canonicalOperation` / `canonicalCommand` and refuses with a tool error naming the field. A unit test proves every catalogue entry's sample canonicalizes and that the catalogue and `canonicalOperation`'s operation list agree (minus the exclusions below). | Per-command tools would mean ~45 declarations in every round (tokens, drift); one tool plus a catalogue keeps the registry small and the argument contract testable. |
| D3 | **Payments**: `propose_action('payment.record', …)` builds a manual payment command **schemaVersion 8** (no `materialize`): the model names the borrower, charges (default: every due charge), amount, date, method, cash account, notes; the host reads the draft (`GET /api/payment-drafts/:borrowerId?scope=due`, command service, same token) and allocates **the full remaining amount of each chosen charge** (`amountReceived` = the sum; the model may not override it). Partial allocations, next-projected-charge booking through a payment (v9 `materialize`) and receipt images stay in the Payments screen. | Full-charge plans are derivable without re-implementing the screen's allocation rules; v9 needs the projected-charge functions the chat roles do not hold. Scope reduction flagged for the owner (Open questions). |
| D4 | **Excluded commands** (not in the catalogue): `partner.create/update/delete` (changes login email, role and the AI Reviewer flag itself: an assistant must not alter its own authorization; the Management screen keeps it); `cash-openings.initialize` (needs the screen's reviewed basis hash); `payment.correct` with `receiptMode:'replace'` and `loan.close` with a receipt (image passthrough; the PWA flow stays); `analytics.refresh` with mode `Full` (long job; `Recent` allowed). Every delete and `settlement.reverse/cancel` and `loan.default` stay **included** per owner decision 1, flagged `destructive` so the card says so; the Confirm tap is the scoped authorization for that one action. No notification is forced by any path: the chat service never calls the notification routes and no push is sent for proposals (decision: no push in this batch). | AGENTS.md hard rules (authority, credentials); DESIGN.md §1 out of scope (attachments). |
| D5 | **Who**: at turn begin the store reads `"AI Reviewer"` for the actor (same transaction, read role) and resolves the actor for `command` through the capability policy; only when both hold is `propose_action` registered for that turn and `/proposals` routes answer. Otherwise the tool is absent, the prompt tells the model to answer "I can only read records for you; use the app screens", and the routes answer 403 `reviewer_required` / `command_required`. | Owner decision 3; a non-reviewer gets a plain reply, no card (Echo). |
| D6 | **Proposal record** (migration V118, table `pwa_chat_proposals`): `id uuid` (= the command's `requestId`), `thread_id`, `message_id` (the user message of the proposing turn), `partner_id`, `kind` (`operation`\|`payment`), `operation`, `command text` (the exact JSON body sent to the command service, ≤ 64 KB), `card jsonb` (server-built: label, target, values, `changes:[{field,before,after}]`, `consequences:[text]`, `destructive`), `state` CHECK IN (`pending`,`executing`,`done`,`failed`,`expired`,`cancelled`,`unknown`), `created_at`, `expires_at`, `claimed_at`, `settled_at`, `attempts smallint`, `outcome jsonb` (`{status,code,result,recordedAt}` from the command service), `record jsonb` (`{type,id,paymentId}` for the UI link), `cancel_reason`. Owner `mw_chat_owner_<env>`, V104 conventions (`REVOKE … FROM PUBLIC`, boundary comment, DELETE/TRUNCATE refused `55000`, UPDATE only through the owner functions, PROD agent default privileges revoked); **not** granted to `mw_chat_read_<env>` (a Partner's command details are not readable through the other Partner's `sql_query`). | Card state must survive reloads and devices and be exactly-once; the existing tables are append-only journals of a different shape. |
| D7 | **Lifecycle**: `pending` for **15 minutes** (`expires_at`); a new user message in the thread cancels its pending proposals (`cancel_reason:'superseded'`); explicit cancel route; typed "yes" never confirms. Confirm: `pwa_chat_proposal_claim_v1` moves `pending→executing` under the row lock (expired → sets and returns `expired`; `executing` → 409 `proposal_executing`; a settled state → returns the stored outcome, so a repeat tap or second tab gets the same answer). Then the service reads the command status (`GET /api/operations/:id` or `/api/payment-commands/:id`); `recorded` → settle; `unresolved` → `POST`; busy 409 `command_busy` → retry twice (1 s, 2 s) then `failed` `command_busy`; `recorded` applied/posted → `done`, rejected → `failed` with the command service's code; timeout, network error or 5xx after the POST → `unknown`. `unknown` (and `executing` older than 2 minutes, a dead instance) is reconciled by the status read on every `GET …/proposals/:id` and on the next Confirm with the same id; the UI polls `unknown` every 3 s for up to 5 minutes and never shows it as failed or offers retry. Stale record: the command service's own checks answer `source_conflict` / `plan_changed` / `selection_unavailable`, which the card shows with the PWA's existing localized table (`savedRejectionMessage`), distinct from `proposal_expired`. | Owner decision 2; AGENTS.md reconciliation rule (reconcile an unknown outcome before retrying); idempotency key is the command's own request id. |
| D8 | **Grounding**: the card renders only server fields (`card`), never model text; amounts are decimal strings formatted by the PWA. `before` values come from a fresh read at proposal time (read provider or SQL tool), `after` from the validated command. Consequences are rule-based and bounded (Byte implements exactly: payment settles every due charge of the borrower; `loan.close` with the payoff amount from the close preview; `payment.correct` replaces the plan; `destructive`). The tool result is an observation, so figures the model repeats in its text pass the grounding check. | Echo; R088 grounding stays enforced. |
| D9 | **Protocol**: SSE event `proposal` `{proposal}` when a proposal is created in the turn (before `message`); assistant message rows carry `proposal` (null or the object) in `pwa_chat_messages_v1`/`pwa_chat_message_v1` (helpers replaced in place in V118), so history shows the card with its current state on any device. Routes: `GET /api/chat/threads/:tid/proposals/:id` (state, reconciles `unknown`), `POST …/proposals/:id/confirm`, `POST …/proposals/:id/cancel`; all 404 for another Partner's thread, 403 for a non-reviewer. Proposal object: `{id,threadId,messageId,kind,operation,state,card,expiresAt,outcome?:{code},record?,createdAt,settledAt?}` (the raw command is never returned). One proposal per turn (`ONE_PROPOSAL_PER_TURN` tool error); a new proposal cancels earlier pending ones in the thread. | Echo's state list; §3.5 event order kept. |
| D10 | **Feedback to the model**: the turn's opening JSON gains `recent_actions` (the thread's last five proposals: operation, target label, state, outcome code, settled time) read with `pwa_chat_proposals_v1` at turn begin; the replay journal is untouched. | The model sees what happened without rewriting append-only history. |
| D11 | **Switch**: Terraform `chat_commands.enabled` (default false in PROD) → env `CHAT_COMMAND_URL`, pinned by `business-config.mjs` for role `chat` to the exact per-env command URL; absent → no tool, routes 404, catalogue not loaded. Rollback is the variable; V118 is additive and stays. | Reversible for two users. |

Rejection codes the chat layer adds (localized by the PWA, one line each): `reviewer_required`, `command_required`, `proposal_expired`, `proposal_cancelled`, `proposal_executing`, `command_busy`, `command_unavailable` (503 or malformed answer from the command service), `outcome_unknown` (state, not a failure). Command-service codes pass through unchanged.

### Test plan (financial/authorization change: positive, negative, role, retry/concurrency, reconciliation; proportional-validation table)

Unit (`npm test`):
- `chat-proposals.test.mjs`: every catalogue entry's sample canonicalizes; host fills `requestId`, `targetId` (create), `expectedVersion`, `predecessorRequestId`; model-supplied `requestId`/`expectedVersion`/`amountReceived` (payment) are refused; unknown operation and excluded operations (`partner.update`, `cash-openings.initialize`, `payment.correct` replace) → `UNSUPPORTED_OPERATION`; payment plan equals the full remaining of the chosen charges and `amountReceived` is the sum; card `changes` before/after and the three consequence rules; second `propose_action` in a turn → `ONE_PROPOSAL_PER_TURN`.
- `chat-command-client.test.mjs` (fake fetch): token forwarded, no `Origin`, 15 s abort; status `recorded` before any POST; `unresolved` → POST; 409 `command_busy` retried twice then `failed`; timeout after POST → `unknown`; malformed body → `command_unavailable`.
- `chat-handler.test.mjs`: routes 404 for another Partner, 403 for non-reviewer and for a reviewer without `command`, 404 when `CHAT_COMMAND_URL` is absent; confirm idempotent (repeat → same outcome, concurrent second call → 409 `proposal_executing`); expired → `proposal_expired`; cancel; new message cancels pending; `proposal` event precedes `message`; `?stream=0` message carries `proposal`.
- `chat-config.test.mjs`: `CHAT_COMMAND_URL` pinned per environment, refused for the reader and command roles; `chat-guard` regression: `mw_app_<env>` membership still refused.
- `chat-pwa.test.mjs`: reducer handles `proposal`; card state machine (pending with countdown, executing, done with record link, failed localized, expired, cancelled, unknown polling, offline disabled).

Database (`Test-CI` groups): `Test-Chat.sql` for V118 (create cancels earlier pending; claim transitions and expiry; settle only from executing/unknown; DELETE/TRUNCATE refused; another Partner's thread `42501`; non-reviewer `42501`; messages carry `proposal`); `Test-AccessMatrix.sql` (api role EXECUTE count 11 → 16; read role has no access to `pwa_chat_proposals`); `Test-ProdDefaultPrivileges.sql` replay; `public-functions.sql` regenerated.

Playwright (`tests/e2e/chat.spec.ts`, stubbed chat origin, Desktop Chrome and Pixel 7): card renders from server fields after the reply; Confirm disabled offline; confirm → done with the record link; failed shows the localized code; unknown polls then resolves; a new message hides the card as cancelled; reload shows the persisted state.

Terraform: `fmt -check`, `validate`, `test` for both stacks in `Development checks`.

DEV end to end (one pass after the DEV deploy, synthetic data, reviewer Partner): record a payment on a synthetic borrower, edit a loan, create an expense, delete the expense; one `source_conflict` forced by editing the loan in the screen between proposal and confirm; one reconciled `unknown` (command service stopped during the POST, then restarted); the non-reviewer Partner gets the plain refusal; the command journal shows the Partner as actor for each request id.
