Owner request (24 October 2026): receipts do not always arrive in the borrower's 3-member group (the partner forwards a slip in a direct message; a referrer and referee share a 4-person group), so the agent cannot tell who paid. The borrower column `Communication Name` becomes the borrower's **payer name** (the sender name printed on slips); its old values are cleared and its old purpose is dropped. Designed by Archie (A). Verified against the code on 24 October 2026; file references are to the current tree.

### Decisions
1. **Slip extraction.** `receipt_image.SCHEMA`/`PROMPT` gain one string field `payer_name`: the sender (payer) name exactly as printed, title included, masked characters kept as `x`, empty when absent or unreadable; never the recipient. `checked()` requires the new key. The recognizer API returns it unchanged; `services/receipts/recognizer-client.mjs` accepts results with or without `payer_name` during the rolling deploy (the `recipient_numbers` pattern), and the first shape without it is treated as unreadable.
2. **Normalization and comparison** live in two parity modules, `integration-agent/src/mw_integration_agent/payer_name.py` and `services/receipts/payer-name.mjs`, driven by one shared vector file `tests/fixtures/payer-name-cases.json`. `payer_key(text)`: NFC, trim, casefold, drop a leading title (`นาย`, `นาง`, `นางสาว`, `น.ส.`, `ด.ช.`, `ด.ญ.`, `คุณ`, `mr`, `mrs`, `ms`, `miss`, with or without a dot), collapse whitespace, turn every mask run (`*`, `•`, `●`, `×`, or two or more consecutive `x`/`X`; a single `x` is a letter) into one `*`. Script = Thai when any Thai letter is present, else Latin. `compare(stored, slip)` returns `match`, `mismatch` or `unknown`: `unknown` when either key is empty, has fewer than 3 unmasked letters, or the scripts differ (Thai on one side, English on the other: banks print either, so this is not evidence); otherwise tokens are compared in order, same token count required, each pair compatible when the pattern of one side (mask = one or more characters) fully matches the other side. **One name per borrower**, no variant set; **fill only if empty**, enforced in the database; no masked-to-less-masked upgrade (a poor stored name is corrected by hand in the borrower record, which stays editable). Different scripts therefore never block; they fall back to the conversation rule and do not fill.
3. **Agent decision table.** A new aware cutoff `payer_name_cutoff` gates everything below (jobs created before it behave as today). Partner forwarding reuses `receipt_forwarding_enabled` and `receipt_forwarder_partner_id`; no second partner identity.

| Context (how the job arrived) | Borrower determination | Stored name empty | `match`/`unknown` | `mismatch` | Name unreadable |
| --- | --- | --- | --- | --- | --- |
| C1 Borrower 1:1 DM (webhook) or C2 borrower sends in a 3-member group (poll) | Sender, as today | Proceed; **fill** on POSTED | Proceed | REVIEW `PAYER_NAME_MISMATCH` | Proceed, no fill |
| C3 Forwarder partner sends in a 3-member group (`FORWARDED`, as today) | Third participant, as today | Proceed; **fill** on POSTED | Proceed | REVIEW `PAYER_NAME_MISMATCH` | Proceed, no fill |
| C4 Group with 2+ enabled borrower participants (4+ persons), forwarder partner sends | New poll outcome `CANDIDATES` with evidence `candidate_borrower_ids`; resolved **after extraction**: exactly one candidate whose stored name matches | **Never fills** (the referrer/referee confusion is exactly this case) | Match → that candidate | Two matches → REVIEW `PAYER_NAME_AMBIGUOUS`; no match → REVIEW `PAYER_UNRESOLVED`; the name matches a non-participant borrower → REVIEW `PAYER_NOT_IN_GROUP` | REVIEW `PAYER_NAME_UNREADABLE` |
| C4' Same group, an enabled borrower sends | Sender (as today), compared against the sender's stored name | Proceed, never fills | Proceed | REVIEW `PAYER_NAME_MISMATCH` (hold names the participant whose stored name matches, if any) | Proceed, no fill |

Implementation notes: `process()` resolves the sender context before extraction (as today), extracts, then calls `resolve_payer(context, extraction, master)`, which returns the borrower or raises the codes above; `validate_receipt` adds `payer_name` (display form) to the receipt dict, so it travels inside the proposal. `receipt_borrower()` keeps re-verifying membership on every later pass; for C4/C5 jobs the resolved borrower id is persisted in the job `result` next to `forwarded_borrower_id` and re-checked against live masters (`BORROWER_CHANGED` as today). `receipt_master.MASTERS_SQL` adds `"Communication Name" payer`; the agent's whole-table SELECT on `"Borrowers"` is retained by V110, so **no grant change**. The partner DM is also the review channel: `ingest` already creates a job for every webhook image, and `decide_replies` gets one guard, a reply event whose text is empty and that carries an attachment is skipped (no `HOLD_REJECT_REQUIRED` acknowledgement for a forwarded slip). Group messages still arrive only through the poll; a message captured by both paths shares its job id and image hash, so it deduplicates as today. `conversation_poll_messages.outcome` has no CHECK constraint in the agent schema (V2), so `CANDIDATES` needs no agent migration.
4. **Reviewer confirmation.** The current cycle supports only `Reject` on a hold and creates proposals only for a determined borrower. The smallest change that lets the reviewer confirm a borrower is: every hold text (`receipt_hold.held_text`) gains the line `Payer on slip: <name>`; the six `PAYER_*` reasons get texts (the sixth, `PAYER_NAME_OTHER_BORROWER`, was added after Chase's review: the slip matches another borrower's stored name and not this borrower's), and `PAYER_UNRESOLVED`/`PAYER_NAME_AMBIGUOUS`/`PAYER_NOT_IN_GROUP` list the candidates (C4: group participants; C5: the matching borrowers, or none) and say: record it in the app, which stores the payer name for next time, or reply Reject. The confirmation is the PWA receiving form (the same reviewer, one screen, existing authorization). A number-reply on the hold that selects a candidate and re-queues the job for the normal Approve request is a separable follow-up, not built here: it is a new authorization surface for a two-person team. The owner accepted confirmation through the PWA form for this release on 24 October 2026.
5. **Write-back.** The agent command bumps to `schemaVersion` 8 with `payerName` (string or null, trimmed, NFC, 1 to 200 bytes, no control characters); `pwa_submit_agent_receipt_v1` accepts 7 and 8 until the agent is deployed on both environments (7 is dropped in a later release), as does `contract.mjs`. Inside the same sub-block as the `Payments` insert (the borrower row is already locked `FOR UPDATE`): `UPDATE "Borrowers" SET "Communication Name"=payer WHERE "Row ID"=borrower AND coalesce(btrim("Communication Name"),'')=''`, so a rejected outcome rolls it back and a replay of the same `requestId` returns the stored status without a second write; a different `payerName` under the same `requestId` is a `conflict`. The agent sends `payerName` only when the borrower was determined and the comparison was not `mismatch` (a mismatch never reaches posting). Audit: the command row (`pwa_payment_commands.canonical_json`) carries the name, the V97 row-change trigger records the borrower update, and `pwa_borrower_version_v2` changes, so an open borrower edit sees the normal version conflict. `pwa_submit_selected_charges_v1` gains `schemaVersion` 8 = 7 plus `payerName` (Bank Transfer only, like `bankReference`); 3 to 7 stay accepted for queued offline commands. Readback and proposal hashing are unaffected (the name is not a financial fact).
6. **Manual PWA path.** The recognition POST sends `X-Borrower-ID` (already a CORS-allowed header); `store.recognize` reads that borrower's stored name and returns `payer: {slipName, storedName, status}` with a warning code `payer_mismatch` ordered after `account_ambiguous`. `SelectedCharges.tsx` shows `Payer on slip: <name>` with the recognition notes, and on `mismatch` a `recognition-note` like the amount/account mismatch (warn, never block). The command carries `payerName` whenever the slip name was read; the database fills only if empty. FROM PUBLIC` and grants as V89/V96; `public-functions.sql` and the chat schema digest rebuilt at 111; data dictionary comment and `services/chat/assets/schema-digest.json` / `services/agent-conversations/native-manifest.json` describe the new meaning. ### Revision 2 (owner-approved, 24 October 2026): no review in a strong context, several payer lines, OCR tolerance, weak-context resolution, nickname hint
Supersedes the review-on-mismatch parts above (decisions 2 to 6 and the table). Goal: a receipt the old process posted automatically still posts automatically; the payer name only adds knowledge, never a hold, in a strong context. Built on branch `claude/payer-name-matching` (6995971), nothing deployed.

**R2.1 Strong context (C1 borrower DM, C2 borrower in a 3-member group, C3 forwarder in a 3-member group).** The conversation decides the borrower exactly as before the payer name existed. `PAYER_NAME_MISMATCH` and `PAYER_NAME_OTHER_BORROWER` are removed; `resolve_payer` never raises in a strong context. Amount, account, date, duplicate and proposal checks are unchanged. A readable slip name that is not already one of the borrower's lines is learned on POSTED (R2.2).

**R2.2 Several payer lines in `Communication Name`, one per line.** Line 1 is the borrower's own name; later lines are people who pay for them; cap 5 lines, 1000 bytes. The owner edits the column freely; `?` in a stored line is exactly one unknown letter (maps to the existing `ANY` marker in `payer_key`). Learning happens only on POSTED receipts in a strong context, on a hint-resolved or uniquely resolved weak-context receipt (R2.4, R2.5), and in the manual PWA path. Rule `learn(lines, slip)` in the parity modules: (i) some line `match`es and the slip has more unmasked letters than that line → replace that line; (ii) some line is `match` or `near` otherwise → no change; (iii) else, fewer than 5 lines → append; (iv) 5 lines → no change. The line order is kept, so line 1 stays the owner's choice. **SQL write**: the comparison stays in the parity modules; the command carries `payerLines: {before: string|null, after: string}` (`before` = the column value the caller read, `after` = the full new value, lines joined by `\n`, 1 to 5 lines, each 1 to 200 bytes, no control characters, `after <> before`), or `payerLines: null` for no learning. In the same sub-block as the `Payments` insert, after the row lock: `UPDATE public."Borrowers" SET "Communication Name"=after WHERE "Row ID"=borrower AND coalesce("Communication Name",'') IS NOT DISTINCT FROM coalesce(before,'')`. Drift since the caller read the column skips the learning (the payment still posts; the next receipt learns), a rejected outcome rolls it back, a replay of the same `requestId` returns the recorded status with no second write, another `payerLines` under the same `requestId` is a `conflict`. `payerName` (single string) is replaced by `payerLines` in both commands; the agent command stays schemaVersion 8 (7 still accepted), `pwa_submit_selected_charges_v1` stays 8 (3 to 7 accepted). **V111 is edited in place** (its comment, both function bodies, `Test-PayerName.sql`); condition: `flyway_schema_history` head is 110 or lower on `loan_manager_dev` and `loan_manager_prod` at merge time (the inventory records V110 as pending on both; the coordinator reports both at 110; either way V111 is applied nowhere). Byte or Forge records the two heads in the Checks table; if 111 is ever found applied, the change becomes V112 instead.

**R2.3 OCR tolerance (`near`).** `compare` returns `match`, `near`, `mismatch` or `unknown`. `near`: same token count, surname tokens compatible as today, given-name tokens (first token) of 4 or more letters on both sides, same length, exactly one differing position whose two letters are a look-alike pair from one shared table in the fixture (`ภ/ก`, `ณ/น`, `ล/ส`, `ด/ต`, `บ/ป`, `ช/ซ`, `ข/ฃ`, `ฎ/ฏ`, `ถ/ภ`, `ผ/พ`, `ฝ/ฟ`, `ค/ศ`, `ท/ห`, `อ/ฮ`; symmetric), everything else equal. A given name under 4 letters or a difference outside the table is `mismatch`. `near` counts as a match only when no other borrower has a line that is `match` or `near` for the same slip; the agent and the route apply that rule over all enabled borrowers. Pinned in `tests/fixtures/payer-name-cases.json` (`near` section plus the pair table), Python and JS parity tests read it.

**R2.4 Weak context (C4 4+ group, C5 forwarder DM).** Candidates = all enabled borrowers with any line `match` or `near` (line 1 and payer lines count the same; a borrower's own name never beats another borrower's payer line: borrower A never pays herself and borrower B always pays for her, so B's line 1 is `<payer P>` and A's line 2 is `<payer P>`; a slip from P makes both candidates). Narrow in order, stopping at the first step that leaves exactly one: (a) 4+ group: participants only; (b) the forwarder's hint (R2.5) when it names exactly one candidate, or, with no name candidates, exactly one enabled borrower (the hint is authoritative; in a 4+ group it must name a participant); (c) drop candidates with nothing due: `review_proposal.facts` charges with `date <= receipt date` and `principal + interest > 0`; (d) exact amount fit to exactly one candidate: the receipt amount equals one due charge's total, one due charge's interest, the sum of that candidate's due charges, or the candidate's payoff from `plan()` (`Loan Close`); (e) otherwise REVIEW `PAYER_UNRESOLVED` listing the remaining candidates (hold text: record it in the app, or reply Reject). A slip with no readable name and no hint → REVIEW `PAYER_NAME_UNREADABLE`. `PAYER_NAME_AMBIGUOUS` and `PAYER_NOT_IN_GROUP` are removed (a non-participant match is simply not a candidate after (a); several survivors are (e)). A weak-context review is not extra work: these slips were ignored or manual before. The resolved borrower is learned per R2.2 and persisted as `payer_borrower_id` with the step that chose it (`participants`, `hint`, `due`, `amount`) for the hold text and the audit.

**R2.5 The forwarder's nickname hint.** A hint is a text message from the configured forwarder, in the same conversation, sent after the slip and within 180 s, with no `reply_to`, not a command word (`review_resend.COMMANDS`) and not a decision word (`partner_review.APPROVE`, `hold_reply.REJECT`), whose normalized text (NFC, casefold, whitespace collapsed, one leading `พี่`/`p'`/`pi` dropped) equals exactly one enabled borrower's normalized `Borrower Name`, `Description` or `Instagram Username`; `Mali`, `Mali2` and `Mali3` are three different exact values. Several borrowers or none → no hint. **Window**: a weak-context job is not resolved before the earlier of 180 s after the slip and the forwarder's next message in that conversation (any text or image); `resolve_payer` returns `WAIT` and `process()` sets `retry_after` to the window end without spending an attempt. **Capture**: groups are read only by the poll, so `MESSAGE_FIELDS` adds `message` and `capture_conversation` stores the forwarder's texts that follow a `CANDIDATES`/`FORWARDED` slip into that job's `result` (`hint_texts`, text and timestamp, forwarder only, capped at 3) with `UPDATE receipt_jobs SET result=? WHERE id=? AND status='PENDING'`; the poll already re-reads the last 300 s, so a text arriving after the slip is picked up on the next minute. For the DM, `resolve_payer` reads the ingress `messages` table (read-only, as `decide_replies` does) for the forwarder's texts after the slip. **Separation from review replies**: a review or hold reply must carry `reply_to` equal to a notice message id (`authorize_reply`) and is parsed only in `decide_replies`; a hint has no `reply_to`, so it is never a reply, and `decide_replies` ignores any event without `reply_to` except the exact command words, so a reply is never a hint. A command word is excluded from hints explicitly. Tests cover the four crossings (hint, reply with text, command, image-only reply).
