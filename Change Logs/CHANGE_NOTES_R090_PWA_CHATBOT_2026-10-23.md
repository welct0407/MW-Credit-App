## Design resolutions (Archie)

Reviewed against `integration-agent/src/mw_integration_agent/` (`conversation_session.py`, `gemini_conversation.py`, `conversation_grounding.py`, `conversation_sql.py`, `conversation_tools.py`, `conversation_store.py`, `partner_conversation.py`) and the R085/R088 change notes. Nothing below re-opens an owner decision of design §1. Two items (10 and 12) touch text the design states differently; both are implementation detail, not owner scope, and are recorded here so the design is read with this note.

1. **Opening message.** The first user part of a turn is the JSON text `{"partner_language":<Partners."Language Preference">,"as_of":<ISO Bangkok>,"request":<message text>}` (the Python request minus `attachments_present`, `attachment_policy` and `writes_enabled`; the writes batch re-adds the last). On a new epoch the seed text (item 4) is a separate first part of the same user content, as `opening()` does. Grounding (`check(text, observations, instruction)`) receives the raw message text as `instruction`, not the JSON wrapper.

2. **Reply detection and nudges.** A model response with no `functionCall` part is the reply candidate; its text is the concatenation of its non-`thought` text parts. Empty text (signature-only or thought-only parts) gets `FINISH_NUDGE` once, as its own user content: `Answer now in plain text; do not call more tools.` A second empty response fails the turn with `INTERNAL` (log detail `REPLY_EMPTY`). `ROUND_NUDGE` text: `Tool-round limit reached. Do not call other tools; answer now in plain text with what you have.` It is appended as a separate user content after the `functionResponse` content of the round that reaches `maxRounds` (Vertex refuses mixed parts). A response after `ROUND_NUDGE` that still calls tools fails with `TOOL_ROUNDS_EXCEEDED` without running them.

3. **Rejections fed back without a `finish` tool.** The host checks the reply candidate in this order: length, then grounding. A failure appends the rejected model content (verbatim, so replay stays byte-identical) and a user content with the rejection text, then requests the next round. Texts: length `REPLY_TOO_LONG: <n> characters; the limit is 4000. Shorten the reply.`; grounding exactly R088's `rejection()`: `UNGROUNDED_AMOUNTS: <a>, <b> are not in this turn's observations. Remove them, or re-check the data with a tool and quote the observed figure. Attempt <n> of 3.` One shared attempt counter covers both kinds; the third rejection ends the turn with `GROUNDING_EXCEEDED` (the R088 behaviour). The client sees `retract {reason, attempt}` before the model's next round. Every reply is checked (no `CLARIFY`/`REFUSE` exemption; a clarifying question that lists figures must take them from this turn's tools).

4. **Epoch, seq and seed.** `pwa_chat_turn_begin_v1` always returns `history` (the rows of the thread's highest epoch, `seq` order, or an empty list) and `seed` (up to 200 most recent completed exchanges, oldest first, excluding the current message: user text and time, assistant text, status and time). The service decides: no rows → epoch 0; else the same epoch when `last.prompt_sha256 === prompt && (last.input_tokens ?? 0) <= historyTokenLimit`, otherwise epoch + 1 with no replayed rows and the seed text. A model change needs no rule of its own: the digest covers model, system text and tool declarations. New rows start at `last.seq + 1` (0 for a fresh epoch); `input_tokens` is written on the turn's last row only, as `promptTokenCount` of the last round. Seed text: header `Earlier conversation with this partner (context only; oldest first; Bangkok time[; N earlier exchange(s) omitted]):` then blocks `[DD-Mon-YYYY HH:MM] Partner: <text>` and `[stamp] Assistant: <text>` (or `Notice: <text>` for a failed turn), newest whole exchanges within `seedChars`, printed oldest first. `seedChars` 0 → the Python `HISTORY_NOTE` text verbatim; a seed build failure → `SEED_FAILED_NOTE` and the turn continues. The `RestartEpoch` path is Claude-only and is not ported; `Resend` (one identical re-request on `MALFORMED_FUNCTION_CALL`) is.

5. **Failed turns.** The assistant row of a failed turn stores the canned localized text in `text` (`text NOT NULL`): EN `I could not complete this request. Check the app before asking again.`, TH `ดำเนินการไม่สำเร็จ กรุณาตรวจสอบในแอปก่อนส่งคำขออีกครั้ง`, with `status='failed'` and the fixed `error_code`. No history rows; tool-call rows are kept. The seed prints this text as the `Notice` line.

6. **Error-code mapping (fixed list of §3.5).** `promptFeedback.blockReason` or `finishReason` in `SAFETY|RECITATION|BLOCKLIST|PROHIBITED_CONTENT|SPII` → `PROMPT_BLOCKED`; HTTP 404, and 429/503/529 after two retries, and 500/502/504 after one retry → `MODEL_UNAVAILABLE`; request timeout after one retry → `MODEL_TIMEOUT`; turn deadline → `TURN_TIMEOUT`; other 4xx, token unavailable, invalid or oversized response (8 MB), `MAX_TOKENS` and other finish reasons → `INTERNAL`. The raw cause goes to the service log only; `error_code` holds the fixed code.

7. **Streaming merge.** Chunks of one round merge into one `content.parts` list: text parts are concatenated while neither carries `thoughtSignature` or `thought:true`; a part with a signature closes the group and is stored whole; `functionCall` parts are kept whole; `finishReason` comes from the last chunk, `usageMetadata` from the last chunk that has one. The merged content is what is appended, journaled and replayed. `delta` events carry only non-thought text as it arrives.

8. **SSE `delta` versus `retract`.** The service streams `delta` while a round's chunks arrive. If that round then ends with a `functionCall` part, it emits `retract {reason:'tool_round', attempt:0}` so the client clears the provisional text silently (no "Checking the figures again…" label); that reason is added to the design's two. `retract` with `ungrounded` or `too_long` carries the attempt number (1 or 2). Order per turn: `accepted`, then per round `round` → `tool`… or `delta`… → (`retract`), then `message` or `error`, then `done`. `: ping` every 15 s. `tool.summary`: `read_records` → the table name, `data_catalogue` → `catalogue`, `sql_query` → `<n> rows`, `loan_payoff` → `loan payoff`, `sum_field` → `sum`.

9. **Observations and grounding input.** `read_records`, `sum_field`, `sql_query` and `loan_payoff` results are wrapped `{observation:'observation-N', as_of, ...value}` with N in call order of the round (so `sum_field` can cite them); `data_catalogue` answers unwrapped. `grounding.mjs` receives the map of wrapped observations and the raw message text; it is a rule-for-rule port including `META_KEYS`, `COUNT_COLUMN`, `RATIO_COLUMN`, the caps and the exact money, percent and exemption regexes (Unicode-aware; use `u` flag and `\p{..}` only where Python needed none).

10. **Native read tools in process.** `createConversationReadProvider` in `services/agent-conversations/read-provider.mjs` imports `resolveConversationActor`, which requires the agent-conversation policy secret and `Partners."IG Integration Enabled"`; the design excludes both (§3.3, §4.2). Resolution: the factory gains an optional `resolveActor` dependency defaulting to `resolveConversationActor` (one line, existing callers unchanged); the chat service passes `policy:null` and `resolveActor: async (client, _policy, _workload, partnerId) =>` re-reading `Partners` by `Row ID = partnerId`, asserting one row whose trimmed lower-case "Login Email" equals `actor.loginEmail`, and returning `actor`; `context = {workload:{issuer, subject}, signal}`, `input.actorPartnerId = actor.partnerId`. The orchestrator names Byte the single writer of `read-provider.mjs` for this batch (path not in the §11 list). `data_catalogue` and `read_records` keep the Python result shapes: `data_catalogue('', '')` → `{apps:{oltp:{version:<manifestSha256>,tables:[..]},olap:{..}}}`; with a table → `{app, table, key, permission:<legacyPermission>, condition:'', columns:{name:{Type:<sourceType>, nativeStatus}}, guidance}` with `writable_fields` and `protected_table` dropped and `guidance` = `Read-only native catalogue. Use Ref keys to link records; aggregate with sum_field or sql_query.`; `read_records` keeps the validation codes (`PAGE_LIMIT_MUST_BE_INTEGER_1_TO_100`, `INVALID_RECORD_QUERY`, `USE_KEYS_OR_SEARCH`, `USE_FILTER_OR_KEYS_OR_SEARCH`, `UNKNOWN_SEARCH_FIELD`, `SEARCH_FIELD_REQUIRED`, `READ_BOUND_REACHED_NARROW_SEARCH`, `RECORD_IDENTITY_MISMATCH`, `REQUESTED_RECORD_MISSING`, `APP_SCHEMA_CHANGED_OR_FIELD_UNAVAILABLE`), the 1001-row probe, the per-turn cache keyed on (app, table, predicate, projection) and the `{app, table, total_matched, offset, rows, complete}` answer with `_nativeVersion` passed through. The catalogue of each scope is fetched once per turn. Tool errors reach the model as `{error:<code>}` text only (never HTTP bodies or stacks): a non-`ConfigurationError` becomes `TOOL_FAILED_INSPECT_BEFORE_RETRY`.

11. **Database privileges for the tools.** The IAM user `mw-credit-app-chat-{env}` holds no direct grants; it inherits `EXECUTE` on `pwa_chat_*_v1` from `mw_chat_api_{env}` and `SELECT` on business relations from `mw_chat_read_{env}` (the read provider's own SQL runs under this inheritance, as `mw_integration_agent` does today). `sql_query` additionally runs `SET LOCAL ROLE mw_chat_read_{env}` inside `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`, so the model's SQL can call no `pwa_chat_*_v1` function and see no `pwa_chat_*` table; the tool asserts `session_user = <IAM user>`, `current_user = mw_chat_read_{env}` and `current_database() = loan_manager_{env}` before executing. Statement timeout `20s` for the tool, `statementTimeoutSql('command')` for RPCs and the read provider. Reads of one round run with a concurrency cap of 4 on the chat pool (pool size at least 5).

12. **`pwa_chat_turn_begin_v1` and `_complete_v1` contracts.** `message jsonb = {id, text}`. Return: `{state:'claimed', message:{id,seq,createdAt}, thread:{id,model,title,messageCount}, partnerLanguage, history:{epoch,rows:[{seq,role,content,prompt_sha256,input_tokens}]}|null, seed:[...]}` or `{state:'completed', user, assistant}` for a re-POST of a finished turn. A thread with a user row claimed under 5 minutes ago and no assistant row raises SQLSTATE `55006` with message `turn_in_progress` (handler → 409); a stale claim is re-claimed in place (`claimed_at` reset). `message_count` at 2,000 raises `54000` `thread_full` (handler → 400 `invalid_request`). Placeholder title on create is the literal `New chat` (the PWA shows `t('New chat','แชทใหม่')` for it); `_complete_v1` replaces it with the first line of the first user message, at most 120 characters. `_complete_v1` inserts the assistant row at `seq = user.seq + 1`; a late completion after a re-claim fails on `UNIQUE (thread_id, seq)` and the service logs it and ends that stream with `error INTERNAL`. Both functions re-resolve `actor` against `Partners` (`42501` otherwise), which is the design's identity re-check before commit; no separate call.

13. **Usage per turn.** Sum over rounds of `promptTokenCount`, `candidatesTokenCount`, `thoughtsTokenCount`, `cachedContentTokenCount`; `rounds` = model requests; `attempts` = HTTP attempts including retries; `latency_ms` = wall time from claim to commit.
